# ADR-0017. Системная роль «Владелец»

- **Статус:** принят
- **Дата:** 2026-10-15

## Контекст

До подэтапа 3c системных ролей было две — `admin` и `member`, и все системные администраторы были равны: любой мог
назначить администратором кого угодно (в том числе приглашением), снять или деактивировать другого администратора.
Компании (~100 человек) нужен один человек с исключительными правами, которого никто не может отключить или
понизить: он отвечает за то, кто управляет системой. Ему же позже достанется то, что не должен видеть обычный
администратор, — аналитика трудозатрат сотрудников (этап 9). Из 3b перенесено: Владелец видит в дереве
по-настоящему пустые папки (ADR-0013, «Изменения»).

Ограничение PM: принцип ADR-0005 не меняется — системная роль, и Владелец тоже, не даёт доступа к содержимому
пространств без роли в них.

## Решение

### Роли и права

`users.role`: `owner | admin | member`. **Системный администратор** — `admin` или `owner`: `User::isAdmin()` (во
фронтенде `isSystemAdmin`) возвращает `true` для обоих, поэтому все проверки админки сразу покрывают Владельца.
Исключительные права — `User::isOwner()` и политики:

| Действие | Владелец | Администратор | Участник |
|---|---|---|---|
| Назначить / снять администратора (`UserPolicy::updateRole`) | ✅, не себе | 403 | 403 |
| Деактивировать / восстановить участника | ✅ | ✅ | 403 |
| Деактивировать / восстановить администратора | ✅ | 403 | 403 |
| Что-либо с учётной записью Владельца (роль, статус, приглашение) | 403 | 403 | 403 |
| Пригласить с ролью member / admin (`InvitationPolicy::create` получает роль) | ✅ / ✅ | ✅ / 403 | 403 |
| Повторить / отозвать приглашение приглашённого администратора | ✅ | 403 | 403 |
| Передать владение (`UserPolicy::transferOwnership`) | ✅, другому | 403 | 403 |
| Аналитика трудозатрат — гейт `view-work-time-analytics` | ✅ | ✗ | ✗ |
| Остальная админка (группы, «Структура», пространства, журнал, корзина…) | ✅ | ✅ | 403 |

Правило одной строкой — `UserPolicy::manages`: Владельцем не управляет никто, администраторами — только Владелец,
участниками — любой системный администратор. Роль `owner` не назначается ни сменой роли, ни приглашением
(`Rule::enum()->only(UserRole::ASSIGNABLE)`, 422) — только передачей владения. Роли Владельца в пространствах и его
членство в группах ведутся как у всех: это доступ к пространствам (ADR-0005, ADR-0012), а не его учётная запись.

Подсказки интерфейсу — с сервера, как `permissions.*` у пространств: в админском списке пользователей
(`AdminUserResource`) — `permissions {update_role, deactivate, reactivate, manage_invitation, transfer_ownership}`,
у приглашений — `can_resend`/`can_revoke` с учётом политики. Нет разрешённых действий — нет кнопок.

### Основной механизм и страховка

Основной механизм — политики (403) и Actions (422): попытка понизить, деактивировать или снять Владельца через API
никогда не доходит до базы (тест на каждую попытку). `ChangeUserRoleAction` и `DeactivateUserAction` сами отказывают
для Владельца — на случай вызова не из HTTP. Ограничения БД — страховка от ошибок вне приложения:

- **не больше одного Владельца** — уникальный частичный индекс `users_single_owner ON users ((true)) WHERE role = 'owner'`;
- **Владелец всегда активен** — CHECK `users_owner_active`;
- **Владелец не пропадает** — отложенный (`DEFERRABLE INITIALLY DEFERRED`) constraint trigger `users_owner_kept`:
  если в транзакции роль Владельца сняли, к коммиту должен появиться новый.

Итого Владелец ровно один с момента назначения; пустая база (до первого администратора) — без Владельца.

### Передача владения

- Из интерфейса: «Администрирование → Пользователи → Передать владение» — выбор активного сотрудника и свой пароль.
  `POST /api/v1/admin/users/{user}/transfer-ownership {password}`: `current_password`, лимит `password-change`
  (как у смены пароля). `TransferOwnershipAction` под блокировкой строк делает получателя Владельцем, бывшего —
  администратором, в одной транзакции. Неактивному (приглашённому, деактивированному) — 422.
- Роль читается из базы на каждый запрос, поэтому права бывшего Владельца понижаются сразу, в его же открытой сессии
  (следующий запрос — уже как администратор, без перезахода).
- Аварийно, если Владелец недоступен (уволился, потерял доступ): `php artisan app:transfer-ownership EMAIL` только
  на сервере, с подтверждением (`--force` — без вопросов); назначает Владельца и там, где его нет.
  `php artisan app:owner` — кто Владелец и с какого момента. Стенд PM — `make pm-owner-show`,
  `make pm-transfer-ownership EMAIL=…`.
- Журнал: `user.ownership_transferred {from_user_id, to_user_id, via}` — subject новый Владелец, только id;
  `via`: `admin_panel` (автор — бывший Владелец), `console` (без автора, `meta.source = console`), `migration`.

### Появление Владельца

- Миграция `add_owner_role`: Владельцем становится самый ранний по `created_at` активный администратор (событие с
  `via: migration`, `from_user_id: null`). Миграция обратима: `down()` делает Владельца администратором и снимает
  ограничения и триггер.
- `app:create-admin`: если Владельца ещё нет — создаётся Владелец (`user.created {role: owner, via: console}`).

### Дерево и «Структура» (ADR-0013)

- `GET /navigation` Владельцу дополнительно отдаёт по-настоящему пустые папки — на любой глубине нет ни одного
  пространства, ни активного, ни архивного (в том числе внутри архивных папок), — с `empty: true`; в сайдбаре —
  приглушённо, с пометкой «пустая». Остальные правила не меняются: пометок «нет доступа» нет, недоступное не
  показывается никому; пустая папка внутри папки без доступных пространств не видна и Владельцу (родитель скрыт).
- «Структура» помечает активные узлы, которых нет в дереве текущего пользователя, значком «Не видно в вашем
  дереве» — по тому же `GET /navigation`, что у сайдбара. Утечки нет: «Структура» и так показывает системному
  администратору все названия.

### Аналитика трудозатрат (этап 9)

`Gate::define(AppServiceProvider::VIEW_WORK_TIME_ANALYTICS)` — только Владелец. Маршруты этапа 9 закрываются этой
проверкой и попадают в `AdminAccessMatrixTest`.

## Последствия

- Обычный администратор не может повысить себя или другого, понизить или отключить администратора и Владельца.
  Если Владелец недоступен, передача — только на сервере (`app:transfer-ownership`): это осознанно.
- `AdminGuard` («не оставить систему без администратора») считает и Владельца; пока Владелец есть, проверка
  проходит всегда — она страхует базу без Владельца.
- **Матрица доступа админских маршрутов** (`tests/Feature/Access/AdminAccessMatrixTest.php`): каждый маршрут
  `/admin/*` и справочники × Владелец / администратор / участник, маршруты над пользователем — с целями участник /
  администратор / Владелец / сам; новый админский маршрут без строки в матрице роняет CI.
- Тесты: `Admin/OwnerRoleTest` (попытки через API — 403/422, ограничения БД, гейт), `Admin/TransferOwnershipTest`
  (в том числе понижение в открытой сессии), `Console/TransferOwnershipCommandTest`, `Database/OwnerRoleMigrationTest`
  (назначение, обратимость), `Navigation/NavigationTreeTest` (пустые папки), `AccessMatrixTest` (Владелец без роли —
  404); фронтенд — `UsersPage.test`, `TreePanel.test`, `StructurePage.test`, `ProfilePage.test`, `guards.test`.
- Демо-данные: `owner@selen.test` — Владелец, `admin@selen.test` — обычный администратор; пустая папка
  «Новые направления». E2E: `e2e-owner@selen.test`, папка «E2E Пустая».

## Изменения

### Аналитика трудозатрат — по праву, не только Владелец (2026-10-22, LATER-47, решение PM)

**Контекст.** Раздел «Аналитика трудозатрат (этап 9)» закрепил сводные отчёты по времени только за Владельцем (гейт
`view-work-time-analytics`, строка в таблице «Роли и права»). Решение PM 22.10 (комментарий в LATER-47): аналитику
видит не только Владелец — он может поручить сбор этой информации другому человеку. Этапа 9 ещё нет, маршрутов за
гейтом пока нет.

**Решение.**
1. Аналитику трудозатрат (сводные отчёты по времени, этап 9) видит тот, у кого есть право «смотреть аналитику
   трудозатрат». Право выдаётся человеку лично или группе — как остальные права «Прав 2.0» (LATER-47) — и действует,
   если его даёт хотя бы один источник (ADR-0012).
2. Владелец видит аналитику всегда и может делегировать: выдать право другому человеку или группе. Могут ли выдавать
   его системные администраторы и получает ли его кто-то по умолчанию — вопросы PM в плане «Прав 2.0».
3. Это право отдельное от права «видеть время других участников» в карточке (таймер и ручной учёт времени, этап 6,
   LATER-1; решение PM 22.10): то — время по одной карточке, это — сводные отчёты.
4. Код до «Прав 2.0» не меняется: гейт пока пропускает только Владельца (`AppServiceProvider`, `OwnerRoleTest`).
   В «Правах 2.0» право входит в каталог, гейт проверяет его; маршруты этапа 9 остаются за гейтом и в матрице доступа —
   с пользователем, которому право выдано лично, через группу, и без права.

**Последствия.** Строка «Аналитика трудозатрат» в таблице «Роли и права» и раздел «Аналитика трудозатрат (этап 9)»
описывают поведение до «Прав 2.0». Обычный администратор без права аналитику по-прежнему не видит. Строка этапа 9
в `docs/roadmap.md` — «по праву, лично или через группу».

### «Права 2.0», П2b-1 (2026-10-23, ADR-0024): администраторы — у компаний

`users.role` — `owner | member`: роль `admin` перешла в `company_members.is_admin` «Компании 1» (миграция; CHECK
обновлён, ограничения Владельца — один, всегда активен, не пропадает — не менялись). Владелец — участник всех компаний,
видит админку всех компаний, назначает и снимает администраторов компаний; администратор компании управляет только
своей компанией (`User::administers`, `Company::permissionsOf`): права компании по умолчанию — все, кроме «удалять
пользователей» и «аналитика трудозатрат». Передача владения: бывший Владелец — администратор своих компаний. В API
роль человека — в контексте компании (`role: owner | admin | member`), поэтому интерфейс прежний. Гейт аналитики
трудозатрат — по-прежнему только Владелец (по праву — П2c). `make admin` создаёт администратора «Компании 1».
