# ADR-0003. Журнал событий append-only и задел на метрики

- **Статус:** принят, изменён на этапе 1 (персональные данные — см. «Изменения»)
- **Дата:** 2026-10-12

## Контекст

Ключевое продуктовое требование на будущее — **измеримые метрики потока** (lead time, cycle time), позже KPI.
Метрики считаются по истории: когда карточка вошла в работу, когда закончилась. Если история
изменяема или неполна, метрики врут. На этапе 0 нужно залогировать события аутентификации и управления
пользователями и заложить принципы, по которым позже будут писаться перемещения карточек.

## Решение

### Таблица `event_log`

| Поле | Тип | Зачем |
|---|---|---|
| `id` | bigint identity | строгий порядок вставки, компактный индекс (ULID здесь не нужен — запись никогда не создаётся вне БД) |
| `occurred_at` | timestamptz(6), UTC | **время факта**; задаёт приложение, а не БД — так возможны импорт и бэкфилл. Микросекунды — для порядка событий одной операции |
| `event_type` | varchar(100) | тип из каталога `App\Enums\EventType`, формат `область.событие_в_прошедшем_времени` |
| `actor_id` | ULID, FK users, null | кто сделал; `null` — система (консоль) или аноним (неудачный вход) |
| `subject_type`, `subject_id` | varchar | над чем; `subject_type` — короткий morph alias (`user`, `invitation`, позже `card`) |
| `payload` | jsonb | доменные данные события — снимок **идентификаторов и значений перечислений** (например, `role_changed: {from, to}`); без персональных данных |
| `meta` | jsonb | технический контекст: только `source` (http/console). IP и user agent — в `auth_audit` (см. ниже) |

Индексы: `(subject_type, subject_id, occurred_at)` — история объекта; `(event_type, occurred_at)` — выборки
для метрик; `(actor_id, occurred_at)` — действия пользователя.

### Принципы

1. **Append-only на двух уровнях.** Модель `EventLogEntry` бросает исключение на update/delete.
   Триггер PostgreSQL (`event_log_append_only`, уровень STATEMENT) запрещает UPDATE, DELETE и TRUNCATE
   любому клиенту, включая ручные SQL-запросы. Промт требовал запрет на уровне приложения; уровень БД добавлен,
   потому что он дешевле любой проверки и защищает от ошибок вне приложения. Обойти может только владелец
   схемы через `DROP`/`ALTER TABLE` — это намеренно видимое действие (миграция).
2. **Единая точка записи** — `App\Services\EventLog\EventRecorder::record()`.
3. **Запись в той же транзакции**, что и доменное изменение (вызов внутри Action). Либо сохраняются
   и данные, и событие, либо ничего. Исключение — неудачный вход: событие пишется до выброса ошибки.
4. **Снимок без персональных данных.** Payload содержит значения на момент события (`from`/`to` роли,
   статуса, категории колонки) и идентификаторы связанных объектов. Email, имена, названия, введённые
   пользователями тексты в журнал **не пишутся**: пользователи не удаляются, поэтому id всегда разрешим
   в актуальное имя через `users`.
5. **Типы событий не переименовываются и не удаляются** — они уже лежат в журнале. Новый смысл — новый тип.
6. Секреты (пароли, токены) и персональные данные (email, имена, IP, user agent) в payload и meta не пишутся.
   Проверяется тестом: после сквозного сценария в `event_log` нет ни одного email и имени пользователя.
7. Порядок ключей в JSONB не сохраняется — сравнивать payload как множества.

### Задел на метрики: специализированная таблица перемещений карточек (этап 1)

> Реализовано на этапе 1b — актуальная схема и определения в [ADR-0006](0006-card-transitions.md).

Для lead/cycle time общий `event_log` неудобен: запросы по JSONB медленнее и не типизированы, а метрики —
это основная аналитическая нагрузка. Поэтому перемещения карточек будут писаться **в специализированную
append-only таблицу `card_transitions` по тем же принципам** (UTC, `occurred_at` из приложения, запись
в транзакции перемещения, запрет UPDATE/DELETE триггером). Параллельно в `event_log` пишется событие
`card.moved` для общей ленты истории.

**Обязательное требование к `card_transitions`:** помимо идентификаторов колонок храним **снимок на момент
перемещения**:

| Поле | Назначение |
|---|---|
| `card_id` | карточка |
| `board_id` | доска на момент перемещения (карточку могут перенести на другую доску) |
| `from_column_id`, `to_column_id` | колонки (null для создания/архивации) |
| `from_category`, `to_category` | **категория колонки на момент перемещения** (например, `queue` / `in_progress` / `done`) |
| `occurred_at` | время перемещения, timestamptz(6), UTC |
| `actor_id` | кто переместил |

Причина: колонки будут переименовывать и менять им категорию. Если метрики считать по текущей категории
колонки, исторические lead/cycle time «поплывут» задним числом. Со снимком категории метрика за прошлый
месяц остаётся неизменной, что бы ни происходило с настройками доски.

Lead time = от первого входа в категорию «очередь/бэклог» (или создания) до входа в «готово»;
cycle time = от первого входа в «в работе» до «готово». Точные определения — решение этапа 1.

### Масштаб

~100 пользователей дают десятки тысяч событий в месяц — PostgreSQL справится без оптимизаций годами.
Если объём вырастет, таблицы разбиваются декларативным партиционированием PostgreSQL по месяцам
(`occurred_at`) без изменения кода записи.

## Последствия

- Журнал нельзя «почистить» средствами приложения. Восстановление из бэкапа сохраняет триггер
  (проверяется `make backup-verify`).
- Тесты используют `RefreshDatabase` (транзакции), а не `DatabaseTruncation` — TRUNCATE запрещён.
- Удаление ПДн по запросу субъекта (152-ФЗ) не требует трогать журнал: достаточно анонимизировать
  запись в `users` и очистить `auth_audit` (задача в `docs/backlog.md`).

## Изменения

### Этап 1 (2026-10-12): персональные данные вынесены из журнала — решение PM

**Контекст.** В этапе 0 в payload писались email и имена (приглашение, создание администратора,
неудачный вход, смена профиля), а в meta — IP и user agent. Неизменяемый журнал с ПДн конфликтует
с правом на удаление данных.

**Решение.**
1. В `payload` и `meta` журнала — только идентификаторы и значения перечислений. Смена профиля пишет
   список изменённых полей (`fields`), значения — только для часового пояса (не ПДн).
2. IP и user agent событий входа (`auth.*`) пишутся в отдельную таблицу **`auth_audit`**:
   `occurred_at`, `event_log_id` (связь с событием), `event_type`, `user_id`, `email_attempted`
   (только если пользователь с введённым адресом не найден — иначе факт перебора адресов терялся бы),
   `ip`, `user_agent`. Таблица **не append-only**: срок хранения 12 месяцев
   (`config/selen.php → auth_audit.retention_months`), очистка — `model:prune` ежедневно в 03:30 UTC
   (модель `AuthAuditEntry` с трейтом `Prunable`).
3. Запись в `auth_audit` делает тот же `EventRecorder` — отдельной точки входа нет, забыть невозможно.
   Из консоли (нет HTTP-запроса) записи в `auth_audit` не создаются.
4. В админке «Журнал событий» IP показывается из `auth_audit`, пока запись не удалена по сроку.
5. Записанные на этапе 0 dev-данные с ПДн не мигрируются — пересоздаются `make fresh` (production ещё нет).

**Последствие.** Обычный `TRUNCATE event_log` теперь сначала упирается во внешний ключ из `auth_audit`;
`TRUNCATE ... CASCADE` блокирует триггер журнала (тест проверяет именно этот вариант).

**2026-10-15, LATER-45 (корзина карточек, ADR-0015).** Гарантия append-only журнала **не менялась**: триггер
в исходном виде, обходов нет. Удаление карточки — мягкое; в журнал добавлены `card.deleted` и
`card.restored_from_trash` (payload пустой, subject — карточка).

**2026-10-23, «Права 2.0», П2b-1 (компании, ADR-0024).** У события есть компания — `event_log.company_id`: компания
объекта (`HasCompany`: у пространства, узла дерева, группы, метки, типа, приглашения — своя колонка, у доски, карточки
и всего внутри — через пространство) или явная (`EventRecorder::record(..., company:)` — действия админки компании над
человеком: смена роли, деактивация, приглашение). Пусто — событие без компании «о человеке» (вход, выход, пароль,
передача владения) или системное. Колонка добавлена `ADD COLUMN … DEFAULT '<Компания 1>'` и `DROP DEFAULT`: старые
строки получили «Компанию 1» на уровне каталога, **без UPDATE** — триггер append-only не срабатывал и не менялся
(тест `CompaniesMigrationTest`: те же строки на тех же местах, `ctid` и `xmin`). Журнал админки компании — её события
и события без компании о её людях; системные события без человека (неудачный вход с неизвестным email, позже —
создание компании) — только Владельцу (решения PM 23.10 и 26.10).

### П2c-2 (2026-10-28): IP и браузер входов на экране — решение PM

IP и браузер событий входа (вход, неудачный вход, выход, смена и сброс пароля, подтверждение нового email —
`auth.email_changed`) остаются в `auth_audit` со сроком **12 месяцев**, не в журнале. На экране «Журнал событий» их видят
все, у кого право компании «Смотреть журнал событий» (Владелец, администратор компании, участник с правом): IP и браузер
коротко («Chrome 131 · macOS»), полная строка User-Agent — в подсказке. Журнал фильтруется по человеку (`user_id`:
автор или объект события); список людей для фильтра — `events/people`, только имена.
В режиме «несколько компаний» (ADR-0026) входы человека с «домами» в нескольких компаниях — события «о человеке» — видны
журналам всех его компаний, с IP и браузером; правило то же (решение PM 2026-10-29).
