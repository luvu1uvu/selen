# ADR-0008. Режим «только свои карточки»

- **Статус:** принят
- **Дата:** 2026-10-13

## Контекст

В пространство иногда нужно пустить человека, которому нельзя видеть всё: подрядчика, сотрудника
другого отдела, который участвует в одной задаче. Роли ADR-0005 (admin / editor / commenter) управляют тем,
**что можно делать**, но не тем, **что видно**: любой участник видит все карточки пространства.

Требование PM: это **ограничение доступа, а не фильтр**. Пользователь с ограничением видит только
карточки, где он заказчик, ответственный или участник. Остальные для него не существуют — в том числе
по прямой ссылке, в счётчиках колонок, в истории, связях, комментариях, файлах и любых будущих
списках и поиске.

## Решение

### Данные

- Флаг `space_members.own_cards_only` (bool, по умолчанию false). Ставит и снимает только администратор
  пространства: `PATCH /spaces/{KEY}/members/{user}` с полем `own_cards_only` (роль и флаг можно поменять
  одним запросом, атомарно).
- Применим к ролям editor и commenter. Администратор пространства видит всё: CHECK в БД
  `NOT (role = 'admin' AND own_cards_only)`, попытка включить — 422. При назначении роли admin флаг
  снимается (событие с `via: role_changed`).
- «Своя» карточка: `cards.customer_id = user` или `cards.responsible_id = user` или строка
  в `card_participants`. Это те же поля, что показываются в карточке, — отдельного списка доступа нет.
- Событие `space.member_restriction_changed {user_id, from, to[, via]}`.

### Единая точка правила — `App\Services\Cards\CardVisibility`

| Метод | Где используется |
|---|---|
| `canSee(User, Card)` | политики (через `ChecksSpaceRole::allowCard`), проверка упомянутых (этап 2b) |
| `present(User, Card)` | связанная карточка в связях, блокировках и ленте истории: номер и название или `{hidden: true}` (2c) |
| `scope(Builder, User, Space)` | любые выборки карточек для пользователя: доска, поиск, архив (2c) |
| `isRestricted(User, Space)` | правило «не потерять доступ», флаг `permissions.restricted` в ответе карточки |

Роль и флаг читаются одной строкой `space_members` и кешируются на экземпляре `Space`
(`membershipOf()`; `roleOf()` использует его же) — как кеш роли из ADR-0005.

### Проверка доступа

- Новый метод трейта `ChecksSpaceRole::allowCard(actor, card, ?permits)`: **сначала видимость, потом роль**.
  Невидимая карточка — `denyAsNotFound()` (404, тот же ответ, что для несуществующей), для любой роли
  и любого действия. Видимая — дальше обычные правила роли, архива пространства и доски (403).
- Все политики вложенных сущностей карточки (комментарии, файлы, чек-листы, ссылки, связи, блокировки —
  этапы 2b и 2c) проверяют доступ через карточку, поэтому ограничение действует в них без отдельного кода.

### Где применяется (полный список; новые места дописываются сюда)

| Место | Как | С какого подэтапа |
|---|---|---|
| Доска `GET boards/{id}` | `cards` — только видимые (`scope`) | 2a |
| Счётчики карточек в колонках | считаются клиентом по тому же списку `cards`; сервер отдаёт только счётчик свёрнутой доски (ниже) | 2a |
| Панель карточки, переходы `GET cards/{card}`, `…/transitions` | `CardPolicy::view` → 404 | 2a |
| Любые изменения карточки (поля, люди, метки, перемещение, архив) | `CardPolicy::update` → 404 раньше 403/422 | 2a |
| Комментарии, файлы (включая отдачу через X-Accel), чек-листы, ссылки | политики через карточку | 2b |
| Ссылка на файл `GET /files/{id}` (веб-маршрут, браузер открывает сам) | `AttachmentPolicy::view` → `allowCard`: чужая карточка — та же страница «Файл не найден или нет доступа», что и «нет такого» | UI-1b |
| Подсказка @ и упоминания в описании и комментариях | только те, кто видит карточку (`canSee`), иначе 422 | 2b |
| Связи, блокировки (`CardResource.relations`, `.blocks`) | `present()`: невидимая карточка → `{hidden: true}` («Скрытая карточка» без номера и названия); связать или заблокировать можно только видимой (иначе 422 «не найдена»), связь со скрытой не убрать | 2c |
| Поиск `GET spaces/{KEY}/cards`, архив `GET boards/{id}/archived-cards` | `scope` | 2c |
| Лента истории `GET cards/{card}/history` | `CardPolicy::view`; id невидимых карточек в payload заменяются на `"hidden"` и не попадают в справочник `refs.cards` | 2c |
| Фасад доски `cards[].can_edit` | `SpaceAccess::allowsOnCard`: при источнике editor с ограничением перетаскиваются только свои | 3a |
| Участники пространства | при ограничении во всех источниках — только список людей, без источников доступа и групп (`viewAccessSources`) | 3a |
| Список досок пространства `GET spaces/{KEY}/boards` | `cards_count` — счётчик свёрнутой доски: активные карточки, видимые пользователю (`scope`), одним запросом на все доски | пакет «Раскладка», PR 3 |

Консольные инструменты (`make metrics`) и журнал событий в админке работают вне пространства и
ограничению не подлежат: журнал хранит только идентификаторы (ADR-0003).

### Правила изменения людей (поправки PM)

- **Не потерять доступ своим действием (B).** Если пользователь с ограничением сменил заказчика или
  ответственного так, что перестал бы видеть карточку, он автоматически становится участником
  (событие `card.participant_added` с `via: keep_access`). Убрать себя из участников, если после этого
  карточка станет недоступна, нельзя (422 с объяснением) — это может сделать только другой пользователь.
  Код: `CardPeople::keepAccess()`, `RemoveCardParticipantAction`.
- **Упоминания (A, этап 2b).** Упомянуть можно только того, кто видит карточку: иначе на этапе 4 он получит
  уведомление о карточке, которую не может открыть. Подсказка @ и серверная проверка документа используют
  одно правило — `CardVisibility::canSee`.

### Тесты

- Матрица доступа (`AccessMatrixTest`): каждый маршрут с `{card}` проверяется для пользователя с ограничением
  (editor и commenter): чужая карточка — 404 с единым телом ответа; своя (как заказчик, ответственный,
  участник) — как обычно для роли. Новый маршрут карточки попадает в проверку автоматически.
- `OwnCardsOnlyTest`: флаг и его инварианты, доска и счётчики, прямые ссылки, потеря доступа, «не потерять
  доступ», число SQL-запросов доски не зависит от числа карточек.

## Последствия

- Любой новый список карточек обязан пройти через `CardVisibility::scope`, любая новая сущность внутри
  карточки — проверять доступ через `CardPolicy`/`allowCard`. Это правило записано в CLAUDE.md.
- Пользователь с ограничением видит доски и колонки пространства (структура не секретна) и список участников
  пространства (нужен для назначения людей), но не чужие карточки.
- Ограничение не делает чужие карточки «приватными» от остальных: это ограничение одного участника,
  а не свойство карточки.
- Если понадобится ограничение на уровне доски или группы, расширяется `CardVisibility`; политики и
  контроллеры не меняются.

## Изменения

**2026-10-14, этап 3 (группы пользователей, ADR-0012).** Флаг `own_cards_only` есть и у личного участия, и у
доступа группы (`space_groups`). Режим действует, только если **все** источники пользователя с ограничением; если
хоть один источник без ограничения — видны все карточки. Изменять карточку можно, если есть источник, роль которого
разрешает действие и который либо без ограничения, либо карточка «своя» (`SpaceAccess::allowsOnCard`).
`CardVisibility` читает права через `Space::accessOf()` вместо `membershipOf()`.

**2026-10-15, LATER-45 (корзина карточек, ADR-0015).** `CardVisibility` отвечает и за карточки в корзине:
`canSee()` — false для всех (404, включая системного администратора), `present()` — `{hidden: true, deleted: true}`
(«Удалённая карточка»). Выборки исключают их сами (`SoftDeletes` у `Card`); записи, которые ссылаются на карточку,
грузят её `withTrashed()` и передают в `CardVisibility`.

**2026-10-20, пакет «Раскладка», PR 3 (ADR-0019).** Сервер отдаёт ещё один счётчик карточек — `cards_count` в списке
досок пространства (у свёрнутой доски карточки не загружаются). Он считается через `scope()`, как выборка доски:
пользователь в режиме «только свои карточки» видит число своих карточек. Строка — в таблице мест применения.
