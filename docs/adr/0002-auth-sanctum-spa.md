# ADR-0002. Аутентификация: Sanctum SPA, сессии в PostgreSQL

- **Статус:** принят
- **Дата:** 2026-10-12

## Контекст

SPA и API работают на одном домене. Требования: вход/выход, «запомнить меня», смена и сброс пароля,
rate limiting, **деактивированный пользователь не может войти и его активные сессии завершаются**.
Промт предлагал хранить сессии в Redis.

## Решение

1. **Laravel Sanctum в режиме SPA (cookie-сессии)**, без API-токенов. `statefulApi()` в `bootstrap/app.php`,
   CSRF-cookie через `/sanctum/csrf-cookie`. Таблица `personal_access_tokens` не создаётся; если когда-то
   понадобятся токены (интеграции, мобильное приложение) — отдельный ADR.
2. **Сессии храним в PostgreSQL (`SESSION_DRIVER=database`), а не в Redis — отклонение от промта.**
   Причина: в таблице `sessions` есть `user_id`, поэтому сессии конкретного пользователя можно надёжно
   найти и удалить. В Redis ключи сессий не индексируются по пользователю. Database-драйвер — вариант
   Laravel по умолчанию начиная с 11-й версии. Нагрузка ~100 пользователей для PostgreSQL ничтожна.
   Redis остаётся для кеша, очередей и rate limiting.
3. **Завершение сессий** (`App\Services\Auth\UserSessions::terminate`): удаляет строки `sessions` пользователя
   и меняет `remember_token` — старые cookie «Запомнить меня» перестают действовать. Применяется:
   - деактивация — все сессии;
   - сброс пароля по почте — все сессии;
   - смена пароля в профиле — все, кроме текущей (для текущего устройства cookie «Запомнить меня» перевыпускается).
4. **Второй рубеж** — middleware `active` (`EnsureUserIsActive`) на всех защищённых маршрутах: если у неактивного
   пользователя всё же есть живая сессия, она завершается, ответ 401.
5. **«Запомнить меня»** — стандартный механизм Laravel, срок 30 дней (`config/auth.php → guards.web.remember`).
6. **Rate limiting** — именованные лимитеры в `AppServiceProvider` (`login`, `password-reset`, `password-change`,
   `invitations`), русские сообщения 429.
7. **Сброс пароля** — стандартный Password Broker Laravel; письмо ведёт на страницу SPA. Ответ на «забыли пароль»
   одинаков для существующих и несуществующих email; неактивным письмо не отправляется.
8. Middleware `guest` в API не используется: ему некуда перенаправлять. Повторный вход просто заменяет сессию;
   SPA сама не показывает форму входа вошедшему.

## Последствия

- Таблица `sessions` растёт; старые сессии чистит встроенный garbage collector Laravel (lottery).
- При горизонтальном масштабировании сессии уже общие (в БД) — дополнительных действий не нужно.
- Для проверки сценариев с cookie в тестах есть хелпер `tests/Support/Browser.php` (свой набор cookie,
  сброс guard'ов между запросами — как отдельный процесс php-fpm в production).

## Изменения

### Подэтап 3c (2026-10-16, LATER-57): вкладка замечает смену пользователя в браузере

**Контекст.** Cookie сессии общие для всех вкладок и окон браузера. Если в соседней вкладке вышли и вошли под
другим пользователем, открытая вкладка продолжала считать пользователем прежнего (он кэширован на 60 секунд), а
данные при переходах перечитывала уже от имени нового — показывала смесь двух пользователей (найдено PM: значки
«Не видно в вашем дереве» по чужому дереву). При завершении сессии (401) сбрасывался только текущий пользователь,
данные прежнего оставались в кэше.

**Решение.**
1. Вкладка сообщает серверу, от чьего имени работает: каждый запрос (кроме `/auth/me` и `/auth/logout`) несёт заголовок
   `X-Selen-User` с id пользователя вкладки. Middleware `tab-user` (`EnsureSessionUserMatches`) на маршрутах вошедших:
   в сессии другой пользователь — **409 `session_changed`**; заголовка нет (вкладка открыта до обновления кода или ещё
   не знает пользователя) — **409 `session_unverified`**: запрос с сессией не выполняется молча от имени того, кто сейчас
   в сессии. Без проверки: `/auth/me` (кто вошёл — сервер говорит сам), выход (выйти можно из любой сессии), файл
   вложения `GET attachments/{id}` (его грузит сам браузер — `<img>`, `<video>`, «скачать» — без заголовков; доступ
   проверяется правами пользователя сессии, действий нет) и публичные маршруты (вход, восстановление пароля,
   приглашение). Проверяются только запросы SPA (Sanctum `fromFrontend`); других клиентов API нет. Middleware стоит
   после аутентификации, но до троттлинга и привязки моделей (`prependToPriorityList`): чужие запросы не тратят
   попытки лимитов, ничего не пишут. Тест сверяет: каждый маршрут вошедших, кроме названных, с проверкой.
2. Вкладка (`frontend/src/app/queryClient.ts`, `installSession`) на 409 перечитывает пользователя (`/auth/me`, один раз
   на несколько ответов) и данные; пользователю показывается текст сервера — «В этом браузере выполнен вход под другим
   пользователем. Действие не выполнено…» или «Страница устарела. Действие не выполнено — обновите страницу».
3. Любая смена пользователя вкладки — вход, выход, принятие приглашения, завершение сессии (401), 409 — сбрасывает все
   данные, кроме самого пользователя (`resetQueries`): открытые экраны загружаются заново от имени нового.
4. Попутно (точечное ревью): `active` (`EnsureUserIsActive`) стоит до привязки моделей — деактивированный с уцелевшей
   сессией получает 401 и на существующий, и на несуществующий ключ пространства (раньше 401/404 различали их).

Первый вариант (сервер подписывал ответы id, вкладка отклоняла ответ при расхождении) заменён после точечного ревью:
он отклонял ответ на уже выполненное действие (действие от имени нового пользователя + «Попробуйте ещё раз» → дубли)
и ломал принятие приглашения во вкладке, где кто-то вошёл.

**Последствия.** Следующий пользователь в том же браузере не видит данных предыдущего, и ни одно действие вкладки не
выполняется от имени другого пользователя или молча без заголовка. Новый маршрут вошедших, который браузер открывает
сам (картинка, файл), — `withoutMiddleware('tab-user')` с комментарием и строкой в тесте `SessionUserMatchTest`.
Тесты эмулируют SPA: `actingAs` в `TestCase` и помощник `browser()` сами шлют `X-Selen-User`. Права, как и раньше, проверяет сервер по сессии. Тесты: backend
`Auth/SessionUserMatchTest` (409 без изменений, порядок относительно лимитов, гость, принятие приглашения,
деактивированный), frontend `app/session.test.tsx`, E2E `acceptance/stage-3/tc-3.31.spec.ts` (смена сессии в той же вкладке).

**2026-10-22, UI-1b (LATER-51): веб-маршрут ссылки на файл.** Единственный веб-маршрут приложения — `GET /files/{id}`
(ADR-0010, «Изменения»): ссылку на файл браузер открывает сам — без Referer/Origin, поэтому Sanctum не считает её запросом
SPA, и `/api/v1` для неё не годится. Маршрут — на той же web-сессии (guard `web`), без `tab-user`; гость и
деактивированный — 302 на `/login?next=/files/{id}`, страница входа принимает только такой `next` (не открытый
редирект). Защита API не менялась: `/api/v1` — по-прежнему только для запросов SPA, CSRF — как раньше.
