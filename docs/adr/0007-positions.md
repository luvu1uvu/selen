# ADR-0007. Порядок карточек, колонок, дорожек и досок: дробные ключи

- **Статус:** принят
- **Дата:** 2026-10-13

## Контекст

Карточки в ячейке, колонки, дорожки и доски упорядочены вручную. Требования: перестановка без массового
перенумерования соседей; сервер — источник истины; перемещение, отправленное по устаревшим данным
(вкладка открыта давно, realtime появится только на этапе 3), не должно ломать порядок на сервере.

Варианты:
1. Целые позиции 1, 2, 3 — вставка в середину требует перенумеровать хвост (много UPDATE, гонки).
2. Числа с плавающей точкой (середина между соседями) — точность кончается после ~50 вставок в одно место,
   нужна периодическая перебалансировка.
3. **Дробные ключи-строки (fractional indexing)** — между любыми двумя ключами всегда есть ещё один;
   используются в Figma, Linear и др.

## Решение

1. **Строковые ключи дробного индекса.** Порт алгоритма `rocicorp/fractional-indexing` (CC0) —
   `App\Support\FractionalIndex`, ~150 строк, юнит-тесты сверяют результаты с эталонными значениями
   оригинальной библиотеки. Перестановка меняет позицию только одного элемента.
2. **Колонки `position` объявлены с `COLLATE "C"`** — побайтовое сравнение. С обычной (языковой) collation
   PostgreSQL сортировал бы `a` и `A` иначе, чем алгоритм, и порядок «поехал» бы.
3. **Ключи считает только сервер.** Клиент сообщает соседей, которых видел: `after_id` (элемент выше/левее)
   и `before_id` (ниже/правее). `App\Services\Positions\Positioner`:
   - берёт `after_id`, если элемент всё ещё в этом списке, и сам читает следующего соседа из БД;
   - иначе `before_id` (и предыдущего соседа из БД);
   - иначе ставит в конец списка.

   Поэтому запрос по устаревшим данным в худшем случае поставит карточку чуть иначе, чем видел
   пользователь, но никогда не сломает порядок и не создаст дубликат.
4. **Гонки.** Вставки в одну ячейку доски сериализуются `pg_advisory_xact_lock` по паре (колонка, дорожка);
   страховка — частичный UNIQUE `(column_id, lane_id, position) WHERE archived_at IS NULL`. Изменения
   колонок и дорожек блокируют строку доски, досок — строку пространства.
5. **Фронтенд** ключей не вычисляет: при перетаскивании он оптимистично переставляет карточку в кеше
   (TanStack Query), отправляет соседей и после ответа перечитывает доску. При ошибке — откат, сообщение
   и перезапрос.
6. **Колонки и дорожки переставляются через меню** («Левее/Правее», «Выше/Ниже»), а не перетаскиванием:
   на сетке с подколонками это надёжнее, доступно с клавиатуры и проще тестировать. Карточки —
   перетаскиванием (dnd-kit, также с клавиатуры: пробел — взять/положить, стрелки — двигать).

## Последствия

- Ключи растут при многократных вставках в одно и то же место (тест: 500 вставок подряд — ключ короче
  120 символов; колонка `varchar(255)`). При необходимости ключи одной ячейки можно переписать заново
  одной транзакцией — это не меняет историю (`card_transitions` позиции не хранит).
- Порядок в ответах API — по `position`; клиент сохраняет порядок массива.
