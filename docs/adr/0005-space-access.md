# ADR-0005. Модель доступа к пространствам

- **Статус:** принят
- **Дата:** 2026-10-12

## Контекст

Главное требование этапа 1: **каждый видит ровно то, к чему ему дали доступ**. Иерархия:
Пространство → Доски → Колонки × Дорожки → Карточки. Отдельной сущности «команда/отдел» нет —
пространство и есть команда. Ролей на уровне доски нет. Нужно, чтобы:

- сотрудник вне пространства не мог узнать даже о его существовании;
- системный администратор (роль `admin` из этапа 0) управлял пространствами, но **не** получал
  автоматически доступ к их содержимому;
- проверка была централизованной, без ручных `if` в контроллерах.

## Решение

### Данные

- `spaces`: `id` ULID, `name`, `key` (2–10 заглавных латинских букв, unique, CHECK в БД; не меняется после
  создания — входит в номера карточек и ссылки), `description`, `last_card_number` (счётчик номеров
  карточек, этап 1b), `archived_at`.
- `space_members`: `space_id`, `user_id` (unique пара), `role` — `admin | editor | commenter` (CHECK в БД).

| Роль | Может |
|---|---|
| `admin` | всё в пространстве: доски, колонки, дорожки, участники и их роли |
| `editor` | создавать, редактировать и перемещать карточки |
| `commenter` | только чтение (комментарии — этап 2) |

### Проверка доступа — только стандартные механизмы Laravel

1. **Policies** (`SpacePolicy`, в 1b — `BoardPolicy`, `ColumnPolicy`, `LanePolicy`, `CardPolicy`) используют общий
   трейт `App\Policies\Concerns\ChecksSpaceRole`:
   - не участник → `Response::denyAsNotFound()` → **404**;
   - участник без нужной роли → deny → **403**;
   - архивное пространство → участникам только чтение (изменения — 403 с понятным текстом).
2. **Авторизация в Form Request до валидации:** `authorize()` возвращает `Gate::inspect(...)` (объект `Response`),
   поэтому чужак получает 404 раньше, чем 422 с подробностями о полях.
3. **Списки — через scope и роли одним запросом:** сайдбар берёт пространства по `space_members` текущего
   пользователя. Ссылки на объекты в теле запроса (column_id, lane_id и т. п., этап 1b) валидируются
   `Rule::exists` с ограничением «тот же объект-родитель» → чужой id даёт 422 без раскрытия данных.
4. **Роль кешируется на экземпляре модели** (`Space::roleOf()`), а не в синглтоне: каждый HTTP-запрос получает
   свежие модели, кеш не «протекает» между запросами (в том числе в тестах, где контейнер общий).
5. **Единый ответ 404.** По умолчанию Laravel пишет в 404 разный текст: «No query results for model
   [App\Models\Space] DEV» для несуществующего и «Not Found» для запрета политики — по тексту можно было бы
   отличить чужое пространство от несуществующего. Обработчик в `bootstrap/app.php` отдаёт любой 404 в `/api`
   одинаково: `{"message": "Не найдено."}`. Тест сравнивает ответы побайтно.

### Системный администратор

- Создаёт и архивирует/восстанавливает пространства, назначает роли (себе или другому) из админки
  (`/api/v1/admin/spaces/...`). Видит только метаданные: название, ключ, администраторов, число участников.
- Не видит досок и карточек, пока не назначит себе роль. Назначение пишется в журнал
  (`space.member_added` / `space.member_role_changed` с `via: admin_panel`).
- При создании пространства указываются его администраторы (по умолчанию — сам системный администратор);
  каждое назначение — отдельное событие `space.member_added` с `via: space_created`.

### Инварианты (в Actions, ошибка 422)

- **В пространстве всегда есть администратор.** Смена роли или исключение последнего администратора
  запрещены. Деактивированный администратор управлять не может и потому не считается.
  Изменения состава участников сериализуются блокировкой строки пространства (`FOR UPDATE`), подсчёт —
  отдельным запросом (PostgreSQL не позволяет `FOR UPDATE` с агрегатами).
- Деактивированного пользователя нельзя добавить; уже добавленный остаётся в списке (ради истории)
  с бейджем «Деактивирован». Войти он не может (middleware `active`, ADR-0002).
- Исключение из пространства удаляет строку `space_members` (это доступ, а не пользователь). Факт и
  прежняя роль — в журнале событий.

### Архив

Архив = скрыто из навигации + только чтение. Архивное пространство не показывается в сайдбаре, но участники
открывают его по прямой ссылке (с плашкой «В архиве»). Восстановить может системный администратор.

### Справочник сотрудников

`GET /api/v1/users/directory` — для выбора участников. Доступен системному администратору и администраторам
пространств; деактивированные не выдаются.

## Последствия

- **Матрица доступа** (`tests/Feature/Access/AccessMatrixTest.php`): каждый маршрут содержимого пространства
  проверяется для не участника (404), системного администратора без роли (404), commenter (403 на изменения),
  editor (403 на структуру и участников). Отдельный тест сверяет список с зарегистрированными маршрутами —
  новый эндпоинт без записи в матрице роняет CI.
- Права в ответах API (`permissions.manage`, `permissions.edit_cards`) — подсказка для интерфейса
  (скрыть кнопки). Реальную проверку всегда делает сервер.
- Если понадобятся роли на уровне доски или группы пользователей — расширяется трейт `ChecksSpaceRole`
  и политики; контроллеры не меняются.

## Изменения

**2026-10-14, этап 3 (группы пользователей, ADR-0012).** Доступ даёт не только личное участие, но и группы.
Роль больше не читается одной строкой `space_members`: `Space::membershipOf()` и `Space::rolesOf()` заменены на
`Space::accessOf()` / `Space::accessesOf()` — итоговые права по всем источникам из `SpaceAccessResolver`;
`roleOf()` остался и возвращает самую сильную роль (для показа). Трейт `ChecksSpaceRole` разрешает действие,
если его целиком разрешает хотя бы один источник. Инвариант «в пространстве есть администратор» уточнён:
хотя бы один **личный** не деактивированный администратор; администраторы через группы — дополнительные.
Деактивация пользователя инвариант не проверяет (решение PM), но предупреждает о последствиях.

**2026-10-15, подэтап 3c (роль «Владелец», ADR-0017).** Системный администратор — роль `admin` или `owner`
(`User::isAdmin()` верна для обеих); у Владельца все права системного администратора плюс исключительные (назначение
администраторов, передача владения). Принцип этого ADR не меняется: Владелец, как и администратор, содержимое
пространства без роли в нём не видит (404, `AccessMatrixTest`).

**2026-10-23, «Права 2.0», П2a (ADR-0024).** Роли — не зашитые проверки, а наборы прав каталога
(`App\Enums\Permission`): «Администратор», «Редактор», «Комментатор» и их варианты «— только свои карточки» —
стандартные роли (`roles`, `role_permissions`). Участие хранится выдачей `access_grants` (пользователь или группа ×
узел пространства в `nav_nodes` × роль), таблицы `space_members` и `space_groups` перенесены и удалены. Политики
(`ChecksSpaceRole`) проверяют права каталога: `space.update`, `space.manage_access`, `board.create/update/delete`,
`card.create/update/move/invite/comment` — вместо «admin» и «editor и выше». API пространств прежний: роль
`admin | editor | commenter` + `own_cards_only` сервер переводит в стандартную роль (`StandardRole::fromLegacy`).
Архив, удаление и перемещение пространства и корзина по-прежнему у системного администратора — правами роли они
станут в П2d. 404 / 403 — как раньше.

**2026-10-23, «Права 2.0», П2b-1 (компании, ADR-0024).** Системного администратора нет: `users.role` — `owner | member`,
администратор компании — `company_members.is_admin`. Принцип не меняется: ни Владелец, ни администратор компании без
выдачи содержимое пространства не видят (404, `AccessMatrixTest`); участник и администратор другой компании — тоже 404.
Архив, восстановление, удаление пространства и назначение роли из админки проверяют права компании («структура»,
«доступ»), удаление карточки в корзину — право компании «корзина» и любую роль в пространстве; правами роли
«Администратор» они станут в П2d.
