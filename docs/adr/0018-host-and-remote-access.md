# ADR-0018. Хост стенда и удалённый доступ: Mac mini, launchd, Tailscale, бэкапы с копией в облако

> Номера PR в этом документе — старого репозитория (архив: selen-archive — приватный `luvu1uvu/selen-archive`, ADR-0022).

- **Статус:** принят; копия бэкапов вне Mac mini отключена до пилота (см. «Изменения»)
- **Дата:** 2026-10-16
- **Карточки:** LATER-59 (Mac mini как хост), LATER-20 (внешняя копия бэкапов)

## Контекст

Стенд PM (ADR-0014) жил на MacBook, бэкапы — вручную, раз в день, на том же диске. PM переносит всё на рабочий
Mac mini: код, Docker, dev, стенд, сессии Claude Code. MacBook дома — только окно: браузер и Remote Control.
Значит, Mac mini должен сам подниматься после перезагрузки, стенд — открываться с MacBook, но не из интернета,
а бэкапы — делаться без участия человека и храниться не только на Mac mini. Сбой бэкапа не должен быть тихим.

## Решение

### Хост

- Mac mini не засыпает и включается после пропадания питания (`pmset`: `sleep 0`, `autorestart 1`). FileVault
  включён: до входа PM диск зашифрован, поэтому всё запускается **после входа в систему**, агентами пользователя
  (`~/Library/LaunchAgents`), не системными демонами от root.
- Каталоги — `~/dev/selen` (основная копия), `~/dev/selen-pm` (стенд, git worktree), `~/dev/selen-pm-backups`.
  Не `~/Documents`: macOS (TCC) не пускает агентов launchd в «Документы», «Рабочий стол» и «Загрузки» —
  проверено пробным заданием. Эти каталоги ни с какими облаками не синхронизируются; единственная копия вне
  Mac mini — зашифрованная restic (ниже).
- Автозапуск: Colima — агент Homebrew (`brew services start colima`); контейнеры стенда поднимает Docker
  (`restart: unless-stopped`; остановленный `make pm-down` стенд остаётся остановленным); бэкапы и Remote Control —
  агенты `local.selen.backup` и `local.selen.remote-control` (`make host-install`, `scripts/host.sh`).
  Своего агента для стенда нет: политика перезапуска Docker уже делает то же самое.
- PATH агентов — Homebrew впереди системного (`/usr/bin/git` зависает на запросе к Связке ключей).
  Логи — `~/Library/Logs/Selen` (`backup.log`, `remote-control.log`; больше 5 МБ — в `.1`). Состояние —
  `make host-status`.

### Remote Control

- Сервер `claude remote-control --spawn worktree` в основной копии: каждая новая сессия — свой git worktree,
  сессии не мешают друг другу. Префикс имён новых сессий — «Selen · Mac mini».
- Под launchd сервер работает без терминала (проверено). Нужно один раз запустить его в Терминале и подтвердить
  доверие к папке и сам режим Remote Control; без терминала он спросить не может и завершается.
- Без терминала сервер раз в секунду перерисовывает статус — около 40 МБ лога в сутки. Обёртка
  `scripts/remote-control.sh` убирает управляющие последовательности и пишет строку, только если её не было
  последние 10 минут: события и ошибки — сразу, неизменный статус — раз в 10 минут. `host-install` копирует обёртку
  в `~/.local/share/selen`, поэтому агент не зависит от ветки, открытой в основной копии.
- `KeepAlive`: launchd перезапускает сервер через минуту после выхода (например, после ~10 минут без сети).
- Переписка Remote Control хранится на серверах Anthropic — пароли и ключи не выводятся в чат и в логи.

### Доступ к стенду с MacBook

- Tailscale (личный tailnet PM) и `tailscale serve`: `https://<имя Mac mini>.<tailnet>.ts.net` → `127.0.0.1:8081`,
  сертификат Let's Encrypt выпускает Tailscale. Адрес доступен только устройствам tailnet. **Funnel (доступ из
  интернета) запрещён** — `make host-status` выводит «ВНИМАНИЕ», если он включён. Порты стенда по-прежнему только
  на `127.0.0.1`.
- `.env` стенда: `APP_URL` и `FRONTEND_URL` — адрес Tailscale (ссылки в письмах открываются с обеих машин),
  `SANCTUM_STATEFUL_DOMAINS` — оба адреса, `SESSION_SECURE_COOKIE=null` (флаг Secure — по протоколу запроса:
  Tailscale передаёт `X-Forwarded-Proto: https`, приложение уже доверяет прокси), `SESSION_DOMAIN=null` (у каждого
  адреса свои cookie). Код приложения не менялся.
- **Все порты Docker — только на `127.0.0.1`**, и dev и E2E тоже (`docker-compose.yml`, `docker-compose.e2e.yml`).
  До этого dev слушал все интерфейсы: на Mac mini он был открыт в офисную сеть и в tailnet, а у dev-базы пароль
  суперпользователя по умолчанию — через него можно выполнять команды в контейнере, а из виртуальной машины Colima
  доступны порты хоста на 127.0.0.1 (Mailpit стенда со ссылками сброса пароля). Найдено ревью. `host-status` и
  ежечасное задание предупреждают о любом проброшенном Colima порте не на 127.0.0.1. Firewall macOS включает PM
  (вторая линия: проброс портов Colima делает системный `ssh`, его firewall по умолчанию пропускает).
- Dev через Tailscale не публикуется: понадобились бы правки Vite (`allowedHosts`, HMR) и `.env` dev — отдельная
  задача, если понадобится.

### Бэкапы стенда

- Каждый час (агент, в :07) — `scripts/backup.sh`: дамп базы и инкрементальный снапшот вложений
  (`rsync --link-dest`, ADR-0010). Уровни: `hourly/` — каждый бэкап, хранится 48 часов (`BACKUP_KEEP_HOURLY`, по
  возрасту); `daily/` — первый бэкап суток, 30 штук; `weekly/` — первый бэкап недели, 12 штук. Копии на уровнях —
  жёсткие ссылки, место не занимают. Без `BACKUP_KEEP_HOURLY` (dev, будущий сервер с cron) — как раньше: каждый
  бэкап ежедневный; еженедельный теперь — первый бэкап недели, а не воскресный.
- Блокировка каталога бэкапов: бэкап по расписанию, `make pm-backup`/`pm-update` и копия в облако не идут
  одновременно. Брошенная блокировка (процесс завершился — сверяется PID и время его старта, или ей больше 3 часов)
  снимается сама; остатки оборванного бэкапа (`*.partial`) удаляются. Каталог — 700, дампы — 600; файлы снапшота сохраняют права вложений (nginx читает их после
  восстановления), их закрывает каталог.
- В отчёте каждого бэкапа — длительность и размер (дамп + новые файлы), его показывает `make host-status`.

### Копия вне Mac mini (LATER-20)

- **Сейчас отключена** (решение PM 2026-10-16, «Изменения»): `OFFSITE_ENABLED=false` в `~/.config/selen/offsite.env`,
  бэкапы стенда — только на Mac mini. Отключённая осознанно копия — не сбой: ни уведомлений, ни «ВНИМАНИЕ»,
  `make host-status` пишет «Копия вне Mac mini: отключена (решение PM, до пилота)», `make pm-restore-check` по
  умолчанию проверяет локальный бэкап. Без переменной (`offsite.env` прежних версий) копия считается включённой —
  ненастроенная даёт «ВНИМАНИЕ», как раньше. Ниже — как копия работает, когда включена; включение — runbook,
  раздел 13, «Копия вне Mac mini: как включить».
- restic → S3-совместимое хранилище в РФ (Yandex Object Storage или Selectel) после каждого бэкапа. Шифрует restic
  на Mac mini; хранилище видит только зашифрованные данные. Один снапшот restic — один бэкап (дамп и его снапшот
  файлов); одинаковые файлы restic хранит один раз. Хранение — как локально: ежечасные за 48 часов, по одному
  в сутки за 30 дней, по одному в неделю за 12 недель (`restic forget --keep-within-*`, группа — только тег: от имени
  машины не зависит). Освобождение места (`prune`) и проверка хранилища (`check`) — раз в сутки.
- Ключ хранилища умеет удалять (так работает `prune`). Чтобы ошибка или шифровальщик на Mac mini не стёрли и копии
  в облаке, у бакета включено версионирование с правилом «старые версии удалять через 30 дней» — удалённое этим
  ключом можно вернуть в течение месяца.
  Снапшот всего каталога бэкапов не выбран: в каждом лежали бы все локальные дампы, и при таком хранении в облаке
  копились бы тысячи сжатых дампов (сжатые дампы restic почти не дедуплицирует).
- Бакет и сервисный ключ только на этот бакет заводит PM; **ключи PM вписывает сам** — сессия называет только имена
  переменных. Файл — `~/.config/selen/offsite.env` (600; шаблон `.env.offsite.example`), **а не `.env` стенда, как
  предполагалось в плане** (отступление согласовано PM 2026-10-16): `.env` стенда целиком попадает в контейнеры приложения (`env_file` и монтирование), а ключ
  хранилища приложению не нужен — утечка через приложение не должна давать доступ к копиям. Пароль restic — файл
  `~/.config/selen/restic-password` (600), его создаёт `make host-install`; копию PM хранит в менеджере паролей:
  без неё копию не расшифровать.

### Без тихих сбоев

- Задание помнит число неудач подряд и время последней успешной копии в облаке. Бэкап или копия не удались два раза
  подряд или последней успешной копии больше 6 часов — системное уведомление macOS и строка «ВНИМАНИЕ» в
  `make host-status`. Если не работает сам агент, уведомить некому — `host-status` покажет «последний бэкап больше
  2 часов назад».
- Уведомление о сбое бэкапа в самом Selen — этап 4 (уведомления), `docs/backlog.md`.

### Проверка восстановления

`make pm-restore-check`: свежий бэкап с копией в облако — тем же заданием, что по расписанию, → последний снапшот
из облака (если копия отключена или не настроена — локальный бэкап; `FROM=local|offsite`) → отдельный временный compose-проект
`selen-restore-check` (только postgres, без портов, данные в анонимном томе) → `pg_restore` → сверка числа карточек
(вместе с корзиной), вложений и файлов вложений с живым стендом, у каждого вложения есть файл → временный проект
удаляется (и при ошибке). Живые контейнеры и тома стенда не затрагиваются.

### Смена секретов стенда

`.env` стенда лежал в iCloud Drive MacBook — секреты считаются раскрытыми. Сменены `APP_KEY`, пароли ролей
`selen_owner`, `selen_app`, суперпользователя базы и QA-бота (бэкап до и после). Зашифрованных полей и подписанных
ссылок в Selen нет, токены приглашений и сброса пароля хранятся хешем — от `APP_KEY` зависят только cookie: все
пользователи стенда вышли из системы и вошли заново прежними паролями.

## Последствия

- Mac mini — единственная машина стенда. **Пока копия вне Mac mini отключена, при потере Mac mini (диск, кража,
  пожар) данные стенда теряются** — PM принимает этот риск до пилота. Когда копия включена, стенд поднимается на
  другой машине из копии restic (runbook, раздел 13, «Восстановление из облака»).
- После перезагрузки ничего не стартует до входа PM (FileVault) — осознанно.
- Сессии Remote Control работают на Mac mini с правами учётной записи PM: **доступ к аккаунту claude.ai — это
  командная строка на Mac mini** (и чтение `.env` стенда, ключей облака). Аккаунт — с двухфакторной аутентификацией;
  при подозрении на утечку — `make host-uninstall AGENT=remote-control` и выход из аккаунта (`claude auth logout`).
- tailnet личный: доступ к стенду есть у устройств PM. Поделиться узлом Mac mini с кем-то — значит открыть ему стенд.
- Новые команды: `make host-install`, `host-status`, `host-uninstall`, `pm-restore-check`.
- Скрипты агентов — из рабочей копии стенда (код main), как `pm.sh`; обёртка Remote Control — копия.

## Изменения

### 2026-10-16, LATER-20: копия вне Mac mini отключена до пилота — решение PM

**Контекст.** После мёржа PR #23 бакет S3 для копии стенда PM не заводил и попробовал вместо него свой Яндекс Диск
через rclone (restic `rclone:`). Не подошло: REST API Диска отвечает rclone `410 Gone` (баг rclone #10067), а WebDAV
Диска на бесплатном тарифе — `402 Payment Required`. Кроме того, токен rclone даёт доступ ко всему Диску PM, а не
к одной папке (ключей на папку, как у бакета, у Диска нет). Remote PM удалил, доступы отозвал; поддержка rclone в код
не вошла.

**Решение.**
1. До пилота — только локальные ежечасные бэкапы на Mac mini (уровни, ротация и проверка восстановления — как выше).
2. Копия отключается осознанно — `OFFSITE_ENABLED=false` в `~/.config/selen/offsite.env` (так его создаёт
   `make host-install`), а не пустыми ключами: пустые ключи — «не настроена», это сбой с «ВНИМАНИЕ» и уведомлением,
   а отключённая — нет. Сбои самого бэкапа уведомляют, как раньше.
3. При подготовке пилота — Object Storage компании (S3): для сервера — `backup-offsite.sh` по cron (`docs/backlog.md`,
   «Эксплуатация»), для стенда — `OFFSITE_ENABLED=true` и ключи бакета (runbook, раздел 13, «Копия вне Mac mini: как
   включить»). Код копии и проверки из облака остаётся (на dev проверен с локальным хранилищем restic, с настоящим S3 —
   при включении).

**Последствие.** До пилота данные стенда живут только на Mac mini (выше, «Последствия»).

### 2026-10-20, LATER-69: очистка рабочих копий — только копии Remote Control, перепроверка после «y» — решение PM

**Контекст.** Точечный аудит 19.10 (`docs/security/audit-2026-10-19-host-worktrees.md`, S-1): `make
host-worktrees-clean` проверял копии только до вопроса, а после «y» снимал любую блокировку и удалял копию — даже если
за время вопроса в ней появились `.env` или живая блокировка. Кроме того, скрипт брал все копии в `.claude/worktrees`,
хотя справка обещала только Remote Control: копию простаивающей сессии приложения Claude, процесс которой завершился,
он счёл бы завершённой.

**Решение.**
1. Очистка трогает только копии сессий Remote Control: каталог `bridge-cse_<id>` прямо в `.claude/worktrees`
   (ветка — `worktree-bridge-cse_<id>`), блокировка, если есть, — в формате сервера «claude agent bridge-cse_<id>
   (pid N start <запуск>)» (сверен на живой копии). Остальные копии, в том числе сессий приложения Claude и
   `claude --worktree`, — в «Оставлены» с причиной «не Remote Control».
2. После «y» каждая копия проверяется заново прямо перед удалением. Блокировка снимается, только если копия по-прежнему
   проходит все проверки; изменились коммит, ветка или блокировка с момента вопроса — копия остаётся.
3. Защита файлов вне git не зависит от настроек git (`status.showUntrackedFiles` и других); любой сбой проверки —
   копия остаётся (сбой `lsof` или docker — ничего не удаляется). Удаляется только ветка самой сессии
   (`worktree-bridge-cse_<id>`).
4. Подтверждение — только с клавиатуры (`echo y | …` не удаляет). Это защита от случайного ввода из конвейера, а не
   граница для агента: терминал можно получить и программой. Границу для агентов задают права Claude Code.

**Последствие.** Копии сессий приложения Claude и `claude --worktree` удаляют их собственные инструменты (архивирование
сессии в приложении) или PM вручную. Изменится формат копий Remote Control — очистка перестанет их находить (все в
«Оставлены» с причиной «не Remote Control»), а не начнёт удалять лишнее.
