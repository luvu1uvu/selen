# ADR-0009. Описание и комментарии: документ Tiptap в JSON и проверка на сервере

- **Статус:** принят
- **Дата:** 2026-10-13

## Контекст

На этапе 2 описание карточки перестаёт быть простым текстом: заголовки, списки, задачи с галочками,
цитаты, код, ссылки, упоминания коллег и картинки. Комментарии — то же самое. Следом (этап 3) по
упоминаниям пойдут уведомления, а позже появится модуль документов с тем же редактором.

Варианты хранения: HTML, Markdown, JSON-документ редактора. HTML требует санитайзера на сервере и
`dangerouslySetInnerHTML` на клиенте — главный источник XSS. Markdown теряет упоминания и картинки-вложения
(нужны свои расширения синтаксиса) и плохо проверяется. JSON-документ Tiptap (ProseMirror) — дерево узлов
с атрибутами: его можно проверить по белому списку, а упоминание и картинка в нём — узлы с id.

## Решение

### Редактор и хранение

- Frontend — **Tiptap 3** (`@tiptap/react`, `@tiptap/starter-kit`, версии закреплены точно, 3.31.3).
- В БД — **JSONB как есть** (`cards.description`, `comments.body`). Существующие текстовые описания
  переведены миграцией в документ из абзацев. HTML нигде не хранится и не генерируется.
- Показ — тот же Tiptap в режиме «только чтение» с той же схемой (`RichTextView`): неизвестный узел
  просто не отрисуется, `dangerouslySetInnerHTML` нет.
- **Упоминание хранит только id пользователя** (`mention.attrs.id`, `label: null`): имя подставляется при показе
  из `names` ответа API (`MentionedUsers::names()` одним запросом). Переименовали сотрудника — упоминания
  показывают новое имя; ПДн в тексте документа нет.
- **Картинка хранит только id вложения** (`image.attrs.attachmentId`): адрес строит клиент
  (`/api/v1/attachments/{id}?inline=1`), доступ проверяется при каждом запросе файла (ADR-0010).

### Проверка на сервере

1. **Структура** — `App\Support\RichText\RichTextDocument` (не зависит от карточки): белый список узлов
   (`doc`, `paragraph`, `text`, `heading` 1–3, списки, `taskList`/`taskItem`, `blockquote`, `codeBlock`,
   `hardBreak`, `horizontalRule`, `mention`, `image`), меток текста (`bold`, `italic`, `strike`, `code`, `link`)
   и **каждого атрибута** с проверкой значения. Ссылки — только `http`, `https`, `mailto`.
   Лимиты: 200 000 байт, глубина 20, 5 000 узлов. **Ничего не вырезается молча**: что не по списку — 422,
   клиент обязан прислать допустимый документ (иначе пользователь не узнает, что часть текста пропала).
2. **Контекст** — правило `App\Rules\RichText` (Form Request):
   - упомянуть можно только активного пользователя, который **видит карточку** (`CardVisibility::canSee`,
     поправка PM A) — то же правило, что у подсказки `GET cards/{card}/mentionable`;
   - картинка — только активное вложение-изображение **этой** карточки;
   - упоминания и картинки, которые уже были в сохранённом документе, повторно не проверяются: правка текста
     не ломается оттого, что упомянутый потерял доступ или вложение удалили.
3. **Сырой JSON.** Глобальные middleware `TrimStrings` и `ConvertEmptyStringsToNull` обходят весь JSON
   запроса и портят текстовые узлы (пробел перед упоминанием исчезает, `" "` становится `null`). Поля-документы
   Form Request берёт из исходного тела запроса — трейт `App\Http\Requests\Concerns\KeepsRawRichText`.

### Упоминания

- Таблица `mentions (card_id, user_id, source_type card|comment, source_id)` — `App\Services\Cards\MentionSync`
  внутри той же транзакции: новые упоминания добавляются, исчезнувшие удаляются, оставшиеся не трогаются.
  На этапе 3 уведомление отправляется только по новой строке — правка текста не рассылает повторно.
- Удалённый комментарий: строка остаётся с пометкой «комментарий удалён», текст стирается (`body = null`),
  его упоминания удаляются (решение PM — меньше ПДн).

### Переиспользование (модуль документов)

- Frontend: `shared/components/rich-text/*` (`RichTextEditor`, `RichTextView`, `MentionList`, `extensions`)
  о карточке не знают — кого можно упомянуть (`loadMentionable`), как загрузить картинку (`onUpload`) и имена
  (`names`) передаёт вызывающий код. Карточка подключает их в `features/cards/components/RichText.tsx`.
- Backend: `RichTextDocument` и `MentionedUsers` — общие. **Привязано к карточке только правило
  `App\Rules\RichText`** (конструктор принимает `Card`; упоминания — через `CardVisibility`, картинки — из
  `attachments.card_id`). Для документов: выделить интерфейс контекста (`canMention(User)`,
  `ownsImages(ids)`), реализовать его для карточки и для документа и передавать в правило вместо `Card`.
  `MentionSync` расширяется новым `source_type`. Переделка небольшая, делаем вместе с модулем документов.

## Последствия

- Схема редактора на клиенте и белый список на сервере должны совпадать: новое расширение Tiptap = новая
  запись в `RichTextDocument` + тест. Иначе сервер ответит 422 на документ с ним.
- Полнотекстового поиска по описаниям пока нет; когда понадобится — отдельная колонка с текстом, извлечённым
  из документа (как во временной колонке миграции), и индекс.
- Подсказка @ берёт всех, у кого есть доступ к пространству (лично и через группы, `SpaceAccessResolver::usersWithAccess`,
  этап 3), и оставляет тех, кто видит карточку.
