# ADR-0010. Файлы вложений: хранение, отдача, бэкап

- **Статус:** принят
- **Дата:** 2026-10-13

## Контекст

К карточке прикладывают файлы: скриншоты, макеты, документы, короткие видео; картинки вставляются в описание
и комментарии (ADR-0009). Требования PM: до 100 МБ на файл, commenter тоже может прикладывать, видео
перематывается, доступ к файлу — ровно как к карточке (включая режим «только свои карточки», ADR-0008),
файлы входят в бэкап и проверяются при `make backup-verify`. Отдельного файлового сервера в компании нет;
S3-совместимое хранилище, возможно, появится позже.

## Решение

### Хранение

- Laravel-диск **`attachments`**: локальный каталог вне `public` (`storage/app/private/attachments`, в
  контейнере nginx — `/var/www/attachments`, только чтение). Переход на S3 — `ATTACHMENTS_DISK=s3` и `AWS_*`
  в `.env`, код не меняется.
- Путь файла — `{card_id}/{ulid}`. Исходное имя в путь не попадает (нет проблем с кодировками, `../` и
  совпадениями); оно хранится в `attachments.name` после очистки (`AttachmentFiles::sanitizeName`: без путей
  и управляющих символов, NFC, ≤ 255 байт с сохранением расширения).
- Тип — **по содержимому** (finfo), не по расширению и не по заголовку браузера. `kind`: `image` / `video` /
  `file` — только для типов из белого списка (PNG, JPEG, GIF, WebP, MP4, WebM, QuickTime), остальное — `file`.
- **Видео с Mac (этап 2c).** Запись экрана macOS сохраняется в `.mov` (`video/quicktime`) — основной сценарий
  скринкастов в компании, поэтому QuickTime в белом списке inline. Контейнер `.mov` браузеры часто открывают,
  но кодек может быть им незнаком (HEVC в Chrome на Windows и Linux). Тогда `<video>` сообщает об ошибке или
  загружает только звук (ширина кадра 0) — клиент в обоих случаях заменяет плеер сообщением «Браузер не может
  воспроизвести это видео» и кнопкой «Скачать». Перекодирование на сервере не делаем (нет ffmpeg, лишняя нагрузка) —
  если понадобится, это задача очереди после загрузки.
- **Права файлов.** Диск `attachments` создаёт файлы 0644 и каталоги 0755 (`visibility: public`): файлы по
  X-Accel-Redirect читает nginx под своим пользователем. Каталог вне webroot, снаружи файлы доступны только через
  приложение. Исправлено в начале 2c: на Linux с правами по умолчанию (0600) nginx не отдавал файлы, на macOS
  Docker это не проявлялось.
- Файл пишется до транзакции; если запись в БД не удалась — файл удаляется (`UploadAttachmentAction`).
- **Удаление мягкое** (`deleted_at`, `deleted_by`); удалить может автор вложения и editor/admin (решение PM).
  Сам файл стирает `model:prune` через 30 дней (`path = ''`, строка остаётся для журнала): до этого
  бэкап, снятый в момент удаления, согласован с базой. Миниатюры не генерируются (backlog).

### Лимит размера — 100 МБ, согласован в трёх местах

| Где | Значение |
|---|---|
| Валидация (`config/selen.php` → `attachments.max_kb`) | 102 400 КБ |
| PHP (`docker/php/php.ini`) | `upload_max_filesize = 100M`, `post_max_size = 101M` |
| nginx (отдельный location загрузки, раньше общего `/api`) | `client_max_body_size 101m`, таймаут 300 с |

Остальной API по-прежнему ограничен 20 МБ.

### Отдача

- Только через приложение: `GET /api/v1/attachments/{id}` → `AttachmentPolicy::view` (через карточку:
  чужая или невидимая — 404, удалённое вложение — 404).
- **Локальный диск:** Laravel отвечает пустым телом с `X-Accel-Redirect: /_protected/attachments/{path}`,
  файл отдаёт nginx из `internal`-location — с Range-запросами (перемотка видео), без PHP в потоке данных.
  Снаружи `/_protected/...` недоступен (404).
- **S3:** редирект на временную ссылку (5 минут) с заданными `Content-Type` и `Content-Disposition`.
- **Безопасность:** `?inline=1` показывает в браузере только типы из белого списка (картинки, видео, включая
  `.mov`); всё
  остальное, **включая SVG, HTML и XML**, — только скачиванием и как `application/octet-stream`. Всегда
  `X-Content-Type-Options: nosniff` и `Content-Security-Policy: default-src 'none'; sandbox` (в internal-location
  nginx они заданы ещё раз — заголовки ответа Laravel туда не доходят). Имя — в `Content-Disposition`
  с `filename*` (UTF-8) и ASCII-запасным `filename`.

### Бэкап

- `scripts/backup.sh`: сначала дамп базы, потом **снапшот каталога файлов** рядом с дампом
  (`selen_<дата>.dump` + `selen_<дата>.files/`). Снапшоты инкрементальные — `rsync --link-dest` к предыдущему:
  неизменённые файлы — жёсткие ссылки, место занимают только новые. Каждый снапшот выглядит как полная копия
  и удаляется вместе со своим дампом той же ротацией (7 дневных, 4 недельных). Порядок «база, потом файлы»
  безопасен: файл удалённого вложения живёт ещё 30 дней, поэтому всё, на что ссылается дамп, в снапшоте есть.
- `scripts/restore.sh` возвращает базу и затем каталог файлов из парного снапшота (`rsync --delete`).
  Бэкап без снапшота (до этапа 2) восстанавливает только базу.
- `scripts/backup-verify.sh`: до бэкапа — счётчики строк (в том числе `cards`, `comments`, `attachments`) и
  манифест файлов (sha256); удаляет базу **и файлы**, восстанавливает, сверяет счётчики и манифест
  и проверяет, что у каждой строки `attachments` (кроме стёртых по сроку) есть файл.
- При `ATTACHMENTS_DISK=s3` скрипты файлы пропускают — их резервирует хранилище (версионирование бакета).

### Расширение на другие сущности (модуль документов)

Сейчас вложение принадлежит карточке: `attachments.card_id` (внешний ключ), путь `{card_id}/...`, доступ —
через `CardPolicy`. **Полиморфную связь сразу не делали**: второй сущности пока нет, а внешний ключ
защищает целостность, которую `morphTo` не даёт. Когда появятся документы:

1. Новая миграция: `attachable_type` + `attachable_id` (заполнить из `card_id`), `card_id` сделать nullable
   или убрать. Пути файлов не меняются — ULID уникальны между таблицами, старые `{card_id}/...` остаются
   валидными.
2. `AttachmentPolicy` выбирает проверку по типу владельца (`allowCard` для карточки, политика документа
   для документа). Отдача (`AttachmentFiles`), лимиты, nginx, бэкап и `backup-verify` от владельца не зависят.
3. `UploadAttachmentAction` принимает владельца вместо `Card`; маршрут загрузки — свой у каждой сущности
   (и свой regex-location nginx с лимитом 100 МБ).
4. Картинки в документе проверяются контекстом правила `RichText` (ADR-0009).

## Последствия

- Любое изменение лимита — в трёх местах из таблицы выше, иначе пользователь получит 413 от nginx или
  PHP вместо понятного 422.
- В dev и E2E каталог вложений смонтирован в nginx; в production то же делает `prod.conf.example`
  (alias на каталог Laravel). Без этого файлы не скачиваются (404 от internal-location).
- `make fresh` очищает и каталог вложений вместе с базой.
- Антивирусной проверки нет: файлы показываются в браузере только из белого списка типов, остальные
  скачиваются. Если понадобится — проверка в очереди после загрузки, до неё файл недоступен.

## Изменения

### UI-1b, LATER-51 (2026-10-22): ссылка на файл, открытая напрямую — веб-маршрут `/files/{id}`

**Проблема.** Файл отдавал `GET /api/v1/attachments/{id}`. Sanctum поднимает сессию по cookie только у запросов SPA —
с Referer/Origin своего домена (`statefulApi()`). Ссылка из адресной строки, новой вкладки или мессенджера приходит без
них — ответ 401 JSON, хотя пользователь вошёл; ссылку на файл нельзя было отправить коллеге.

**Решение** (план и решения PM — `docs/stages/ui-1.md`, «План UI-1b»):
- **Веб-маршрут `GET /files/{attachment}`** (`routes/web.php`, `FileController`): web-сессия — та же cookie, что у SPA
  (`auth` guard `web`), `active`, лимит `files` (600 в минуту на пользователя: картинки окна карточки грузятся по нему
  же). Без `tab-user`: адрес открывает браузер сам (`SessionUserMatchTest`). `/api/v1` не менялся — API, как и раньше,
  только для запросов SPA; CSRF не отключался (у GET его нет).
- **Права — при каждом открытии**, как у файла в приложении: `AttachmentPolicy::view` → `allowCard` → `CardVisibility`.
  Нет доступа, «только свои» и чужая карточка, карточка в корзине, вложение удалено, нет такого id — один ответ: браузер
  уходит на страницу Selen «Файл не найден или нет доступа» (`/file-not-found`, `config/selen.php → frontend_paths`)
  с «На главную», без имени файла и карточки (решение PM 22.10 вместо стандартной страницы 404 Laravel); запрос
  с `Accept: application/json` — 404 с тем же JSON «Не найдено», что у API.
  Публичных и вечных ссылок нет. Файл отдаётся с `Cache-Control: private, no-cache` (раньше `max-age=3600`, и у API тоже):
  браузер переспрашивает сервер при каждом открытии — из истории, после выхода, после потери доступа, — а неизменённый файл
  nginx отдаёт ответом 304 без повторной передачи (точечный аудит UI-1b, S-5).
- **Без входа** — 302 на `/login?next=/files/{id}` (`redirectGuestsTo`); деактивированный с уцелевшей сессией — так же
  (сессия завершается). Адрес возврата строится из маршрута (`FileController::loginUrl`), а не из запроса: лишние
  параметры ссылки (метки мессенджера) возврату не мешают. Страница входа принимает `next` только вида
  `/files/<id>[?download=1]` (`fileReturnPath`) — не открытый редирект. Переход к файлу — в одном месте (`RequireGuest`:
  и после входа, и уже вошедшему), заменой адреса (`location.replace`): «Назад» из файла не возвращает на вход. Документ
  браузер скачивает, оставаясь на странице, — она показывает «Открываем файл…» и «На главную», а не вечную загрузку.
- **Что открывается в браузере** (`AttachmentFiles::linkResponse`): картинки и видео из белого списка и **PDF — только
  определённый сервером по содержимому** (`finfo` при загрузке, `attachments.mime`), не по имени и не по расширению
  (решение PM 21.10, вариант А); остальное — скачиванием как `application/octet-stream`; `?download=1` — всегда скачать.
- **PDF и CSP.** Chrome не показывает PDF в документе с CSP `sandbox`. PDF в браузере отдаётся через отдельный
  internal-location nginx `/_protected/attachments-pdf/` (тот же каталог) с CSP без `sandbox`:
  `default-src 'none'; object-src 'self'; style-src 'unsafe-inline'; base-uri 'none'; form-action 'none';
  frame-ancestors 'none'` (`AttachmentFiles::PDF_CSP`), `nosniff` — как у остальных. Это ослабление защиты для одного
  типа файлов — его проверял точечный аудит безопасности подэтапа (критичного нет). Приложение (`/api/v1`) PDF
  по-прежнему не показывает.
- **Принятый риск — PDF с активным содержимым** (JavaScript, `/OpenAction`, `/Launch`, ссылки и автопереход наружу;
  аудит UI-1b, S-3). Такой PDF тоже открывается в браузере на адресе Selen. Не ограничиваем (решение PM 22.10):
  загружают только вошедшие сотрудники; JavaScript из PDF выполняет встроенный просмотрщик браузера изолированно от
  страницы Selen (документ нашего домена — с `default-src 'none'`); поиск «опасных» слов в байтах PDF ненадёжен
  (обходится кодированием имён и сжатыми потоками), а разбор PDF библиотекой — лишняя сложность. **Пересмотреть в
  «Правах 2.0»**, когда в Selen появятся гости других компаний: тогда загружать сможет не только сотрудник.
- **Интерфейс:** `AttachmentResource.url` и картинки в тексте — `/files/{id}`; у файла в «Файлах» — «Скопировать ссылку
  на …» (браузер не дал буфер обмена — сообщение об ошибке, а не «скопирована»; так же у ссылки на карточку);
  «Скачать» — `?download=1`. Имя файла, который открывается в браузере (`AttachmentResource.opens_in_browser`:
  картинки, видео, PDF по содержимому), открывает его в новой вкладке, имя остальных — скачивает (решение PM 22.10).
- **Имя файла в адресе не показываем** (решение PM 22.10): адрес — `/files/{id}`, имя — в `Content-Disposition`
  (`filename*` в UTF-8 и ASCII-запасной `filename`) и у «открыть в браузере», и у «скачать» (проверяют `FileLinkTest`
  и E2E). Имя берёт сохранение файла. Название вкладки браузер выбирает сам: картинку Chrome называет по адресу
  («<id> (1×1)» — видно в UX-ревью UI-1b), PDF — по заголовку документа или имени файла, в зависимости от браузера;
  заголовком ответа это не меняется. Старые ссылки `/api/v1/attachments/{id}`, уже скопированные пользователями, так и
  отвечают 401 — интерфейс их больше не выдаёт.
- **nginx:** `/files/` — в php-fpm (`default.conf`, `prod.conf.example`, `docker/e2e/nginx.conf`); стенд подхватывает
  конфигурацию при `make pm-update` (перезапуск).

**Тесты:** backend `Cards/FileLinkTest` (прямой переход без Referer/Origin — файл, API — 401; вход и возврат, адрес
возврата из маршрута; «не найдено» одного вида — страница Selen и JSON; имя в `Content-Disposition`; PDF по содержимому — и через загрузку, «.pdf» с HTML внутри;
деактивированный; веб-маршрут один и без `tab-user`), `Access/AccessMatrixTest` (`/files/{attachment}` — в матрице прав:
роли, группы, «только свои», системный администратор и Владелец без роли; веб-маршрут с объектом карточки вне матрицы
роняет тест), frontend `LoginPage.test` (один переход, «Открываем файл…») и `shared/lib/browser.test` (`next` — только
`/files/<id>`, копирование), E2E `file-link.spec.ts` (новая вкладка, вход и возврат; PDF через настоящий nginx — CSP без
`sandbox`, `nosniff`, 304 при повторном открытии; internal-location снаружи — 404).
