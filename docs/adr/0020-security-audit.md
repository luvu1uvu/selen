# ADR-0020. Аудит безопасности: агент-аудитор и проверки в CI

> Номера PR в этом документе — старого репозитория (архив: selen-archive — приватный `luvu1uvu/selen-archive`, ADR-0022).

- **Статус:** принят
- **Дата:** 2026-10-19
- **Карточки:** LATER-60

## Контекст

Безопасность Selen держится на нескольких инвариантах: единая точка прав (`SpaceAccessResolver`, `CardVisibility`,
ADR-0005, 0008, 0012), одинаковый 404 для чужого, append-only история под ролью приложения без прав (ADR-0016),
порты только на 127.0.0.1 и стенд только в tailnet (ADR-0018), ПДн не в журнале событий (ADR-0003). До сих пор их
проверял ревьюер подэтапа — каждый раз заново и по своему разумению. Пилот близко: нужна регулярная проверка по
постоянному чек-листу и автоматическая — зависимостей и секретов. Требования PM: аудитор ничего не меняет, находки —
карточками, и он не должен съедать лимиты сессий.

## Решение

### Агент `security-auditor`

- Описание — `.claude/agents/security-auditor.md`: чек-лист по нашей системе (права и обходы единой точки, IDOR,
  утечки названий, сессии, CSRF и `X-Selen-User`, вложения, инъекции, секреты, ПДн, зависимости, Docker и Tailscale,
  заголовки, лимиты попыток, права на бэкапы и `.env`), уровни «критично / важно / мелочь» и формат отчёта.
- **Только чтение.** Инструменты — Read, Grep, Glob, Bash. Hook PreToolUse в описании агента
  (`.claude/hooks/security-auditor-guard.sh`, нужны `jq` и `perl` — есть в macOS):
  - Bash — одна простая команда из белого списка (чтение git только внутри рабочей копии, `ls`/`stat`/`wc`,
    `make audit-deps`, `make host-status` — только на хосте стенда; `make test`/`make lint` — только из основной копии,
    потому что контейнеры dev смонтировали её). Символы — только `[A-Za-z0-9 ._/:@^~=,%+-]`: кавычки, скобки и шаблоны
    позволяли спрятать параметр от проверки. Опасные параметры git запрещены вместе с их сокращениями и склейками
    (`--output`, `--no-index`, `-O`, `--contents`, `blame -S`, `--ignore-revs-file`…), пути вне копии — тоже (git
    сравнил бы файлы на диске).
  - Read и Grep — только в копиях Selen, на стенде, в агентах launchd и логах Selen. Секреты (`.env`, `offsite.env`,
    пароль restic, бэкапы, кеш конфигурации Laravel, файлы вложений) не читаются; Grep со строками по каталогам, где они
    лежат, запрещён — только счётчик или список файлов. Пути приводятся к реальным (`..`, симлинки), регистр не
    учитывается (APFS).
  - Любой сбой hook — запрет. Тест — `scripts/test-auditor-hook.sh` (обходы, найденные ревью и первым аудитом), входит
    в `scripts/check-scripts.sh`: `make lint` и CI.
  - Hook защищает от **случайного** вывода секретов и случайных изменений (ошибка агента, инструкция из прочитанного
    текста), а не от злонамеренного агента: по счётчику Grep значение можно подобрать.
- Hook агента работает, только если Claude Code доверяет папке проекта. Поэтому агент запускается только из
  `~/dev/selen` или его рабочих копий (`.claude/worktrees/…`), а первой командой проверяет hook: hook всегда
  запрещает `echo security-auditor-hook-check`. Если команда выполнилась — hook не действует, и агент больше не
  выполняет команд Bash (решение PM 2026-10-19).
- Карточки находок «критично» и «важно» заводит основная сессия (`make pm-bug` с `"labels": ["безопасность"]`) по
  JSON из отчёта: агент на стенд не пишет. `pm-bug` только ставит существующие метки стенда — если метки нет,
  предупреждает; права бота не расширяются (ADR-0014).
- **Когда** — CLAUDE.md, «Аудит безопасности»: полный аудит в конце этапа и перед пилотом, точечный — в подэтапе,
  который затрагивает вход и сессии, права, файлы или инфраструктуру. Чаще — нет: аудит дорогой.

### Проверки в CI — workflow «Security»

На каждый push и PR и раз в неделю (понедельник, 07:00 МСК): новые уязвимости публикуются без наших коммитов.

| Проверка | Как | Падает |
|---|---|---|
| composer | `composer audit --locked` по `backend/composer.lock` | на high и critical (`--ignore-severity=low,medium`); уязвимость без указанной важности тоже роняет — осторожнее пропустить |
| npm | `npm audit --package-lock-only --audit-level=high` — `frontend` и `e2e` | на high и critical |
| секреты | gitleaks (официальный образ, версия зафиксирована) по **всей** истории git, `--redact` | на любой находке |

- Один скрипт для CI, `make audit-deps` и аудитора — `scripts/deps-audit.sh`. Low, medium и заброшенные пакеты
  печатаются, но проверку не роняют: заброшенный пакет — не уязвимость, а `composer audit` по умолчанию на нём падает
  (сейчас — `dragon-code/pretty-array`, `dragon-code/support` из laravel-lang).
- Локально composer и npm не установлены (всё в Docker): скрипт берёт образы dev (`selen-php:dev`, `node:24-alpine`) и
  монтирует файлы зависимостей только для чтения.
- gitleaks — CLI из образа, а не `gitleaks-action`: проще, без лицензии и без комментариев в PR; вся история
  сканируется за секунды. Версию образа Dependabot не обновляет — поднимать вручную.

### Dependabot (решение PM 2026-10-19)

- **Обновления безопасности — сразу**, отдельными PR. Их включают в настройках репозитория (Dependabot alerts и
  Dependabot security updates) — это делает владелец репозитория, файл их не включает.
- **Обычные обновления — только minor и patch, все экосистемы одним PR раз в неделю** (`multi-ecosystem-groups`:
  composer, npm `frontend` и `e2e`, GitHub Actions, Docker `docker/php`, docker-compose); `open-pull-requests-limit: 3`
  на группе (на обновления безопасности не действует: у них свой встроенный лимит GitHub — 10 открытых PR).
  Расписание, лимит и префикс коммитов `chore(deps)` — только на группе `weekly` (LATER-62, «Изменения»).
- **Major не предлагаются** (`ignore` с `update-types: semver-major` — действует только на обычные обновления).
  Также не предлагаются minor-версии PHP (8.4 → 8.5 — решение стека, вместе с CI и CLAUDE.md) и nginx (нечётные
  minor — ветка mainline).
- PR Dependabot мёржатся как любые: зелёный CI и «принято» PM.

## Последствия

- PR из-за новой уязвимости может покраснеть не по своей вине: это сигнал завести карточку или хотфикс обновления
  зависимости, а не чинить в чужом PR.
- `@playwright/test` (npm `e2e`) и образ `mcr.microsoft.com/playwright` (`docker-compose.e2e.yml`) должны совпадать
  по версии. Если в недельном PR обновился только один — E2E упадёт; версию второго поднять в том же PR.
- Агент из нового или изменённого описания доступен со следующей сессии Claude Code. Первый прогон (2026-10-19) шёл
  общим субагентом с тем же текстом инструкции: hook там не действует, поэтому аудитор только читал файлы (Read), а
  команды выполнила основная сессия; отчёт и что осталось непроверенным — `docs/security/audit-2026-10.md`.
- Отчёты полных аудитов — `docs/security/audit-ГГГГ-ММ.md`; точечные — строкой в отчёте подэтапа.

## Изменения

### 2026-10-19, LATER-62: лимит и префикс коммитов Dependabot — на группе

**Контекст.** После мёржа PR #25 GitHub не принял `.github/dependabot.yml` (Insights → Dependency graph →
Dependabot: «Your .github/dependabot.yml contained invalid details»): `commit-message` и `open-pull-requests-limit`
стояли у каждой из 6 экосистем, а у экосистем, входящих в multi-ecosystem группу, GitHub их не допускает. Обычные
обновления из-за этого не работали; обновления безопасности включены в настройках репозитория и от файла не зависят.

**Решение (PM).** `commit-message` (`prefix: chore(deps)`) и `open-pull-requests-limit: 3` — на группе
`multi-ecosystem-groups.weekly`, рядом с расписанием. У экосистем — только `package-ecosystem`, `directory`,
`multi-ecosystem-group`, `patterns`, `ignore`. Остальные решения раздела «Dependabot» не меняются. По документации
GitHub (Configuring multi-ecosystem updates, Multi-ecosystem updates → Configuration merging behavior) только на
группе задаются также `milestone`, `target-branch` и `pull-request-branch-name`, а `labels` и `assignees`
складываются с уровня группы и экосистемы — понадобятся, ставить по этим правилам.

**Последствие.** Локально конфиг не проверить: схема SchemaStore эти ключи у экосистемы не запрещает, GitHub
разбирает файл только в основной ветке. Проверка — после мёржа, в Insights → Dependency graph → Dependabot.
