# ADR-0012. Группы пользователей и итоговые права по источникам доступа

- **Статус:** принят
- **Дата:** 2026-10-14

## Контекст

До этапа 3 доступ к пространству давало только личное участие (`space_members`, ADR-0005) с ролью и режимом
«только свои карточки» (ADR-0008). Компании нужно выдавать доступ отделам и подрядчикам целиком: «Аналитики» —
читатели во всех продуктовых пространствах, «Подрядчики» — редакторы своих карточек во Frontend. У человека
появляется **несколько источников доступа**: личное участие и любое число групп.

Главный риск — правило сочетания источников. Если «максимальная роль» складывается с «каким-нибудь» ограничением,
получаются права, которых никто не выдавал: личный commenter без ограничения + группа editor «только свои» дали бы
editor на все карточки. Требование PM: **действие разрешено, если его ЦЕЛИКОМ разрешает хотя бы один источник**;
роль и ограничение одного источника не смешиваются с другим. И правило должно жить в одном месте.

## Решение

### Данные

| Таблица | Поля |
|---|---|
| `groups` | `id` ULID, `name` (unique по `lower(name)`, включая архивные), `description`, `archived_at` |
| `group_members` | `group_id`, `user_id` (PK пара), `added_by`, `created_at` |
| `space_groups` | `space_id`, `group_id` (unique пара), `role` admin/editor/commenter, `own_cards_only`; CHECK `NOT (role = 'admin' AND own_cards_only)` |

- Группы ведёт только системный администратор (создание, название, описание, архив, состав). Доступ группы к
  пространству выдают, меняют и отзывают системный администратор (страница группы, `via: admin_panel`) и
  администратор пространства (вкладка «Группы») — как с людьми.
- Группы не удаляются — **архивируются**: архивная группа доступа не даёт, но её состав и доступы сохраняются,
  восстановление возвращает всё как было. Архивная группа — только для чтения (403 с текстом).
- **Деактивированный** остаётся в группах, но групповые источники ему не засчитываются (личное участие — как раньше:
  остаётся ради истории, войти он не может).

### Итоговые права — набор источников

`App\Services\Access\SpaceAccess` — действующие источники `AccessSource(role, ownCardsOnly, groupId|null)`:

| Вопрос | Правило |
|---|---|
| Есть ли доступ (`isMember`) | есть хоть один источник; иначе 404 |
| Видит ли все карточки (`canSeeAllCards`) | есть источник без ограничения; иначе видит только «свои» (ADR-0008) |
| Действие в пространстве без карточки (`allows`) | есть источник, чья роль его разрешает (структура, участники, создание карточки) |
| Действие с карточкой (`allowsOnCard`) | есть источник, чья роль разрешает **и** (нет ограничения **или** карточка «своя») |
| `my_role` в ответах (`highestRole`) | самая сильная роль — только для показа; права — по строкам выше |

Пример PM: Пётр — лично commenter без ограничения + группа «Contractors» editor «только свои» во Frontend →
видит все карточки (commenter-источник), редактирует и двигает только свои (editor-источник с ограничением).

### Единственная точка вычисления — `SpaceAccessResolver`

`App\Services\Access\SpaceAccessResolver` — **единственный класс, который читает `space_members`, `space_groups`
и `group_members` для прав**. Один SQL-запрос `UNION ALL`: личное участие + доступы неархивных групп активных
(не деактивированных) участников + доступы встроенной группы «Все сотрудники» (для любого активного пользователя,
см. ниже).

| Метод | Где используется |
|---|---|
| `forSpace(User, Space)` | `Space::accessOf()` — кеш на экземпляре пространства (как в ADR-0005: кеш не переживает HTTP-запрос и не протекает между запросами в тестах) |
| `forUser(User)` | `Space::accessesOf()` — сайдбар, список пространств, админка: одним запросом, затем `rememberAccess()` |
| `usersWithAccess(Space)` | вкладка «Люди», выбор людей в карточку, подсказка @ (одним запросом + `rememberAccess`) |
| `spaceIdsQuery(User)` | `Space::scopeVisibleTo()` |
| `administersAnySpace(User)` | справочник сотрудников и групп для администраторов пространств |
| `explain(User)` | админка → пользователь: все источники, включая недействующие, с причиной |
| `spacesOpenToEveryone()` | значок «доступно всем» в дереве навигации и «Структуре» (ADR-0013) |

Через `Space::accessOf()` права читают трейт политик `ChecksSpaceRole` (`allowMember`, `allowRole`, `allowCard` —
последний: сначала видимость, затем `allowsOnCard`), `CardVisibility` (`canSee`, `scope`, `isRestricted`, `present`),
ресурсы (`SpaceResource`, `CardResource.permissions`, фасад доски `cards[].can_edit`), правило `AssignableMember`.
Прямых запросов к `space_members`/группам для прав в обход нет. Actions личного участия и групп работают со своими
таблицами — это управление источником, а не вычисление прав.

### Встроенная группа «Все сотрудники»

`groups.system_key = 'everyone'` (CHECK: единственное допустимое значение, unique; системная группа не может быть
в архиве — CHECK), создаётся миграцией. **Состав не хранится, а вычисляется**: в группе каждый пользователь со
статусом active — третья ветка `UNION ALL` в резолвере. Новый сотрудник, принявший приглашение, со следующего
запроса видит всё, что открыто группе; деактивированный — теряет.

Ограничения (422 в Actions): группу нельзя переименовать, архивировать, менять её состав (добавить или исключить
человека) и выдать ей роль admin (ни при выдаче доступа, ни при смене роли). «Только свои карточки» — можно.
В интерфейсе: у группы бейдж «Встроенная» и пояснение вместо редактора состава; роль admin в списке ролей для
неё недоступна.

### Инвариант «в пространстве есть администратор»

Хотя бы один **личный** (не через группу) не деактивированный admin. Администраторы через группы —
дополнительные. `SpaceAdminGuard` считает только `space_members` и действует на операции с участниками
(смена роли, исключение — 422). Операции с группами инвариант не затрагивают.

**Деактивация не блокируется** (решение PM): отключить доступ уволенного важнее. Диалог деактивации заранее
показывает пространства, где человек — последний личный администратор (`GET admin/users/{user}/deactivation-impact`),
и даёт назначить замену. Такие пространства в админке «Пространства» — с бейджем «Нет администратора» и первыми.

### Источники доступа видны не всем

Вкладка «Люди» показывает всех с доступом и откуда он (лично, через какие группы), вкладка «Группы» — группы
пространства. Пользователю, у которого **все** источники с «только своими карточками» (типичный подрядчик),
источники не показываются (поправка PM): `GET spaces/{KEY}/groups` — 403, в `GET spaces/{KEY}/members` только
`user`, `permissions.view_access_sources = false`. Названия групп не уходят ему ни в один ответ (тест).

### Журнал

`group.created`, `group.updated {fields}`, `group.archived`, `group.restored`, `group.member_added/removed {user_id}`;
`space.group_added {group_id, role, own_cards_only}`, `space.group_role_changed {group_id, from, to}`,
`space.group_restriction_changed {group_id, from, to}`, `space.group_removed {group_id, role}` (+ `via`). Названия и
описания групп — тексты, в журнал не пишутся.

## Последствия

- Новый источник доступа (например, роль на уровне папки или доски) добавляется в `SpaceAccessResolver` и
  `SpaceAccess`; политики, `CardVisibility` и контроллеры не меняются.
- Матрица доступа (`AccessMatrixTest`) прогоняет все маршруты пространств и карточек и через группу (каждая роль,
  «только свои»), для архивной группы и после исключения из группы, а маршруты карточки — для смешанных источников.
- Число запросов доски и списка пространств не зависит от числа групп и пространств (тест).
- Исключение из группы действует со следующего запроса: сессии не трогаются, права вычисляются заново на каждый запрос.

## Изменения

### Этап 3b (2026-10-14): встроенная группа «Все сотрудники» — решение PM

**Контекст.** Пространства вроде «Компания» или «Management» открываются всей компании. Обычная группа с
поимённым составом требует добавлять каждого нового сотрудника вручную — его легко забыть.

**Решение.** Раздел «Встроенная группа „Все сотрудники“» выше: состав вычисляется в `SpaceAccessResolver`
(все активные), а не хранится; правило сочетания источников не меняется — это ещё один групповой источник.
Запрет роли admin сохраняет смысл инварианта личного администратора: управлять пространством должен
конкретный человек. Значок «доступно всем» в дереве — по `spacesOpenToEveryone()` (ADR-0013).

**Последствия.** Матрица доступа прогоняет маршруты и через группу «Все сотрудники»; сквозной сценарий этапа 3
(критерий 9) — приглашённый сотрудник сразу видит открытое пространство, после деактивации — нет.

### «Права 2.0», П2a (2026-10-23, ADR-0024): выдачи и права каталога

Источник доступа — строка `access_grants` (пользователь или группа, в том числе «Все сотрудники», × узел
пространства в `nav_nodes` × роль); `space_members` и `space_groups` перенесены миграцией со сверкой и удалены.
`SpaceAccessResolver` переименован в `App\Services\Access\AccessResolver`: тем же одним запросом `UNION ALL` он
читает выдачи и права их ролей (`roles`, `role_permissions`); `role_permissions` больше никто не читает (arch-тест).
`AccessSource` — роль выдачи (набор прав + область карточек) и группа; `SpaceAccess::allows(Permission)` и
`allowsOnCard(Permission, …)` — по правам каталога, правило «целиком в одном источнике» не меняется. Инвариант
«есть администратор» считается в резолвере: личная выдача с правом `space.manage_access` не деактивированному
пользователю (в П2a — роль «Администратор»); `SpaceAdminGuard` спрашивает резолвер. Сводка «почему он видит» и вкладки
«Люди» / «Группы» показывают роль и «только свои» в прежнем виде API.
