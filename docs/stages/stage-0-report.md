## 2. Принятые решения и их причины

**Отклонения от промта (согласованы при утверждении плана):**

1. **Сессии в PostgreSQL, а не в Redis.** Только так можно надёжно найти и завершить сессии конкретного
   пользователя при деактивации. Redis — для кеша, очередей, rate limiting. (ADR-0002)
2. **Пользователь создаётся сразу при приглашении** (`status=invited`), иначе статус `invited` не имеет смысла. (ADR-0004)
3. **Отзыв приглашения → пользователь `deactivated`**, но в админке он помечен бейджем «Приглашение отозвано»,
   чтобы не смешиваться с отключёнными сотрудниками. Такого пользователя можно пригласить повторно.
4. **Append-only журнала ещё и на уровне БД** (триггер на UPDATE/DELETE/TRUNCATE), а не только в приложении.
5. **Страница «Журнал событий» в админке** (в ТЗ не было) — чтобы проверить критерий «события видны» без SQL.
6. **Без таблицы API-токенов Sanctum** — используются только cookie-сессии.
7. **Демо-пользователи** создаются `make fresh` только при `APP_ENV=local`.
8. **Смена и сброс пароля завершают остальные сессии** — стандартная практика безопасности.
9. **Приглашения не удаляются**, scheduler чистит только просроченные токены сброса пароля (поправка PM).

**Решения, принятые по ходу работы:**

10. **Версии:** Laravel 13, PHP 8.4 (а не 8.5 — шире совместимость), PostgreSQL 18, Redis 8, Node 24 LTS,
    React 19, Vite 8, React Router 8 (data mode), Pest 5, Vitest 5, ESLint 10. (ADR-0001)
11. **Один корневой `.env`** для docker compose и Laravel (в контейнер он монтируется как `backend/.env`).
12. **Повторная отправка приглашения** создаёт новое приглашение, старое помечается «заменено новым»
    (его ссылка отвечает «устарела, используйте последнее письмо»), а не «отозвано» — честная история.
13. **Проверка паролей по базам утечек отключена** — это обращение к внешнему сервису (противоречит цели проекта).
    Политика: не короче 10 символов.
14. **Middleware `guest` в API не используется** — ему некуда перенаправлять; повторный вход просто заменяет сессию.
15. **`pest --parallel` выключен** — в текущих версиях pest 5.3 и paratest несовместимы; тесты идут ~5 с в один поток.
16. **Docker на этом Mac — через Colima** (бесплатно для компаний), выбран вами при планировании.
17. **Файлы `AGENTS.md`/`CLAUDE.md` из скелета Laravel удалены** — в них были инструкции ставить PHP через
    `curl | bash` и Laravel Boost. Правила проекта — в корневом `CLAUDE.md`.
18. **Git:** в репозитории настроен локальный автор коммитов `luvu1uvu` (с переезда в публичный репозиторий — GitHub noreply-адрес, ADR-0022)
    (глобальной настройки git на машине не было). Репозиторий: приватный `github.com/luvu1uvu/selen` (теперь архив: selen-archive, ADR-0022).

**Найдено и исправлено при проверке:**
- В контейнере переменные `.env` попадают в `$_SERVER`, и `phpunit.xml` их не перекрывал — первый прогон
  теста ушёл в dev-базу и пересоздал её (только dev-данные). Исправлено: переменные заданы и как `<server>`,
  плюс тесты теперь **отказываются запускаться не на `selen_testing`**.
- nginx после пересоздания контейнера php отдавал 502 (кешировал IP) — добавлен DNS-резолвер Docker.
- Страница приглашения при ошибке сервера писала «ссылка недействительна» — теперь «не удалось загрузить» + «Повторить».
- Текст подтверждения деактивации указывал пол пользователя («его сессии») — заменён на нейтральный.

## 3. Схема БД

| Таблица | Ключевые поля | Примечания |
|---|---|---|
| `users` | `id` ULID · `name` · `email` unique (lower-case) · `password` null до принятия приглашения · `role` admin\|member · `status` invited\|active\|deactivated · `timezone` (Europe/Moscow) · `last_login_at` · `deactivated_at` · `remember_token` · `created_at`/`updated_at` | CHECK на role и status; записи не удаляются |
| `invitations` | `id` ULID · `user_id` → users · `email` · `token_hash` sha256 unique · `invited_by_id` → users · `expires_at` · `accepted_at` · `revoked_at` · `superseded_by_id` → invitations · timestamps | Состояние (pending/expired/accepted/revoked/superseded) вычисляется; записи не удаляются |
| `event_log` | `id` bigint identity · `occurred_at` timestamptz(6) · `event_type` · `actor_id` → users · `subject_type` · `subject_id` · `payload` jsonb · `meta` jsonb | Append-only (триггер); индексы по объекту, типу и актору |
| `sessions` | `id` · `user_id` ULID · `ip_address` · `user_agent` · `payload` · `last_activity` | Сессии в БД (ADR-0002) |
| `password_reset_tokens` | `email` · `token` (хеш) · `created_at` | Просроченные чистит scheduler каждые 15 мин |
| `cache`, `jobs`, `job_batches`, `failed_jobs` | стандартные таблицы Laravel | Кеш и очереди фактически в Redis |

Все даты — `timestamptz` в UTC.

**Типы событий:** `auth.login_succeeded`, `auth.login_failed`, `auth.logout`, `auth.password_changed`,
`auth.password_reset_requested`, `auth.password_reset_completed`, `user.created`, `user.invited`,
`user.profile_updated`, `user.role_changed`, `user.deactivated`, `user.reactivated`, `invitation.resent`,
`invitation.revoked`, `invitation.accepted`.

## 4. API

Все пути — с префиксом `/api/v1`, формат JSON. Плюс `GET /sanctum/csrf-cookie` (CSRF для SPA) и `GET /up` (health check).

| Метод | Путь | Назначение | Доступ |
|---|---|---|---|
| POST | `/auth/login` | Вход (email, пароль, «запомнить меня») | Все · 5/мин на email+IP |
| POST | `/auth/logout` | Выход | Вошедший |
| GET | `/auth/me` | Текущий пользователь | Вошедший |
| POST | `/auth/forgot-password` | Письмо со ссылкой сброса (ответ всегда одинаковый) | Все · 3/мин на email |
| POST | `/auth/reset-password` | Новый пароль по токену из письма | Все · 3/мин на email |
| GET | `/invitations/{token}` | Данные приглашения для страницы принятия | Все · 20/мин на IP |
| POST | `/invitations/{token}/accept` | Задать пароль, активировать, войти | Все · 20/мин на IP |
| PATCH | `/profile` | Имя и часовой пояс | Вошедший |
| PUT | `/profile/password` | Смена пароля (с текущим) | Вошедший · 6/мин |
| GET | `/admin/users` | Пользователи (фильтр по статусу, поиск, пагинация) | Администратор |
| PATCH | `/admin/users/{id}/role` | Смена роли | Администратор (не себе) |
| POST | `/admin/users/{id}/deactivate` | Деактивация + завершение сессий | Администратор (не себя) |
| POST | `/admin/users/{id}/reactivate` | Реактивация | Администратор |
| GET | `/admin/invitations` | Приглашения с состояниями | Администратор |
| POST | `/admin/invitations` | Пригласить (имя, email, роль) | Администратор |
| POST | `/admin/invitations/{id}/resend` | Отправить повторно (новая ссылка) | Администратор |
| POST | `/admin/invitations/{id}/revoke` | Отозвать | Администратор |
| GET | `/admin/events` | Журнал событий (фильтры: тип, актор, объект) | Администратор |

«Вошедший» — только активный пользователь: деактивированный получает 401 даже с уцелевшей сессией.
Нельзя оставить систему без активного администратора (422).

## 5. Как проверить руками

Понадобится Mac с установленным Docker (Colima уже установлен на этой машине) и терминал.

1. **Запуск.** В терминале, в папке проекта:
   ```bash
   colima start
   make up
   make fresh
   ```
   Дождитесь строки `Selen: http://localhost:8080`.
2. **Создайте администратора:** `make admin`. Ответьте на вопросы: имя, email (например, `anna@selen.test`), пароль (не короче 10 символов).
3. **Войдите:** откройте http://localhost:8080 и войдите как администратор. Слева должно быть меню с разделом «Администрирование».
4. **Пригласите сотрудника:** «Пользователи» → «Пригласить» → имя, email (`boris@selen.test`), роль «Участник» → «Отправить приглашение».
   В списке появится Борис со статусом «Приглашён».
5. **Найдите письмо:** откройте http://localhost:8025 — там письмо «Приглашение в Selen». Пароля в нём нет, только кнопка «Задать пароль».
6. **Примите приглашение «как Борис».** Чтобы не выходить из админки, откройте **другой браузер или окно инкогнито**
   и вставьте ссылку из письма. Придумайте пароль → «Сохранить пароль и войти». Откроется главная с надписью «Доски появятся на этапе 1».
7. **Смените пароль:** в окне Бориса нажмите на имя справа сверху → «Профиль» → «Смена пароля».
8. **Сбросьте пароль через почту:** выйдите (меню → «Выйти») → «Забыли пароль?» → email Бориса → в Mailpit
   письмо «Сброс пароля в Selen» → по ссылке задайте новый пароль → войдите с ним, отметив «Запомнить меня».
9. **Деактивируйте Бориса:** в окне администратора «Пользователи» → «⋯» у Бориса → «Деактивировать» → подтвердите.
10. **Проверьте, что Бориса «выкинуло»:** в окне Бориса обновите страницу — откроется страница входа. Попробуйте
    войти — появится «Учётная запись деактивирована. Обратитесь к администратору.»
11. **Журнал:** в окне администратора «Журнал событий» — все шаги сценария по порядку (вход, приглашение,
    принятие, смена и сброс пароля, деактивация, неудачная попытка входа).
12. **Бэкап:** `make backup-verify` — в конце должны быть две строки «УСПЕХ».
13. **Тесты и линтеры:** `make test` и `make lint` — без ошибок.

Демо-пользователи после `make fresh`: `admin@selen.test` и `member@selen.test`, пароль `password-123`.

## 7. Известные проблемы, техдолг, риски

**Риски**
- **Персональные данные в неизменяемом журнале** (email, IP) — противоречит праву на удаление ПДн по 152-ФЗ,
  если такие запросы будут. Нужно решение (вопрос 2).
- **Бэкапы лежат на том же диске**, что и база. От потери сервера не защищают — нужна внешняя копия (этап деплоя).
- **Prod-SMTP не проверялся** — нет сервера; конфигурация стандартная, проверим при деплое.
- **Молодые мажорные версии** (Vite 8, React Router 8, Vitest 5, ESLint 10, Pest 5): уже встретили
  несовместимость pest/paratest. Обновления — отдельными задачами.

**Техдолг**
- `pest --parallel` выключен до исправления совместимости pest 5.3 и paratest.
- Нет браузерных E2E-тестов (Playwright): сценарий покрыт API-тестом и проверен вручную. Предлагаю добавить на этапе 1 (вопрос 7).
- Покрытие frontend ~73 %: не покрыты мобильное меню, пагинация, часть веток ошибок.
- В dev очередь работает через `queue:listen` (перечитывает код); в prod нужен `queue:work` под supervisor — этап деплоя.
- Смена email пользователя администратором не реализована (не входила в scope).
- В журнале показывается сырой JSON payload — для этапа 0 достаточно, позже нужно человекочитаемое описание.
- Сессии в БД чистятся встроенной «лотереей» Laravel; при росте можно добавить плановую очистку.

**Особенности окружения**
- Colima монтирует в VM только домашний каталог: проект должен лежать внутри `~` (сейчас так и есть).
- `node_modules` ставятся в Linux-контейнере. Запуск `npm` прямо на Mac может конфликтовать с бинарниками —
  используйте `make` / `docker compose run --rm node npm ...`.

## 8. Вопросы и решения перед этапом 1

1. **Мёрж PR `stage-0` → `main`** — после вашей проверки отчёта.
2. **ПДн в журнале событий:** оставляем email/IP в журнале (проще расследования) или псевдонимизируем
   (в журнале только id, email — в `users`)? Нужна ли процедура удаления ПДн уволенных?
3. **Определения метрик:** какой набор категорий колонок (предлагаю: `backlog` / `queue` / `in_progress` / `review` / `done`)
   и где начинаются lead time и cycle time? От этого зависит схема `card_transitions` (ADR-0003).
4. **Модель доступа к доскам:** все видят все доски или доски командные/приватные? Нужны ли роли на уровне доски
   (владелец, участник, наблюдатель) помимо admin/member?
5. **Структура компании:** нужны ли команды/отделы (продакт, дизайн, разработка, QA, аналитика) как сущность — для фильтров и KPI?
6. **Жизненный цикл сотрудника:** достаточно ли деактивации при увольнении? Нужна ли смена email администратором?
7. **E2E-тесты в браузере (Playwright)** — добавить на этапе 1 вместе с досками?
8. **Параметры безопасности:** сессия 120 минут без активности, «запомнить меня» — 30 дней, пароль от 10 символов. Устраивает?
9. **Деплой (отдельный этап):** домен, SMTP-сервер компании, характеристики VPS, куда копировать бэкапы.
10. **Laravel Boost** (официальный MCP-сервер Laravel для AI-агентов) — подключить, чтобы Claude Code лучше
    понимал проект? Это dev-зависимость, на production не влияет.
