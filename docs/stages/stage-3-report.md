## 2. Принятые решения и их причины

| Решение | Почему |
|---|---|
| **Итоговые права — набор источников**: действие разрешено, если его целиком разрешает хотя бы один источник (ADR-0012) | «Максимальная роль + какое-нибудь ограничение» выдаёт права, которых никто не давал (личный commenter + группа editor «только свои» ≠ editor на всё). `my_role` в ответах — максимум, только для показа |
| **Одна точка вычисления — `SpaceAccessResolver`**, один запрос `UNION ALL` | Политики, `CardVisibility`, доска, подсказка @, дерево не расходятся; новый источник (папка, доска) добавляется в одном месте |
| Кеш прав — на экземпляре `Space`, не scoped-синглтон | Laravel не сбрасывает scoped-синглтон между HTTP-вызовами в тестах — кеш протекал бы между запросами |
| Архивная группа и деактивированный пользователь доступа через группы не дают; исключение из группы — со следующего запроса | Права вычисляются на каждый запрос, сессии трогать не нужно |
| **Деактивация не блокируется** (решение PM): предупреждение и замена прямо в диалоге, бейдж «Нет администратора» | Отключить уволенного важнее инварианта; инвариант строго — только на операции с участниками |
| Подрядчику (все источники «только свои») источники и названия групп не показываются (поправка PM) | Название группы — тоже информация; тест ищет его во всех доступных ответах |
| **«Все сотрудники» — состав вычисляется**, а не хранится; без роли admin, без архива и правки состава | Новый сотрудник не забыт; управлять пространством должен конкретный человек (смысл инварианта) |
| **Папки не дают доступа** (ADR-0013): папка видна, если внутри есть доступное пространство; имена прочих папок не уходят в ответы | Нет второго источника прав в обход резолвера; название папки не раскрывает лишнего |
| Пространство видно в дереве всегда, даже без досок (поправка PM) | Иначе администратор нового пространства не попадёт в него создать первую доску |
| Значок «доступно всем» у папки — только если открыты **все** её активные пространства по всему дереву | Значок не должен обещать больше, чем есть |
| Глубина папок ≤ 4 | Панель ~256 px, отступ 12 px; глубже — признак неудачной структуры для 100 человек |
| Архивировать — только папку без активного содержимого (решение PM); восстановление в архивную папку — в корень | Ничего не пропадает из дерева незаметно |
| «Структура» — меню («Переместить в…», «Выше/Ниже»), а не перетаскивание | Надёжно, доступно с клавиатуры, просто тестировать (как колонки, ADR-0007); DnD — в backlog |
| Поиск по дереву — на клиенте | Дерево пользователя уже загружено и содержит только доступное: мгновенно и без утечек |
| Иконка-эмодзи — в узле дерева (`nav_nodes.icon`), не в `spaces` | Это свойство отображения в дереве, одно поле для папок и пространств |
| Изменения дерева — под advisory-блокировкой | Проверки глубины и циклов не разъезжаются при одновременных перемещениях |
| Дерево — только доступное, для всех одинаково, без пометок (приёмка, решение PM) | Конфиденциальность: даже системный администратор не видит в дереве названий того, к чему у него нет доступа. Структуру целиком он ведёт в «Структуре» |
| Восстановление пространств вместе с папкой — только прямо в ней, по галочке | Из вложенной архивной папки восстановленное ушло бы в корень, а не на место |
| «+»/«⋯» в дереве — общий код с «Структурой» (`useStructureActions`) | Одни запросы, проверки и сообщения в двух местах интерфейса |
| Выбранный раздел полосы слева — в браузере по id пользователя | Как в Kaiten: выбор панели не зависит от открытой страницы |

## 3. Схема БД

Новые миграции этапа (смёрженные не редактировались):

| Таблица | Поля |
|---|---|
| `groups` | `id` ULID, `name` (unique без учёта регистра), `description`, `system_key` (3b: `everyone`, unique, CHECK; системная не в архиве — CHECK), `archived_at`, timestamps |
| `group_members` | `group_id`, `user_id` (PK пара), `added_by`, `created_at` |
| `space_groups` | `id`, `space_id`, `group_id` (unique пара), `role` admin/editor/commenter (CHECK), `own_cards_only` (CHECK: не у admin), timestamps |
| `nav_nodes` | `id` ULID, `parent_id` → `nav_nodes`, `type` folder/space (CHECK), `name` (у папки), `icon`, `space_id` (unique), `position` (COLLATE "C"), `archived_at` (у папки), timestamps; CHECK согласованности типа и полей; индекс `(parent_id, position)` |

Миграция `nav_nodes` создала узел каждому существующему пространству в корне; миграция `add_everyone_group` — группу
«Все сотрудники».

| GET | `/groups/directory` | системный админ и админы пространств |
| GET · POST · PATCH · DELETE | `/spaces/{KEY}/groups` · `/groups/{group}` | участник (GET, кроме «только своих») · админ пространства |
| GET | `/spaces/{KEY}/members` — все люди с доступом и источники | участник |
| GET | `/navigation` — дерево пользователя | все |
| GET | `/admin/navigation` — полное дерево с архивом | системный админ |
| POST | `/admin/folders` | системный админ |
| PATCH | `/admin/nav-nodes/{node}` (название папки, иконка) | системный админ |
| POST | `/admin/folders/{node}/archive` · `/restore` | системный админ |
| POST | `/admin/nav-nodes/{node}/move` | системный админ |

Изменено: `POST /admin/spaces` — необязательные `icon` и `parent_id` (папка); `POST /admin/folders/{node}/restore` —
необязательный `restore_spaces`; `GET /navigation` — у пространства `can_manage`; фасад доски — `cards[].can_edit`; `SpaceResource.permissions.view_access_sources`.

Журнал: `group.created/updated/archived/restored`, `group.member_added/removed`, `space.group_added/role_changed/
restriction_changed/removed`, `folder.created/renamed/archived/restored`, `nav_node.moved`, `nav_node.icon_changed` —
только id и перечисления.

## 5. Как проверить руками

Общие предусловия для всех тест-кейсов: выполнены `make up` и `make fresh` (**все данные dev-базы и файлы вложений
удаляются**), приложение — http://localhost:8080, пароль у всех демо-пользователей — `password-123`. В дереве
под раскрытой папкой — папки и пространства, под раскрытым пространством — его доски (у досок свой значок). Узкая полоса
слева — полоса разделов: значки «Дерево» и «Администрирование» (название — во всплывающей подсказке). Если
тест-кейс меняет данные, следующий лучше начинать с нового `make fresh`.

### ТК-3.1. Дерево у системного администратора — только доступное
Зачем: даже системный администратор не видит в дереве названий того, к чему у него нет доступа.
Предусловия: вход как admin@selen.test.
Шаги:
1. Посмотреть на панель «Дерево» слева.
2. Нажать на папку «Продуктовые команды», затем на стрелку у пространства «Разработка».
Ожидаемый результат:
- сверху вниз: «Компания» (🏢) со значком «доступно всем» (силуэты людей) и папка «Продуктовые команды» (💡);
- папки «Операции» нет (в ней «Эксплуатация» и «Маркетинг», где у админа нет роли), надписей «нет доступа» и «пустая» нет;
- после шага 2 видны пространство «Разработка» и под ним его доски «Продукт» и «Инфраструктура» (значок доски).
Если не так: скриншот панели «Дерево».

### ТК-3.2. Раскрытые папки запоминаются
Зачем: после обновления страницы дерево не сворачивается заново.
Предусловия: вход как admin@selen.test, в дереве раскрыты «Продуктовые команды» и «Разработка» (ТК-3.1).
Шаги:
1. Обновить страницу (F5).
Ожидаемый результат:
- «Продуктовые команды» и «Разработка» по-прежнему раскрыты, доски видны.
Если не так: скриншот дерева после обновления.

### ТК-3.3. Поиск по дереву
Зачем: найти доску по части названия, не раскрывая папки вручную.
Предусловия: вход как admin@selen.test, все папки свёрнуты.
Шаги:
1. В поле «Найти…» над деревом ввести «инфра».
2. Нажать крестик в поле поиска.
Ожидаемый результат:
- после шага 1 видны только папка «Продуктовые команды» (раскрыта), «Разработка» и доска «Инфраструктура»; «Компании» и «Операций» нет;
- при вводе «xyz» — надпись «Ничего не найдено»;
- после шага 2 дерево снова полное, папки свёрнуты, как были.
Если не так: скриншот дерева с введённым текстом.

### ТК-3.4. Папка без доступа не видна сотруднику
Зачем: сотрудник не узнаёт даже названия папок, где у него ничего нет.
Предусловия: вход как member@selen.test.
Шаги:
1. Посмотреть на панель «Дерево».
Ожидаемый результат:
- видны «Компания» и папка «Продуктовые команды» с «Разработкой»;
- папки «Операции» нет нигде на странице.
Если не так: скриншот страницы.

### ТК-3.5. Пустая папка видна только в «Структуре»
Зачем: полная структура со всеми названиями — только в админке; в дереве пустых папок нет ни у кого.
Предусловия: вход как admin@selen.test.
Шаги:
1. Полоса разделов → «Администрирование» → «Структура» → «Создать папку».
2. Название «Тест приёмки» → «Создать».
3. Полоса разделов → «Дерево» (страница «Структура» остаётся открытой).
4. Выйти (меню пользователя справа вверху → «Выйти»), войти как member@selen.test.
Ожидаемый результат:
- после шага 2 «Тест приёмки» — последней строкой в «Структуре», сообщение «Папка создана»;
- после шага 3 в дереве слева папки «Тест приёмки» нет;
- после шага 4 у member@selen.test папки «Тест приёмки» тоже нет.
Если не так: скриншоты «Структуры» и дерева.

### ТК-3.6. Перенос в «Структуре» сразу виден в дереве
Зачем: исправление по приёмке — после переноса дерево обновляется без перезагрузки.
Предусловия: вход как admin@selen.test; в полосе разделов выбрано «Дерево».
Шаги:
1. Открыть http://localhost:8080/admin/structure (дерево слева остаётся открытым).
2. У «Разработка» нажать «…» → «Переместить в…» → «Куда»: «Корень дерева» → «Переместить».
3. Не обновляя страницу, посмотреть на дерево слева.
4. Там же у «Разработка» нажать «…» → «Выше» три раза, после каждого нажатия смотреть на дерево.
Ожидаемый результат:
- после шага 3 пространство «Разработка» — в корне дерева после «Компании»; папки «Продуктовые команды» в дереве
  больше нет (в ней не осталось доступного), в «Структуре» она есть. Если «Разработка» раскрыта, под ней — её доски
  «Продукт» и «Инфраструктура» (значок доски), это не папки;
- на шаге 4 после первых двух нажатий в дереве ничего не меняется: «Разработка» поднимается мимо папок «Операции»
  и «Продуктовые команды», которых нет в вашем дереве (в «Структуре» видно, как она поднимается); после третьего
  нажатия «Разработка» в дереве встаёт выше «Компании».
Если не так: скриншот «Структуры» и дерева рядом.

## 7. Известные проблемы, техдолг, риски

- **Доски в дереве скрыты под свёрнутым пространством** (как в Kaiten): на один клик больше, чем в старом плоском
  сайдбаре. Переход по ссылке на пространство, доску или карточку раскрывает путь сам. Экран пространства со всеми
  досками — этап 7.
- **Поиск по дереву — на клиенте.** На сотнях узлов мгновенный; при тысячах — перенос на сервер (backlog, вместе
  с общим поиском этапа 6).
- **Перетаскивание в дереве и «Структуре»** — в backlog (сейчас меню).
- **Начало перетаскивания на ×4 — ~217 мс** (выше порога заметности 100 мс) — с этапа 2, dnd-kit перерисовывает все
  карточки. На обычной скорости — 33 мс. Если доски вырастут — виртуализация ячеек (backlog).
- **Значок «доступно всем» у папки** считается по всему дереву: пользователь может видеть в папке не все
  пространства, но значок верен для папки целиком — так задумано (ADR-0013).
- **Ручная проверка в браузере** — точечно (воспроизведение бага «Структуры», вид кнопок «+»/«⋯»); остальное —
  автотестами (frontend, E2E на production-сборке). Приёмку интерфейса по референсу Kaiten делает PM (раздел 5).
- **Перемещение относительно скрытых узлов** (папок и пространств, недоступных пользователю, в том числе
  системному администратору) в его дереве не заметно — только в «Структуре». Так задумано (ADR-0013, «Изменения»).
- **E2E близко к лимиту входов:** прогон делает ~17 входов при лимите 20 в минуту на IP. Перед новыми сценариями —
  повторное использование входа (`storageState`, backlog).
- **Риск:** любое новое место, где показывается список пространств или папок, должно брать данные из
  `NavigationTree`/`accessesOf`, иначе утечёт название скрытой папки. Правило — в CLAUDE.md (п. 11) и ADR-0013.

### 9.3. Решения

| Решение | Почему |
|---|---|
| `isAdmin()` включает Владельца, исключительное — `isOwner()` и политики | ~30 проверок админки сразу верны для Владельца; исключительные права — в одном месте (`UserPolicy::manages`) |
| Ограничения БД — страховка, основной механизм — политики и Actions (уточнение PM) | Любая попытка через API — 403/422, никогда 500 (тест на каждую); база защищает от ошибок вне приложения |
| «Ровно один» — уникальный индекс + CHECK + **отложенный** триггер | Передача меняет две строки в одной транзакции; к COMMIT Владелец должен быть |
| Подсказки интерфейсу (`permissions` у пользователей, `can_resend`/`can_revoke`) — с сервера | Кнопки совпадают с политикой; нет разрешённых действий — нет кнопок |
| Пометка в «Структуре» — по `GET /navigation` (как сайдбар) | Совпадение с деревом гарантировано, без нового поля на сервере |
| Роли и группы Владельца в пространствах — как у всех (подтверждено PM) | Это доступ к пространствам (ADR-0005/0012), а не его учётная запись |

### 9.8. Как проверить руками

#### ТК-3.23. Бейдж «Владелец» в админке и в профиле
Зачем: Владельца должно быть видно сразу — он единственный и с особыми правами.
Предусловия: выполнен `make fresh`; вход owner@selen.test, пароль password-123.
Шаги:
1. Меню пользователя (справа вверху) → «Профиль».
2. Полоса слева → «Администрирование» → «Пользователи».
3. Нажать на имя «Демо Владелец» в списке.
Ожидаемый результат:
- в профиле рядом с заголовком «Профиль» — бейдж «Владелец»;
- в списке пользователей у «Демо Владелец» в колонке «Роль» — бейдж «Владелец», у «Демо Администратор» — «Администратор»;
- на странице пользователя рядом с именем «Демо Владелец» — бейдж «Владелец».
Если не так: скриншот страницы.

#### ТК-3.24. Обычный администратор ничего не может сделать с Владельцем
Зачем: Владельца не может понизить или отключить никто, а обычный администратор не управляет администраторами.
Предусловия: выполнен `make fresh`; вход admin@selen.test, пароль password-123.
Шаги:
1. «Администрирование» → «Пользователи».
2. Посмотреть на правый край строки «Демо Владелец» и навести на значок.
3. Нажать «⋯» в строке «Анна Смирнова».
Ожидаемый результат:
- в строке «Демо Владелец» нет кнопки «⋯» — только значок ключа с подсказкой «Действия с администраторами и Владельцем доступны только Владельцу»;
- в меню Анны есть «Деактивировать», но нет «Сделать администратором»;
- кнопки «Передать владение» на странице нет.
Если не так: скриншот.

#### ТК-3.25. Обычный администратор приглашает только участника
Зачем: назначать администраторов — даже приглашением — может только Владелец.
Предусловия: выполнен `make fresh`; вход admin@selen.test, пароль password-123.
Шаги:
1. «Администрирование» → «Пользователи» → «Пригласить».
2. Раскрыть список «Роль».
3. Закрыть диалог, выйти, войти owner@selen.test (пароль password-123) и повторить шаги 1–2.
Ожидаемый результат:
- у admin@selen.test в списке «Роль» только «Участник», под полем — «Назначить администратора может только Владелец.»;
- у owner@selen.test в списке — «Участник» и «Администратор», подсказки нет.
Если не так: скриншот диалога.

#### ТК-3.26. Владелец назначает и снимает администратора
Зачем: назначение администраторов — исключительное право Владельца.
Предусловия: выполнен `make fresh`; вход owner@selen.test, пароль password-123; второй браузер (или окно инкогнито) — admin@selen.test.
Шаги:
1. owner: «Администрирование» → «Пользователи» → «⋯» у «Борис Петров» → «Сделать администратором».
2. admin (во втором окне): «Администрирование» → «Пользователи», найти строку «Борис Петров».
3. owner: «⋯» у «Борис Петров» → «Сделать участником».
Ожидаемый результат:
- после шага 1 — сообщение «Роль изменена», у Бориса роль «Администратор»;
- у admin@selen.test в строке Бориса нет кнопки «⋯» (только значок ключа);
- после шага 3 у Бориса снова «Участник».
Если не так: скриншот.

#### ТК-3.27. Передача владения
Зачем: Владелец может передать роль другому сотруднику и сам станет администратором — сразу, без перезахода.
