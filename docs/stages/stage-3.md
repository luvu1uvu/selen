# План (утверждён PM)

## Контекст

Сейчас доступ к пространству даёт только личное участие (`space_members`), а сайдбар — плоский список
пространств. Компании (~100 человек) нужно выдавать доступ отделам и подрядчикам целиком (группы) и
навести порядок в навигации (папки). Главный риск — права: у пользователя появляется несколько источников
доступа, и правило их сочетания должно жить в одном месте, иначе политики, доска, подсказка @ и сайдбар
разойдутся. Задел уже есть: роль и видимость читаются только через `Space::roleOf()/membershipOf()/rolesOf()`
и `CardVisibility` (решение этапа 2).

Этап 0 (закрытие этапа 2) выполнен: PR #7 смёржен merge-коммитом, ветки удалены, локально свежий `main`.

## Решения PM (при планировании)

1. **Деактивация никогда не блокируется** (отключить уволенного важнее инварианта). В диалоге деактивации —
   заранее предупреждение со списком пространств, где человек — последний личный активный администратор, и
   возможность прямо там назначить замену (необязательно). Такие пространства в админке «Пространства» —
   бейдж «Нет администратора» и первыми в списке. Инвариант строго действует только на операции с участниками
   и группами.
2. **Архивировать можно только папку без активного содержимого** (активных пространств и активных вложенных папок),
   иначе 422 «сначала перенесите содержимое» со списком мешающего. Архивные пространства и папки внутри не мешают
   и остаются внутри неё (свой статус архива сохраняют). Восстановленное архивное пространство, чья папка в
   архиве, возвращается в корень дерева.

## Решения разработки (с обоснованием, фиксируются в ADR)

- **Итоговые права = набор источников**, а не одна «максимальная роль». Источник — `(тип: personal|group, group_id?, role, own_cards_only)`.
  Действие разрешено, если его целиком разрешает хотя бы один источник:
  - видеть карточку: есть источник без ограничения, или карточка «своя»;
  - действие с карточкой (`permits(role)`): есть источник, где `permits(role)` и (нет ограничения или карточка своя);
  - действие в пространстве без карточки (создать карточку, управлять структурой/участниками): есть источник с `permits(role)`;
  - `my_role` в ответах — максимальная роль (только для показа), права (`permissions.*`) — по правилу выше.
- **Архивная группа доступа не даёт** (строки состава и доступов сохраняются, восстанавливается системным админом).
  **Деактивированному** групповые источники не засчитываются (личный остаётся как сейчас — войти он всё равно не может).
- Группа с ролью admin не может иметь `own_cards_only` (CHECK, как у личного участия).
- **Кеш — на экземпляре `Space`, как сейчас** (ADR-0005): каждый HTTP-запрос получает свежие модели, кеш не
  протекает между запросами и в тестах. Scoped-синглтон не берём: Laravel не сбрасывает его между HTTP-вызовами
  в тестах.
- **Глубина папок — не больше 4 уровней** (пространство — на 5-м): сайдбар ~240 px с отступом 12 px на уровень;
  глубже — признак неудачной структуры для компании на 100 человек. Предел — одна константа.
- **Админка «Структура» — через меню** («Переместить в…» с выбором папки/корня, «Выше», «Ниже»), как колонки на
  этапе 1 (ADR-0007): надёжнее DnD в дереве, проще тестировать и доступно с клавиатуры. DnD — в backlog.
- Участники пространства (обе вкладки) видны всем, у кого есть доступ к пространству (как список людей сейчас),
  **кроме пользователя, у которого в пространстве только источники с `own_cards_only`** (поправка PM, см. ниже).
  Состав группы — в админке; во вкладке «Группы» — название, роль, ограничение, число людей.

## Поправки PM к плану

1. **Сайдбар (3b):** пространство видно независимо от наличия досок — новое пространство без досок тоже в дереве.
2. **Участники для «только своих» (3a):** пользователь, у которого в пространстве **все** источники с
   `own_cards_only` (типичный подрядчик), видит вкладку «Люди» без источников доступа (без названий групп и
   без ролей источников) и не видит вкладку «Группы»: `GET spaces/{KEY}/groups` для него — 403, в
   `GET spaces/{KEY}/members` поле `sources` отсутствует. Названия групп не уходят ему ни в один ответ API —
   тест по аналогии со скрытыми папками (строка названия группы ищется во всех ответах, доступных ему).
   Подсказка @ и выбор людей в карточку работают для него как прежде.

## 3a. Группы и итоговые права

### Данные (новая миграция)

| Таблица | Поля |
|---|---|
| `groups` | `id` ULID, `name` (unique по `lower(name)`), `description` null, `archived_at`, timestamps |
| `group_members` | `group_id`, `user_id` (PK пара), `added_by`, `created_at` |
| `space_groups` | `id`, `space_id`, `group_id` (unique пара), `role` admin/editor/commenter (CHECK), `own_cards_only` (CHECK `NOT (role='admin' AND own_cards_only)`), timestamps; индекс по `group_id` |

### Единая точка прав — `App\Services\Access`

- `SpaceAccess` (value object): список `AccessSource`; методы `isMember()`, `canSeeAllCards()`, `isRestricted()`,
  `allows(callable permits)`, `allowsOnCard(callable permits, bool involves)`, `highestRole()`, `sources()`.
- `SpaceAccessResolver` — **единственный класс с запросами к `space_members`/`space_groups`/`group_members` для прав**:
  - `forSpace(User, Space): SpaceAccess` — один запрос `UNION ALL` (личное + группы: не архивные, пользователь активен);
  - `forUser(User): Collection<space_id, SpaceAccess>` — одним запросом для списков (сайдбар, админка, сводка);
  - `usersWithAccess(Space): Collection` — люди с источниками (вкладка «Люди», подсказка @, выбор людей в карточку);
  - `explain(User)` — сводка для админки: все источники, включая недействующие, с причиной (группа в архиве,
    пользователь деактивирован, пространство в архиве);
  - `administersAnySpace(User)` — для справочника сотрудников (`UserPolicy::viewDirectory`).
- `Space`: `accessOf(User)` (кеш на экземпляре), `static accessesOf(User)`, `rememberAccess()`, `forgetResolvedAccess()`;
  `roleOf()` остаётся как `accessOf()->highestRole()` (для показа); `membershipOf()`, `rolesOf()` удаляются,
  `scopeVisibleTo` переписывается через подзапрос резолвера.
- `ChecksSpaceRole`: `allowMember/allowRole/allowCard` — через `SpaceAccess` (`allowCard`: видимость →
  `allowsOnCard`). Политики и контроллеры не меняются, кроме мест ниже.
- `CardVisibility`: `isRestricted/canSee/scope/present` — через `accessOf()`.

**Переводятся на резолвер:** `SpaceController::index`, `Admin\SpaceController::index`, `SpaceResource`,
`AdminSpaceResource`, `CardResource` (`in_space`, `permissions`), `CardController::mentionable`,
`Rules\AssignableMember`, `UserPolicy::viewDirectory`, `SpaceMemberController::index`.
Actions личного участия (`Add/Change/Remove/SetRestriction`) и `SpaceAdminGuard` по-прежнему работают со своей
таблицей `space_members` — это управление источником, а не вычисление прав.

**Доска:** в фасад карточки добавляется `can_edit` (для Петра: видит все, двигает только свои). Считается
`SpaceAccess::allowsOnCard` + `withExists` «своя карточка» в том же запросе доски; клиент: `edit_cards && card.can_edit`.

### Инвариант личного администратора

`SpaceAdminGuard` уже считает только личных активных admin — сохраняется. Проверяется во всех операциях
с участниками (смена роли, исключение) и группами (выдача admin группе инвариант не меняет; снятие — тоже).
Деактивация не блокируется (решение PM 1): `GET admin/users/{user}/deactivation-impact` → пространства, где он
последний личный активный admin; в диалоге — назначение замены через существующий
`PUT admin/spaces/{space}/members/{user}`. `AdminSpaceResource` — `has_active_admin`, список сортируется
«без администратора» первыми.

## 3b. Дерево навигации

### Данные

`nav_nodes`: `id` ULID, `parent_id` → `nav_nodes` (null — корень), `type` folder|space (CHECK; позже `document`),
`name` (только у folder), `space_id` (unique, только у space), `position` (COLLATE "C", дробные ключи ADR-0007),
`archived_at` (только у folder; у пространства — своё `spaces.archived_at`), timestamps. CHECK на согласованность
типа и полей. Миграция создаёт узел каждому существующему пространству в корне (по названию);
`CreateSpaceAction` — узел в конец корня. Новый тип элемента = новый `type` + ссылка, без переделки дерева.

### Правила

- Ведёт только системный админ: создать, переименовать, архивировать/восстановить папку; переместить папку или
  пространство (в папку, в корень, порядок по соседям `after_id/before_id`).
- Родитель — только активная папка; нельзя переместить папку в саму себя/потомка (рекурсивный CTE); глубина ≤ 4.
- Архив папки — решение PM 2; восстановление папки, чей родитель в архиве, — в корень.
- **Папки не влияют на доступ.** `GET /navigation`: дерево для пользователя — только папки, где на любой глубине
  есть доступное ему активное пространство (`accessesOf` одним запросом + узлы одним запросом, обрезка в PHP).
  **Каждое доступное активное пространство показывается всегда, даже без досок** (иначе админ нового пространства
  не попадёт туда создать первую доску); под ним — список его активных досок (может быть пустым).
  Имена прочих папок не уходят ни в один ответ (тест ищет строку во всех ответах).
- Перемещение меняет только `nav_nodes.parent_id/position`: ключ, номера, история, метрики, доступы не трогаются (тест).

### API и журнал

`GET /navigation` (все); `GET /admin/navigation` (полное дерево с архивом), `POST /admin/folders`,
`PATCH /admin/folders/{id}`, `POST /admin/folders/{id}/archive|restore`, `POST /admin/nav-nodes/{id}/move`.
События: `folder.created`, `folder.renamed`, `folder.archived`, `folder.restored`, `nav_node.moved {node_id, space_id?, from_parent_id, to_parent_id}`.

### Frontend

## 3c. Роль «Владелец»

План утверждён PM 2026-10-15 (с уточнениями PM — ниже, в плане). Промт PM: модель ролей owner | admin | member,
передача владения (из интерфейса и аварийная), пустые папки в дереве Владельца, пометка в «Структуре», проверка
прав «аналитика трудозатрат», приёмка по правилу CLAUDE.md. Карточка на стенде — LATER-54.

### Контекст

Сейчас системных ролей две — `admin` и `member`, и все системные администраторы равны: любой может назначить
администратором себе подобного, снять или деактивировать другого администратора. Компании нужен один человек
с исключительными правами (назначение администраторов, передача владения, а с этапа 9 — аналитика трудозатрат),
которого никто не может понизить или отключить. Заодно — отложенная из 3b задача (backlog): Владелец видит
в дереве по-настоящему пустые папки, а «Структура» помечает узлы, которых нет в дереве текущего пользователя.
Принцип ADR-0005 не меняется: системная роль (и Владелец тоже) не даёт доступа к содержимому пространств.

Ветка `stage-3c` от свежего `main`. Первый коммит — этот план в `docs/stages/stage-3.md` (раздел 3c).

### Модель и данные

- `UserRole::Owner = 'owner'`. Новая миграция `add_owner_role`:
  - CHECK `users_role_check` → `('owner', 'admin', 'member')`;
  - **не больше одного Владельца** — уникальный частичный индекс `users_single_owner ON users ((true)) WHERE role = 'owner'`;
  - **Владелец всегда активен** — CHECK `users_owner_active (role <> 'owner' OR status = 'active')`;
  - **Владелец не пропадает** — отложенный (`DEFERRABLE INITIALLY DEFERRED`) constraint trigger: если в транзакции
    роль Владельца сняли, к коммиту должен появиться новый (передача = смена двух строк в одной транзакции).
    Итого «ровно один» с момента назначения; пустая база (до первого админа) — ноль, это нормально;
  - данные: Владелец — самый ранний по `created_at` (затем `id`) **активный** админ; событие
    `user.ownership_transferred {from_user_id: null, to_user_id, via: 'migration'}` (сырой insert, как прочие
    миграции — без кода приложения). Логика в публичном методе анонимного класса миграции — тест вызывает его.
- `User::isAdmin()` — «системный администратор, **включая Владельца**» (все ~30 проверок в политиках сразу
  покрывают Владельца); новый `User::isOwner()`. Места с `where('role', 'admin')` → обе роли: `AdminGuard`,
  `PmBacklogCommand`, `scripts/pm.sh` (`cmd_owner`), `tests/Pest.php`. `UserFactory::owner()`, хелпер `owner()`.
- `app:create-admin`: если Владельца нет — создаётся Владелец (`user.created {role: 'owner', via: 'console'}`).

### Права (политики; бизнес-ограничения — в Actions, 422)

Правило «кем управляет»: **Владельцем — никто** (и он сам, кроме передачи владения); **администраторами —
только Владелец**; **участниками — любой системный администратор**.

| Действие | Владелец | Админ | Участник |
|---|---|---|---|
| Сменить роль (member ↔ admin), `UserPolicy::updateRole` | ✅ (не себе) | 403 | 403 |
| Деактивировать / восстановить участника | ✅ | ✅ | 403 |
| Деактивировать / восстановить администратора | ✅ | 403 | 403 |
| Что-либо с Владельцем | 403 | 403 | 403 |
| Пригласить с ролью member / admin (`InvitationPolicy::create` получает роль) | ✅ / ✅ | ✅ / 403 | 403 |
| Повторить / отозвать приглашение приглашённого админа | ✅ | 403 | 403 |
| Передать владение | ✅ (другому) | 403 | 403 |
| Остальное в админке (группы, «Структура», пространства, журнал…) | ✅ | ✅ | 403 |

- Роль `owner` через `PATCH …/role` и приглашение не назначается: `Rule::enum()->only([Admin, Member])` → 422.
- «Изменить» Владельца — это системная учётная запись (роль, статус, приглашение). Его роли в пространствах и
  членство в группах ведутся как у всех (это доступ к пространствам, ADR-0005/0012), — так и понимаю промт.
- Подсказки интерфейсу — с сервера, как `permissions.*` у пространств: в строках админского списка
  пользователей `permissions {update_role, deactivate, reactivate, manage_invitation}`, у приглашений
  `permissions {resend, revoke}`, в `/auth/me` — роль.
- **Аналитика трудозатрат**: `Gate::define('view-work-time-analytics', fn (User $u) => $u->isOwner())`
  в `AppServiceProvider` + тест; этап 9 закрывает ею свои маршруты.

### Передача владения

- `POST /api/v1/admin/users/{user}/transfer-ownership {password}` — `TransferOwnershipRequest`
  (`current_password:web`, `throttle:password-change` как у смены пароля), `UserPolicy::transferOwnership`
  (Владелец, не себе). `TransferOwnershipAction::handle(?User $actor, User $to, string $via)`: блокировка строк,
  получатель только активный (иначе 422), бывший Владелец → admin, получатель → owner, событие
  `user.ownership_transferred {from_user_id, to_user_id, via}` (subject — новый Владелец; только id).
- Аварийно: `php artisan app:transfer-ownership {email} {--force}` — показывает «кто → кому», спрашивает
  подтверждение; работает и когда Владельца нет. Событие — с `actor = null`, `via: 'console'`
  (`meta.source = console` пишет `EventRecorder` сам). `php artisan app:owner` — кто Владелец сейчас.
- Стенд PM: `make pm-owner-show` (`app:owner`), `make pm-transfer-ownership EMAIL=…` (с подтверждением в
  терминале). `make pm-owner` остаётся (создать учётную запись PM), подсказка уточняется. Команды берутся из
  `pm.sh` стенда, поэтому заработают после мёржа и `make pm-update`.

### Дерево и «Структура»

- `NavigationTree::forUser`: узлы грузятся все (включая архивные папки — чтобы найти пространства в них),
  архивные папки по-прежнему не выводятся. Множество «непустых» папок — подъём от каждого узла-пространства
  (активного или архивного) по родителям. **Владельцу** видна ещё и папка, где нет ни одного пространства на
  любой глубине, — с `empty: true`; остальным правила не меняются (`empty` всегда `false`). Пустую папку внутри
  папки с недоступными пространствами Владелец не видит: родитель не показывается, значит, и она. Число
  запросов не меняется.
- Сайдбар: у пустой папки приглушённая пометка «пустая» (по образцу отменённого в 3b `EmptyMark`), шеврон —
  только если есть вложенные. «Удалить навсегда…» в «⋯» для пустой папки у Владельца активен (логика уже
  смотрит на полное дерево); текст подсказки о непустой папке — без «пустые папки в дереве не видны».
- «Структура»: значок `EyeOff` (приглушённый, `title` + `sr-only` «Не видно в вашем дереве», как `EveryoneMark`)
  у активных узлов, которых нет в дереве текущего пользователя. Источник — тот же `GET /navigation`, что у
  сайдбара (`useNavigation`, ids узлов общие): без нового поля на сервере, совпадение с деревом гарантировано.
  Архивные узлы не помечаются — у них уже «в архиве». Tooltip-компонента в проекте нет, везде `title` — так же.
