## Сделано

### LATER-116 — время в сообщении о лимите приглашений

- **Причина.** Лимит «10 в минуту» отсчитывает окно от первой попытки: сервер запоминает «конец окна» в целых секундах,
  в ответе 429 — `Retry-After` = конец окна − текущая секунда. Тест делает 11 запросов подряд по живым часам: если
  между первым и последним сменилась секунда (не обязательно медленный CI — достаточно попасть на границу секунды),
  остаётся 59 с, и сообщение честно говорит «59 сек.», а тест ждал «1 мин.». До исправления — 1 провал из 20 прогонов.
- **Что честнее для пользователя — оставить секунды.** `waitTime` уже округляет вверх минуты (от минуты и больше) и
  показывает секунды, когда осталось меньше минуты: «через 12 сек.» — точно, а «через 1 мин.» заставило бы ждать
  лишние 48 секунд. Округление до минут в сообщении не делали; ошибка — в тесте, который зависел от живых часов.
- **Исправление (только тест):** `freezeTime()` в начале теста — время стоит, `Retry-After` всегда 60 («1 мин.»),
  проверка строки целиком осталась. Добавлена проверка ветки «меньше минуты»: через 15 с — «через 45 сек.» (отказ 429
  попыткой не считается); как и раньше, через минуту от начала приглашение снова проходит.
- **Проверено:** тест 20 раз подряд — 20 из 20 (оба теста лимита). Отдельно смоделирован медленный CI — временная пауза
  1,1 с перед запросом, который получает отказ (в коммит не вошла): без заморозки 0 из 3, с заморозкой 3 из 3.

### PR #30 — точный тип `inactive_reason` в `AccessResolver::explain()`

- **Причина.** Код и раньше возвращал только эти три значения или `null` (тип `$sources` перед возвратом — точный).
  Тип расширяется на `$spaces->map(...)`: phpstan 2.3.2 (приходит в PR #30 вместе с Larastan 3.13.1), выводя шаблон
  `TMapValue` коллекции, обобщает строковые литералы внутри массива до `string`. Пробой проверено: так же при выводе
  через вспомогательный метод с точным `@return`, через `collect()` и у базовой `Collection`; точный тип остаётся у
  `array_map` (обычный массив) и у перечисления (объект не обобщается).
- **Исправление:** перечисление `App\Enums\AccessInactiveReason` (`group_archived`, `user_deactivated`, `user_invited` —
  те же значения), как уже сделаны другие «причины» (`BlockEndReason`, `TransitionReason`); frontend называет этот тип
  так же (`shared/types/api.ts`). Причину считает метод `inactiveReason()` с объявленным типом
  `?AccessInactiveReason`; описание `explain()` — `inactive_reason: AccessInactiveReason|null` (те же три значения, не
  `string`); контроллер сводки отдаёт в API `->value` — ответ API не изменился (`UserAccessTest`, `EveryoneGroupTest`
  сверяют строки).
- **Зачем отдельный метод.** Первый вариант — перечисление прямо в `match` — проходил на phpstan 2.3.2, но `make lint`
  на версии main (2.3.1) упал: 2.3.1 выводит `match` как точные случаи (`GroupArchived|UserDeactivated|UserInvited|null`),
  2.3.2 — как общий тип, а шаблон `Collection` инвариантен, совпасть с описанием должно точно. Тип вызова метода —
  объявленный, одинаковый на обеих версиях. Строки с тем же приёмом не помогают: 2.3.2 обобщает и объявленный
  `@return` со строками.
- Вариант «вернуть массив вместо коллекции» (`array_map` строки не обобщает) отклонён: точность держалась бы на
  особенностях вывода типов, и первый же `collect()` вернул бы ошибку.
- **Проверено на обеих версиях:** phpstan 2.3.2 + Larastan 3.13.1 (`composer.lock` из ветки Dependabot во временной
  установке, в коммит не вошёл) — до исправления 1 ошибка (та же, что в CI PR #30), после — «No errors»; версии main
  (phpstan 2.3.1 + Larastan 3.13.0) — «No errors».

Руками не проверяется: поведение для пользователя не менялось (LATER-116 — только тест, сводка доступа — тот же ответ
API); проверяют автотесты backend.
