## Решения PM при планировании

1. Commenter может прикладывать картинки и файлы в комментарии; удалить вложение могут его автор и editor/admin.
2. Текст удалённого комментария стирается, строка с пометкой «комментарий удалён» остаётся.
3. У карточки может быть несколько родителей — как в Kaiten.
4. Бэкап файлов — снапшоты `rsync --link-dest` с той же ротацией, что у дампов.
5. Миниатюры картинок не генерируем — запись в backlog.
6. **Упоминания (поправка A):** упомянуть можно только того, кто видит карточку. Пользователь с ограничением
   без доступа к карточке не появляется в подсказке @, сервер отклоняет такое упоминание (422) — и в описании,
   и в комментарии. Правило одно — `CardVisibility::canSee` — и для подсказки, и для валидатора документа.
7. **Потеря доступа (поправка B):** если пользователь с ограничением своим действием перестал бы видеть карточку
   (сменил заказчика/ответственного, убрал себя из участников), он автоматически остаётся участником.
   Убрать его из карточки может только другой пользователь.

**Решения по ходу 2a:**
- **Автоназначение:** если ответственного нет — переместивший становится ответственным, иначе — участником
  (если он ещё не ответственный и не участник). В модели Kaiten ответственный — это участник с флагом, поэтому
  «стать ответственным» уже означает участие; дублировать человека в двух ролях не стали. Срабатывает при любом
  ручном переходе в колонку «в работе» или «готово» (в том числе между двумя колонками «в работе»), не срабатывает
  при смене типа колонки, появлении подколонки и перестановке внутри ячейки.
- **Убрать себя из участников (поправка B):** если пользователь с ограничением после этого перестал бы видеть
  карточку, сервер отвечает 422 с объяснением «попросите коллегу». При смене заказчика или ответственного
  он молча остаётся участником (`via: keep_access` в журнале).
- **Журнал `card.updated`:** вместо прежнего `card_type_id: {from, to}` на верхнем уровне — общий блок
  `changes {поле: {from, to}}` для типа, людей, срока, «Срочно» и оценки. Production ещё нет, dev-данные
  пересоздаются `make fresh`.
- **Срок:** дата без времени — `due_date`, с временем — `due_at` (UTC). Время вводится в часовом поясе
  из профиля (не браузера) и пересчитывается в UTC на клиенте.
- **Метки:** изменение и архив общей метки и метки пространства — один маршрут `labels/{id}`; права решает
  `LabelPolicy` (общая — системный администратор, 403 для остальных; метка пространства — его администратор,
  404 для не участников).

## Критерии готовности этапа (из промта PM)

Сквозной сценарий (`Stage2ScenarioTest`):
1. В DEV: A (admin), B (editor), C (commenter), E (editor с режимом «только свои карточки»).
2. B создаёт DEV-1: заказчик B, ответственный E, участник C; срок, оценка 6 ч, метки (общая и пространства),
   чек-лист, ссылка, описание с упоминанием C, вложения — скриншот и видео.
3. B создаёт DEV-2, где E никак не участвует, и делает DEV-2 блокирующей для DEV-1.
4. E видит DEV-1, но не DEV-2: на доске, по прямой ссылке, в счётчиках колонок; в блокировке DEV-1 — «Скрытая карточка».
5. C комментирует DEV-1, но не меняет поля и не двигает карточку.
6. DEV-2 переходит в done — блокировка DEV-1 снимается автоматически, история блокировки сохранена.
7. B переносит DEV-1 в In Progress — автоназначения корректны (ответственный уже назначен).
8. Вложения DEV-1 скачиваются участниками; посторонний и E для файлов DEV-2 — 404; SVG/HTML не открываются inline.
9. В event_log нет ПДн; лента истории DEV-1 показывает перемещения и изменения полей.
10. `make backup-verify` восстанавливает базу и файлы (вручную, вывод — в отчёт).

**Решения по ходу 2c:**
- **Лента истории при равном времени:** событие, записанное в тот же момент, что и переход (автоназначение
  после перемещения), показывается выше перехода — оно его следствие. Id сравниваются числами.
- **Поиск по числу** находит и карточку с таким номером, и карточки, где число есть в названии («Отчёт 100%»).
- **Блокировку нельзя поставить карточкой, которая уже в «готово»** (422) — иначе она никогда не снимется сама.
- **Frontend:** старый клиентский `GET …/transitions` больше не используется (лента берёт `…/history`), сам маршрут
  на сервере сохранён. Лента подписывает события по справочникам `refs`; неописанные отдельно типы событий
  берут подпись из каталога журнала (`admin.json → events.types`) — новый тип события сразу виден в ленте.
- **Проверки 2c:** `make lint`, `make test` (backend 659 тестов, покрытие 98,3 %; frontend 115 тестов, покрытие
  строк 83,0 %), `make e2e` (7 сценариев), `make backup-verify` (в счётчиках — `card_relations` и `card_blocks`;

- **Сиды:** в `BoardsDemoSeeder` на доске «Продукт» — 5 эпиков с дочерними, 16 активных блокировок (текстом

  автоснятие при переносе в Done, лента истории, восстановление из архива.
- **Хелпер `browser()`** умеет загрузку файлов (multipart) и DELETE; `uploadedFile()`, `PNG_1X1`, `MOV_HEADER`

  запрос, показываются прежние результаты.

**Модель и API (уточнения к утверждённому плану):**
- `card_relations(id, parent_id, child_id, created_by, created_at)`: unique (parent, child), CHECK parent ≠ child,
  обе карточки из одного пространства. Цикл проверяется рекурсивным CTE под блокировкой пространства.
  `POST cards/{card}/relations {card: "DEV-5", kind: parent|child}` (editor), `DELETE cards/{card}/relations/{relation}`.
  Связать можно только видимую неархивную карточку (иначе 422 «карточка не найдена»). Связь со скрытой карточкой
  пользователь с ограничением не удаляет (422). События `card.relation_added/removed` пишутся у обеих карточек
  (`{relation_id, kind, card_id}`), чтобы связь была в истории каждой.
- Прогресс родителя: дочерние в «готово» (`completed_at`) / все активные дочерние, включая скрытые от зрителя
  (они и так видны в списке как «Скрытая карточка»).
- `CardVisibility::present(User, Card)` — `{id, key, title, category, archived}` или `{hidden: true}`.
- `card_blocks` — по ADR-0011. `POST cards/{card}/blocks {reason?, blocking_card?}` (editor),
  `POST card-blocks/{block}/resolve` (editor). Блокирующая — видимая, из того же пространства, не сама карточка,
  не архивная и не в «готово»; одна активная блокировка на пару карточек. Текст причины в журнал не пишется.
- `GET cards/{card}/history` (member): переходы + события карточки, новые сверху; словари людей, карточек
  (через `present`), меток, типов и колонок. `card.moved`/`card.reordered` не дублируются.
- `GET boards/{board}/archived-cards?search=&page=` (editor+), `GET spaces/{KEY}/cards?search=` (member, до 20,
  только активные) — обе выборки через `CardVisibility::scope`.

## Проблемы и находки

- `page.request` в Playwright не отправляет `Referer`, и Sanctum не узнаёт в нём SPA (401) — в замере
  запросы к API идут через `fetch` из страницы.
- Первый запрос в тесте создаёт сессию (лишний SQL-запрос) — тест «число запросов доски не зависит от числа
  карточек» сначала делает прогревочный запрос.
- `pint` поправил порядок импортов в сидере — перед коммитом обязателен `make lint`, как и записано.
- **E2E в CI PR #6 упал на превью картинки:** локальный диск Laravel пишет файлы 0600 и каталоги 0700, а
  X-Accel-Redirect читает nginx под своим пользователем. На macOS Docker права не проверяются, поэтому локально
  всё работало; на Linux (CI и production) картинка не отдавалась. Диску `attachments` задано `visibility: public`
  (0644/0755; каталог по-прежнему вне webroot и доступен только через internal-location), тест прав в `AttachmentsTest`.
  Повтор теста Playwright (retry) шёл на той же базе и падал на дубле имени — имена файлов теперь с суффиксом попытки.
