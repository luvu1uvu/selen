# LATER-92: параллельные сессии — журнал работ

Карточка: **LATER-92** («Бэклог», метка «инфраструктура»). Ветка `infra/parallel-sessions` от main `8df530a`.
Рабочая копия — основная папка `~/dev/selen`. Задание — описание карточки: замок на dev (Б), свой E2E-стек у каждой
копии (В), правила в CLAUDE.md и runbook (А).

## Сверка фактов карточки (2026-10-22)

- **Через `docker compose exec php`** (контейнер dev): `test-backend`, `lint` (Pint, Larastan), `fix` (Pint), `fresh`,
  `migrate`, `metrics`, `shell`, `admin`. Проверено пробной копией в `.claude/worktrees/`: `exec` из неё попадает
  в контейнер, смонтированный из `~/dev/selen`, — тесты и Larastan идут по чужому коду.
- **Через `docker compose run`** — своя копия: frontend (`run node`), `composer install` в `make up` и `make install`,
  `make key` (`run php`). `run php` требует `.env` в копии (`env_file`): в новой копии без `.env` падает.
- **Не названы в карточке, но тоже бьют по dev чужой копии:** `make down` (останавливает dev), `make destroy`
  (удаляет базу dev), `make db-roles`, `make backup | restore | backup-verify`. У бэкапа база — из dev чужой копии,
  а файлы вложений — из своей папки, поэтому бэкап несогласован. `restore` перетирает чужие данные.
- **E2E:** имя проекта `selen-e2e` и порт `127.0.0.1:8090` фиксированы. В конце `scripts/e2e.sh` (trap) —
  `down -v`. Второй прогон делает `migrate:fresh` в базе первого, конец любого сносит стек обоим. `make e2e-down`
  сносит общий стек. `make perf` использует тот же стек. С разными именами проектов столкнулись бы на порте 8090.
- **Dev сейчас смонтирован из `/Users/ranis/dev/selen`** (`docker inspect selen-php-1`, том `/var/www/backend`).
- **Не было в карточке:**
  - `.env` основной папки отличается от `.env.example` паролями ролей базы и `APP_KEY`. Копия без `.env`
    при `make up` берёт шаблон, и dev, поднятый из неё, не подключится к базе: том инициализирован паролями
    основной папки.
  - Замок на `test-backend`, `lint`, `fix` оставляет сессию без dev без обязательных перед коммитом Pint, Larastan
    и Pest. Хотфикс LATER-61 в рабочей копии обходил это вручную одноразовым контейнером php.

## Решения PM (2026-10-22)

  (`selen-test-<папка>`), не через dev. Поправки:
  1. Стек тестов — тот же Postgres 18 и те же init-скрипты (`docker/postgres/init`, `grants.sql`), что у dev и CI:
     роли `selen_owner` / `selen_app` и запреты прав такие же. Защита `TestCase` «только selen_testing» и переменные

  2. `dev-take`: вместо копии `.env` основной папки — ссылка на него (один источник секретов). Если ссылка не работает
     с монтированием в Docker — копия, с проверкой, что `.env` рабочей копии не попадает в git; аудитор смотрит это.
  3. CLAUDE.md, «Параллельные сессии», — явно: «одна папка — одна сессия» (в том числе основная `~/dev/selen`)
     и «разрешение на dev-take PM может дать сразу в задании».
  4. Отказ замка — первой строкой что делать: «Попросите PM разрешить make dev-take или дождитесь, пока та сессия
     закончит».

  Попутно: docker на месте отсутствующего источника bind mount создаёт **каталог** — поэтому `.env` создаёт цель
  Makefile до любого `docker compose`.

- Hook и описание аудитора: `make test` / `make lint` — и из рабочей копии (проверки больше не идут в dev).

## Ревью кода и точечный аудит безопасности (2026-10-22)

Ревьюер: «важно» — 2, «мелочь» — 9, «вкус» — 4. Аудитор: «критично» и «важно» — 0, «мелочь» — 4, вопросов — 3.
По вопросу PM: ссылка `.env` в рабочей копии в git не попадает (`.gitignore:2` действует на любой глубине; даже `git add -f`
сохранил бы только путь ссылки), секреты через неё никуда не уходят, очистка копий удаляет только саму ссылку.

Исправлено:
- **Очистка копий почти перестала бы удалять копии** (ревьюер, «важно»; вопрос аудитора): стеки проверок и E2E
  монтируют пустой `.env` поверх `backend/.env`, docker создаёт в копии пустой файл-точку монтирования. Пустой
  `backend/.env` теперь не мешает удалению (`host.sh`, тест `test-host-worktrees.sh`).
- **Runbook: `composer require` через `exec`** попадал в копию, из которой поднят dev (ревьюер, «важно») — теперь
  `./scripts/test-stack.sh composer require`.
- **Docker не ответил за 10 с — отказ, а не пропуск проверки** (ревьюер, аудитор S-1): команда пошла бы в тот же docker
  вслепую. Меняет пункт плана «docker не ответил — без проверки»: при остановленной Colima цели dev всё равно падали бы,
  теперь — с понятной причиной. Отдельный текст для контейнера php без тома кода.
- Регистр букв в пути: `/bin/pwd -P` (встроенный `pwd -P` не приводит регистр к записанному на диске).
- `.env`-ссылка — только в рабочих копиях `.claude/worktrees/…` и только если в `.env` основной есть `APP_KEY`; цели dev
  и `make dev-take` в стенде `~/dev/selen-pm` и копиях вне `.claude/worktrees` — отказ (аудитор S-3); `.env` из шаблона —
  права 600 (S-4); «не правьте `.env` в рабочей копии» и «dev — только через цели Makefile» — в CLAUDE.md и runbook (S-2,
  S-1).
- Проверка настроек базы в `.env` рабочей копии — в замке (и для `make up`), а не только в `dev-take`.
- `dev-take`: сначала сборка образа, потом остановка dev; без `--remove-orphans` — проверено: он убивает идущие
  одноразовые контейнеры проекта, то есть проверки frontend других сессий (обычный `down` их не трогает).
- `pg_isready -h 127.0.0.1` в стеках проверок и E2E: по сокету он отвечает «готов» ещё во время init-скриптов.
- Стек проверок: брошенные убитой командой стеки своей копии убирает следующий запуск; без двойного `composer install`.
- Комментарий Makefile о целях без замка, порядок `trap` в тесте, устаревшая строка runbook о `selen_testing`, общий образ
  `selen-php:dev` — подробнее в runbook (разделы 12 и 15).

Не исправлялось (риск принят, записано в runbook):
- Замок защищает от случайностей, не от обхода: `make -i`, прямой `docker compose up`, гонка двух `make up` при
  остановленном dev, `make destroy` при остановленном чужой копией dev (карточка: «dev не запущен — работаем как обычно»).
- Общий образ `selen-php:dev` (тег по хешу Dockerfile — лишняя сложность ради редкого случая).
- `make key` не трогается: ссылка ставится только на `.env` с `APP_KEY`, и `make up` ключ не пересоздаёт.

## Как проверить руками (Mac mini)

Предусловия для всех: PR смёржен; Терминал, папка `~/dev/selen` на `main` (`git pull`); dev запущен (`make up`),
`make dev-status` → «Dev поднят из этой копии». Вторая рабочая копия (как у второй сессии) — один раз:
`git worktree add .claude/worktrees/l92-second -b l92-second origin/main`, затем в ней `make install`.
Убрать за собой в конце: в `~/dev/selen` — `make dev-take` (если dev забран), `git worktree remove --force
.claude/worktrees/l92-second` и `git branch -D l92-second`.

### ТК-L92.1. Одна сессия работает как раньше
Зачем: в своей копии замок ничего не спрашивает и не мешает.
Предусловия: общие.
Шаги:
1. В `~/dev/selen`: `make dev-status`
2. `make migrate`, затем `make fresh`
3. `make lint`
Ожидаемый результат:
- В шаге 1 — «Dev поднят из этой копии: ~/dev/selen — ветка main.»
- В шагах 2–3 команды выполняются, как раньше: ни строки «Попросите PM…», ни вопросов; `make lint` зелёный.
Если не так: вывод команд из Терминала.

### ТК-L92.2. Замок останавливает команду dev из другой копии и объясняет, что делать
Зачем: вторая сессия не сотрёт данные и не подменит код dev, которым пользуется первая.
Предусловия: общие; dev поднят из `~/dev/selen`.
Шаги:
1. `cd ~/dev/selen/.claude/worktrees/l92-second`
2. `make fresh`
3. Открыть http://localhost:8080 — войти, открыть любую доску.
Ожидаемый результат:
- В шаге 2 первая строка — «Попросите PM разрешить make dev-take или дождитесь, пока та сессия закончит.»; дальше —
  «Dev (http://localhost:8080) поднят из другой рабочей копии:», строка «~/dev/selen — ветка main, с …», строка о
  программах в той копии, «Эта копия: ~/dev/selen/.claude/worktrees/l92-second — ветка l92-second.», ««make fresh» не
  выполнена…» и «…только с разрешения PM: make dev-take». Команда завершается ошибкой.
- В шаге 3 данные dev на месте (`make fresh` не выполнялся).
Если не так: вывод команды из Терминала.

### ТК-L92.3. Забрать dev можно только явной командой
Зачем: dev переходит к другой копии только по `make dev-take`, а не «заодно» от `make up` или `make restart`.
Предусловия: ТК-L92.2.
Шаги:
1. Во второй копии: `make up`, затем `make restart`
2. `make dev-take`
3. `make dev-status`, `ls -l .env`, `git status --short`
4. Открыть http://localhost:8080, войти (`admin@selen.test`, пароль `password-123`)
Ожидаемый результат:
- В шаге 1 обе команды останавливаются тем же сообщением замка («make up» / «make restart» не выполнена).
- В шаге 2 — «Забираю dev у копии ~/dev/selen — ветка main…», затем обычный вывод `make up` и подсказка про
  `make migrate` / `make fresh`.
- В шаге 3 — «Dev поднят из этой копии: …/l92-second»; `.env -> /Users/…/dev/selen/.env` (ссылка); `git status` пустой.
- В шаге 4 вход работает (пароли базы подошли).
Если не так: вывод команд из Терминала, скриншот страницы.

### ТК-L92.4. Замок различает основную папку
Зачем: основная папка `~/dev/selen` — такая же копия, как остальные: если dev у второй копии, основная тоже не трогает
его без разрешения.
Предусловия: ТК-L92.3 (dev забран второй копией).
Шаги:
1. `cd ~/dev/selen`, `make migrate`
2. `make dev-take` (вернуть dev), затем `make dev-status`
Ожидаемый результат:
- В шаге 1 — сообщение замка с «~/dev/selen/.claude/worktrees/l92-second — ветка l92-second»; «make migrate» не
  выполнена.
- В шаге 2 — «Dev поднят из этой копии: ~/dev/selen — ветка main.»
Если не так: вывод команд из Терминала.

### ТК-L92.5. Тесты и линтеры идут по коду своей копии, без dev
Зачем: раньше `make lint` из второй копии проверял код той, что подняла dev, и показывал «зелёное».
Предусловия: общие; dev поднят из `~/dev/selen`.
Шаги:
1. Во второй копии испортить стиль PHP:
   `printf '<?php\n$a=1 ;\n' > backend/app/Probe.php`
2. Там же: `make lint`
3. В `~/dev/selen`: `make lint`
4. Во второй копии: `rm backend/app/Probe.php`
Ожидаемый результат:
- В шаге 2 Pint падает и называет `app/Probe.php`; сообщения замка нет.
- В шаге 3 `make lint` зелёный (файла в основной копии нет).
Если не так: вывод команд из Терминала.

### ТК-L92.6. Два make e2e одновременно не мешают друг другу
Зачем: две сессии могут гонять E2E в одно время.
Предусловия: общие.
Шаги:
1. Окно 1, `~/dev/selen`: `make e2e`
2. Сразу же окно 2, вторая копия: `make e2e`
3. Пока идут оба, окно 3: `docker compose ls`
Ожидаемый результат:
- Оба прогона зелёные; в начале каждого — «Стек E2E selen-e2e-selen: http://127.0.0.1:…» и «Стек E2E
  selen-e2e-l92-second: http://127.0.0.1:…» с разными портами.
- В шаге 3 — оба проекта `selen-e2e-selen` и `selen-e2e-l92-second`; после прогонов их нет.
Если не так: вывод обоих окон.

### ТК-L92.7. make e2e-down убирает только свой стек
Зачем: остановка зависшего стека в одной копии не роняет прогон другой.
Предусловия: общие.
Шаги:
1. Окно 1, `~/dev/selen`: `make e2e`
2. Пока идёт, окно 2, вторая копия: `make e2e-down`
Ожидаемый результат:
- Прогон в окне 1 продолжается и заканчивается зелёным.
Если не так: вывод обоих окон.

### ТК-L92.8. make host-status показывает, из какой копии поднят dev
Зачем: PM видит, у какой сессии сейчас dev.
Предусловия: общие; выполнен `make pm-update` (host.sh берётся из копии стенда).
Шаги:
1. `make host-status`
Ожидаемый результат:
- Строка «Dev:              поднят из ~/dev/selen — ветка main, с …».
Если не так: вывод команды.
