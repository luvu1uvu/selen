## 2. Принятые решения и их причины

**Согласованы с PM при планировании и по ходу:**
1. Этап разбит на три подэтапа с отдельными PR (1a, 1b, 1c); после мёржа предыдущего — ветка от свежего `main`.
2. Первая подколонка у колонки с карточками забирает карточки (переход `column_split`, категория та же).
3. Перестановка доски — только внутри пространства; перенос между пространствами API не допускает (тест).
4. Восстановление архивных колонок и дорожек — в backlog.

**Решения по ходу работы:**
5. **Единый ответ 404 в API.** По умолчанию Laravel отвечает на «не найдено» и на «запрещено политикой» разным
   текстом — по нему можно было бы узнать, что чужое пространство существует. Теперь любой 404 одинаков
   (`{"message": "Не найдено."}`), тест сравнивает ответы побайтно.
6. **Архив = скрыто из навигации + только чтение** (пространства и доски): по прямой ссылке участники видят
   содержимое с плашкой «В архиве».
7. **Колонки и дорожки переставляются через меню**, карточки — перетаскиванием (ADR-0007): на сетке с
   подколонками это надёжнее и доступно с клавиатуры.
8. **Карточка в API адресуется номером** (`/api/v1/cards/DEV-123`), как и в интерфейсе.
9. **Архивация карточки — не переход** (положение не меняется). Восстановление в архивную колонку невозможно —
   карточка уходит в первую колонку доски, это пишется переходом.
10. **Неудачный вход по неизвестному email**: введённый адрес сохраняется только в `auth_audit` (12 месяцев),
    иначе терялся бы факт перебора адресов.
11. **Изменение профиля** пишет в журнал только список изменённых полей; часовой пояс (не ПДн) — с было/стало.
12. **Сводка метрик в консоли** `make metrics SPACE=DEV DAYS=60` — инструмент проверки (не отчёт), считает тем
    же сервисом, что панель карточки. Нужен, чтобы метрики на демо-данных можно было посмотреть без SQL (раздел 10).
13. **Опрос файлов в Vite включён по умолчанию** (`VITE_USE_POLLING=true`): в Docker на macOS события файловой
    системы до контейнера не доходят. Проверено: правка `.tsx` видна через 1–2 с, нагрузка ~3 % CPU.
14. **E2E на отдельном compose-проекте** (`docker-compose.e2e.yml`): своя база в памяти и production-сборка
    фронтенда. Окружение `docker/e2e/e2e.env` лежит в репозитории — в нём только тестовый ключ и пароли
    одноразовой базы, это не секреты.
15. **Ключ E2E-пространства — `QA`**: ключ `E2E` отклонила проверка в БД (цифры в ключе запрещены).

**Найдено и исправлено при проверке:**
- CLI `npx shadcn add` ставит посторонний npm-пакет `cn` вместо импорта нашей утилиты — откачено дважды,
  ловушка описана в CLAUDE.md.
- dnd-kit объявлял действия для скринридеров по-английски и с внутренними id — теперь по-русски, с номером карточки.
- Нестабильный тест фокуса после закрытия панели карточки (Radix возвращает фокус асинхронно) — исправлен.
- **Поправка к отчёту по 1b:** там указано «64 теста frontend», на самом деле их было 60 (модельные тесты
  посчитаны дважды). Сейчас — 73.

## 3. Схема БД

Новые таблицы этапа (все даты — `timestamptz`, UTC):

| Таблица | Ключевые поля | Примечания |
|---|---|---|
| `auth_audit` | `occurred_at` · `event_log_id` · `event_type` · `user_id` · `email_attempted` · `ip` · `user_agent` | НЕ append-only; записи старше 12 мес. удаляет `model:prune` (ежедневно 03:30 UTC) |
| `spaces` | `id` ULID · `name` · `key` unique, CHECK `^[A-Z]{2,10}$` · `description` · `last_card_number` · `archived_at` | Не удаляются |
| `space_members` | `space_id` · `user_id` (unique пара) · `role` CHECK admin/editor/commenter | Строка удаляется при исключении; история — в журнале |
| `card_types` | `id` · `name` unique · `color` CHECK `#rrggbb` · `is_default` (ровно один) · `archived_at` | 4 типа создаются миграцией |
| `boards` | `id` · `space_id` · `name` · `description` · `position` (COLLATE "C") · `archived_at` | |
| `board_columns` | `id` · `board_id` · `parent_id` (неизменяем) · `name` · `category` · `position` · `archived_at` | CHECK: тип есть ровно у колонок первого уровня |
| `lanes` | `id` · `board_id` · `name` · `position` · `archived_at` | |
| `cards` | `id` · `space_id` · `number` (unique в пространстве) · `board_id` · `column_id` · `lane_id` · `card_type_id` · `title` · `description` · `position` · `created_by` · `first_started_at` · `completed_at` · `archived_at` · timestamps(6) | Частичный unique `(column_id, lane_id, position)` у активных |
| `card_transitions` | `card_id` · `space_id` · `from/to_board_id` · `from/to_column_id` · `from/to_lane_id` · `from/to_category` · `moved_at`(6) · `actor_id` · `reason` | Append-only: модель + триггер; CHECK на категории и причины |

**Новые типы событий журнала:** `space.*` (created, updated, archived, restored, member_added,
member_role_changed, member_removed), `card_type.*`, `board.*`, `column.*` (created, renamed, moved,
category_changed, archived), `lane.*`, `card.*` (created, updated, moved, reordered, archived, restored).

## 5. Как проверить руками

Нужны Mac с Docker (Colima) и терминал, как на этапе 0.

1. **Запуск и демо-данные:** `colima start`, затем `make up` и `make fresh` (несколько секунд; в конце строка
   «Демо-доски: пространства DEV, OPS, MKT, 380 карточек…»). Если у вас старый `.env` — проверьте, что в нём
   `VITE_USE_POLLING=true` и `SESSION_LIFETIME=480`, затем `make restart`.
2. **Системный админ не видит чужое содержимое:** войдите как `admin@selen.test` / `password-123`. В сайдбаре —
   только DEV. «Администрирование → Пространства»: видны DEV, OPS, MKT с администраторами. В OPS ролей у вас
   нет — меню «⋯» → «Назначить роль» → «Назначить себе» → «Комментатор». OPS появится в сайдбаре, а в
   «Журнале событий» — «Участник добавлен в пространство» с `via: admin_panel`.
3. **Доска на 300 карточек:** выйдите и войдите как `anna@selen.test` (админ DEV). Сайдбар → DEV → «Продукт».
   Доска открывается сразу; прокрутите вправо — колонки до Done, дорожки «Основная» и «Срочные».
4. **Перетаскивание:** перетащите карточку в другую колонку, обновите страницу — она на новом месте.
   С клавиатуры: Tab до карточки, пробел — взять, стрелки — двигать, пробел — положить.
5. **Карточка по ссылке:** кликните по карточке в колонке Done — откроется панель, адрес вида `/cards/DEV-57`.
   В панели — время выполнения и время в работе, история перемещений. «Скопировать ссылку» — для пересылки.
6. **Смена типа колонки:** меню «⋯» колонки Code Review → «Сменить тип» → «Готово»: диалог покажет, сколько
   карточек сменят статус. Можно отменить.
7. **Роли:** войдите как `vera@selen.test` (commenter в DEV) — DEV виден, но нет «+ Карточка» и меню колонок;
   перетаскивать нельзя. Войдите как `member@selen.test` — в сайдбаре только DEV; откройте ссылку на карточку
   из OPS (например, `http://localhost:8080/cards/OPS-1`) — «Карточка не найдена».
8. **Создание пространства и доски:** как `admin@selen.test` → «Пространства» → «Создать пространство»
   (ключ, например, `HR`). Откройте его → «Создать доску» → шаблон «Разработка» или «Простая».
9. **Метрики** — раздел 10.
10. **Тесты:** `make test`, `make lint` и `make e2e` (около 1–2 минут, ваши dev-данные не трогает).

## 7. Известные проблемы, техдолг, риски

**Риски**
- **Ошибочное перемещение нельзя «исправить» в истории** — только новым перемещением. Так задумано
  (append-only), но метрика такой карточки будет учитывать ошибку. Для отчётов этапа 9 может понадобиться
  правило исключения выбросов.
- **Доска без колонки «Готово»** не даёт метрик — интерфейс предупреждает, но не запрещает.
- **Бэкапы на том же диске** и **prod-SMTP не проверен** — без изменений с этапа 0 (к пилоту).

**Техдолг** (подробно — [backlog.md](../backlog.md))
- Начало перетаскивания на 300 карточках — ~70 мс (dnd-kit перерисовывает все карточки); при росте досок —
  виртуализация.
- Восстановление архивных колонок и дорожек из интерфейса.
- Перестановка колонок и дорожек перетаскиванием (сейчас — меню).
- `npx shadcn add` ставит посторонний пакет — обходится вручную.
- Предустановленные типы карточек созданы миграцией с ULID в верхнем регистре, новые объекты — в нижнем;
  на работу не влияет.

**Особенности окружения**
- В `.env` старых установок могут оставаться `VITE_USE_POLLING=false` и `SESSION_LIFETIME=120` — заменить
  и `make restart`.
- Не правьте `.env` через `sed -i`: контейнеры перестают видеть файл (лечится `make restart`).

## 9. Определения lead time и cycle time (как реализованы)

Источник истины — `card_transitions`: каждое изменение положения карточки со **снимком типа колонки на
момент перехода**. Расчёт — `App\Services\Metrics\CardFlowMetrics` (подробно — ADR-0006).

| Величина | Определение |
|---|---|
| `created_at` | момент перехода `created` (создание карточки) |
| `first_started_at` | первый вход в категорию «в работе» (или сразу в «готово», если «в работе» пропущена); дальше не меняется |
| `completed_at` | момент **последнего** входа в «готово», если карточка сейчас в «готово»; при возврате из «готово» обнуляется, при повторном завершении получает новое значение |
| **Lead time** | `completed_at − created_at` |
| **Cycle time** | `completed_at − first_started_at` |

У незавершённой карточки обе метрики не определены. Переименование колонки и смена её типа не меняют уже
записанные переходы: смена типа пишет новые переходы для карточек, которые сейчас в колонке.

**Расчёт для DEV-1 из сквозного сценария** (`Stage1ScenarioTest`, время — UTC, день условный):

| Время | Переход | Категория | Эффект |
|---|---|---|---|
| 09:00 | создана в To Do | очередь | `created_at` = 09:00 |
| 10:00 | To Do → In Progress | очередь → в работе | `first_started_at` = 10:00 |
| 14:00 | In Progress → Code Review | в работе → в работе | — |
| 17:00 | Code Review → Done | в работе → готово | `completed_at` = 17:00 |
| 18:00 | Done → Code Review | готово → в работе | `completed_at` = нет (вернули) |
| 21:00 | Code Review → Done | в работе → готово | `completed_at` = 21:00 |

- **Lead time** = 21:00 − 09:00 = **12 ч** (43 200 с).
- **Cycle time** = 21:00 − 10:00 = **11 ч** (39 600 с).
- Первое завершение в 17:00 не учитывается: после возврата карточка завершена заново.
- После переименования Code Review в «Ревью кода» и смены её типа на «Готово» все шесть переходов DEV-1
  остались прежними, метрики не изменились (проверяется тем же тестом).

## 10. Как самому посмотреть метрики на демо-данных за 60 дней

Демо-данные создаёт `make fresh`. Карточки «прожили» последние 60 дней: создавались, двигались по колонкам,
иногда возвращались на доработку и завершались повторно. Каждый раз данные одинаковые и отсчитываются от
сегодняшнего дня.

**По одной карточке — в интерфейсе.**
1. Войдите как `anna@selen.test` / `password-123` и откройте доску DEV → «Продукт».
2. Кликните по любой карточке в колонке Done. В панели:
   - «Время выполнения (lead time)» и «Время в работе (cycle time)»;
   - даты «В работе с …» и «Готово …»;
   - «История перемещений» — каждый переход с датой, автором и типом колонки на тот момент.
3. У карточек в колонках «в работе» метрик ещё нет — только дата начала работы.

**Сводка по доскам — одной командой.** В терминале, в папке проекта:

```bash
make metrics SPACE=DEV DAYS=60
```

Покажет по каждой доске пространства: сколько карточек всего, сколько сейчас в работе, сколько завершено за
60 дней, а также среднее и медиану lead time и cycle time. На демо-данных DEV / «Продукт»: около 100 завершённых
карточек, lead time в среднем ~12 дней, cycle time ~8 дней. Вместо `DEV` можно указать `OPS` или `MKT`,
вместо 60 — любое число дней.

Обе цифры считаются одним и тем же сервисом и только по истории перемещений. Графики и отчёты для руководства
(распределения, тренды, пропускная способность) — этап 9, на этих же данных.
