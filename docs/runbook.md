# Runbook: эксплуатация Selen

Пошаговые инструкции: запуск, бэкап, восстановление, частые проблемы.
Все команды выполняются из корня репозитория.

## 1. Первый запуск на новой машине

### macOS с нуля

Проверено на чистом Mac mini (Apple Silicon, macOS 15) 2026-10-16. Docker — Colima (бесплатно для компаний).
Команды — в Терминале.

1. **Homebrew** — по инструкции с https://brew.sh. Установщик сам ставит Command Line Tools (в них `make`).
   В конце он просит добавить `brew` в PATH — выполните эти команды: в `~/.zprofile` должна появиться строка
   `eval "$(/opt/homebrew/bin/brew shellenv)"`. Терминалы и сессии Claude Code, открытые до этого, не видят
   `brew`, `docker` и `gh` — откройте новые.
2. **Инструменты:**
   ```bash
   brew install git gh colima docker docker-compose docker-buildx
   ```
3. **Плагины docker** `compose` и `buildx` (без этого `make up` падает: `'compose' is not a docker command`).
   Если файла `~/.docker/config.json` ещё нет:
   ```bash
   mkdir -p ~/.docker && echo '{ "cliPluginsExtraDirs": ["/opt/homebrew/lib/docker/cli-plugins"] }' > ~/.docker/config.json
   ```
   Если файл уже есть — допишите в него ключ `cliPluginsExtraDirs` руками. Проверка: `docker compose version`.
4. **Виртуальная машина Docker:**
   ```bash
   colima start --cpu 4 --memory 6 --vm-type vz --mount-type virtiofs
   ```
   Параметры запоминаются (`~/.colima/default/colima.yaml`): после перезагрузки Mac достаточно `colima start`.
   Запуск при входе в систему — один раз `brew services start colima`.
5. **Доступ к GitHub.** Репозиторий закрытый, SSH-ключа на новой машине нет — вход через браузер, git по HTTPS:
   ```bash
   gh auth login --hostname github.com --git-protocol https --web
   ```
   На вопрос «Authenticate Git with your GitHub credentials?» — **Yes**: после этого работают `git clone`, `pull`, `push`.
6. **Код — строго в `~/dev/selen`:** рядом живут стенд PM и его бэкапы (`~/dev/selen-pm`,
   `~/dev/selen-pm-backups`, раздел 10), а Colima видит только домашний каталог. **Не в `~/Documents`, `~/Desktop`
   и `~/Downloads`:** macOS не пускает в них фоновые агенты launchd (бэкапы, Remote Control — раздел 13), а у этих
   папок бывает синхронизация с iCloud. Папки проекта, стенда и бэкапов не синхронизируются ни с какими облаками.
   ```bash
   mkdir -p ~/dev
   git clone https://github.com/luvu1uvu/selen.git ~/dev/selen
   cd ~/dev/selen
   make up
   make fresh
   ```
   `make up` сам создаст `.env` из `.env.example` (если файла нет), сгенерирует `APP_KEY`, установит зависимости
   composer и npm. Первый запуск занимает несколько минут (скачиваются образы).
7. Откройте http://localhost:8080. Демо-вход: `admin@selen.test` / `password-123` (только при `APP_ENV=local`).
   Письма смотрите в Mailpit: http://localhost:8025.
8. Проверка машины: `make lint`, `make test`, `make e2e` — всё зелёное (первый `make e2e` дольше: скачивается
   образ Playwright).

**Linux:** Docker Engine + плагин compose из официального репозитория Docker, `git`, `make` и `gh` — из пакетов
дистрибутива, дальше — шаги 5–8.

### Переезд с другого компьютера

Git переносит только код. Со старой машины возьмите (лично — флешка, AirDrop; не через почту и облако):

| Что | Зачем |
|---|---|
| `~/dev/selen-pm/.env` | **Обязательно:** `APP_KEY`, пароли ролей базы, пароль QA-бота, `PM_OWNER_EMAIL`. Без него `make pm-up` создаст новые секреты |
| `~/dev/selen-pm-backups/` | Данные стенда: дампы базы и снапшоты вложений (раздел 4) |
| `~/dev/selen/.env` | Необязательно: dev-база всё равно демо. Если переносите — положите до `make up` |

`backend/.env` (пустой) переносить не нужно: Docker создаёт его сам как точку монтирования `.env`.

На новой машине:
1. «macOS с нуля», шаги 1–8.
2. Бэкапы — на то же место, с жёсткими ссылками (`-H`); уже лежащие там файлы не перезаписываются:
   ```bash
   rsync -aH --ignore-existing /Volumes/USB/selen-pm-backups/ ~/dev/selen-pm-backups/
   ```
3. Стенд — **сначала рабочая копия, потом `.env`** (команды — из `~/dev/selen`):
   ```bash
   make pm-worktree      # только git worktree ~/dev/selen-pm, без запуска
   cp /Volumes/USB/selen-pm.env ~/dev/selen-pm/.env
   chmod 600 ~/dev/selen-pm/.env
   make pm-up            # пустой стенд
   ls -t ~/dev/selen-pm-backups/*/*.dump | head -n 1     # последний бэкап (время в имени — UTC)
   make pm-restore FILE=~/dev/selen-pm-backups/hourly/selen_2026-10-16_095213.dump   # путь из строки выше; спросит yes
   make pm-up            # main новее бэкапа — догонит миграции; иначе «Nothing to migrate»
   ```
   `make pm-up` на пустом стенде предложит `make pm-owner` — **не создавайте** учётную запись: она придёт из бэкапа.
   Если папку `~/dev/selen-pm` создать руками (например, чтобы сразу положить `.env`), `make pm-*` откажут:
   «это не рабочая копия стенда». Тогда уберите `.env` в сторону, удалите папку и начните с `make pm-worktree`.
4. Проверка: `make pm-owner-show` — ваш email; на http://127.0.0.1:8081 — вход прежним паролем, на досках LATER
   те же карточки, вложения открываются.
5. Копию секретов, по которой переносили (флешка, временная папка), удалите.

## 3. Создание первого администратора (в т. ч. на сервере)

```bash
make admin
# или без вопросов (например, в скрипте):
docker compose exec php php artisan app:create-admin --name="Иван Петров" --email=ivan@company.ru
```
Пароль лучше вводить интерактивно (опция `--password` останется в истории shell).

**Владелец** (ADR-0017). Первый администратор на пустой базе становится **Владельцем** — единственным, кто назначает
и снимает администраторов и может передать владение (из интерфейса: «Администрирование → Пользователи → Передать
владение», с паролем). Кто Владелец сейчас:

```bash
docker compose exec php php artisan app:owner
```

**Аварийная передача владения** — только на сервере, если Владелец недоступен (уволился, потерял доступ). Бывший
Владелец становится администратором, событие пишется в журнал (источник — консоль):

```bash
docker compose exec php php artisan app:transfer-ownership new-owner@company.ru
```

Команда показывает, кто и кому, и спрашивает подтверждение; получатель — активный сотрудник. Так же назначается
Владелец, если его нет (база, где на момент обновления не было активных администраторов).

## 4. Бэкап

```bash
make backup
```

- Формат: `pg_dump -Fc` (сжатый), файл `backups/daily/selen_YYYY-MM-DD_HHMMSS.dump` (время в UTC).
- **Файлы вложений** (ADR-0010) — снапшот каталога рядом с дампом: `selen_YYYY-MM-DD_HHMMSS.files/`.
  Снапшоты инкрементальные (`rsync --link-dest`): неизменённые файлы — жёсткие ссылки на предыдущий снапшот,
  место занимают только новые. Каждый снапшот — полная копия; удаляется вместе со своим дампом.
  Реальный размер всех снапшотов: `du -sh backups/daily` (du считает жёсткие ссылки один раз).
  Каталог вложений — `ATTACHMENTS_PATH` (по умолчанию `backend/storage/app/private/attachments`).
  При `ATTACHMENTS_DISK=s3` файлы не копируются — резервирование настраивается в хранилище (версионирование бакета).
- После создания файл проверяется (`pg_restore --list`); оборванный дамп в ротацию не попадает.
- Уровни (границы суток и недель — UTC; копии на уровнях — жёсткие ссылки, место не занимают):
  - `hourly/` — только при `BACKUP_KEEP_HOURLY` > 0 (стенд PM, бэкап каждый час — раздел 13): сюда кладётся каждый
    бэкап, хранятся бэкапы за последние `BACKUP_KEEP_HOURLY` часов;
  - `daily/` — без `hourly` каждый бэкап, с `hourly` — первый бэкап суток; хранится `BACKUP_KEEP_DAILY` штук (7);
  - `weekly/` — первый бэкап недели (с понедельника) или любой с `BACKUP_FORCE_WEEKLY=1`; хранится
    `BACKUP_KEEP_WEEKLY` штук (4).
- Два бэкапа одновременно не идут: второй ждёт первого (до 15 минут). Каталог бэкапов — только владельцу (700),
  дампы — 600.
- В конце — строка «Бэкап готов за N с: размер …» (дамп и новые файлы вложений) и место под все бэкапы.
- Каталог — `BACKUP_DIR` (по умолчанию `backups/` в корне, в git не попадает).

**На сервере** — ежедневно через cron (пример, 03:00 по времени сервера):
```cron
0 3 * * * cd /opt/selen && ./scripts/backup.sh >> /var/log/selen-backup.log 2>&1
```
Если PostgreSQL на сервере работает не в Docker: `PG_MODE=local ./scripts/backup.sh`
(нужен `postgresql-client` той же или более новой версии и доступ по `DB_HOST`/`DB_PORT`).

> Бэкап на том же диске защищает от ошибок, но не от потери сервера. Копия вне машины — `scripts/backup-offsite.sh`
> (restic → S3, шифрование на машине). Для сервера (пилот) — Object Storage компании, настройка при подготовке пилота; у стенда
> PM копия есть в коде, но отключена до пилота (раздел 13). Если копируете `backups/` другим способом — с жёсткими
> ссылками (`rsync -aH`), иначе каждый снапшот файлов займёт полный объём.

## 5. Восстановление

> ⚠️ Текущие данные будут **полностью заменены** данными из бэкапа.

```bash
ls backups/daily backups/weekly                      # выбрать файл
make restore FILE=backups/daily/selen_2026-10-12_030000.dump
# скрипт спросит подтверждение — введите yes
```

Что делает скрипт: проверяет файл → останавливает `queue` и `scheduler` → закрывает подключения к базе →
пересоздаёт базу → восстанавливает → **заменяет каталог файлов вложений** парным снапшотом `<имя>.files/`
(`rsync --delete`: файлы, загруженные после бэкапа, пропадут вместе со строками в базе) → запускает
`queue` и `scheduler`. Если снапшота рядом нет (бэкап до этапа 2) — восстанавливается только база. После восстановления все
пользователи должны войти заново, если их сессии создавались позже момента бэкапа.

## 6. Проверка, что бэкапы восстанавливаются

```bash
make backup-verify
```
Считает строки в ключевых таблицах (в том числе `cards`, `comments`, `attachments`) и снимает манифест файлов
вложений (sha256), делает бэкап, **удаляет все данные и файлы**, восстанавливает и сверяет счётчики и
манифест, проверяет, что у каждой строки `attachments` есть файл и что защита журнала событий (триггер) на
месте, а роль приложения после восстановления читает данные и не может изменить историю (раздел 11).
Ожидаемый результат — пять строк `УСПЕХ`:
```
УСПЕХ: данные восстановлены полностью
УСПЕХ: файлы вложений восстановлены, 20 шт., контрольные суммы совпадают
УСПЕХ: у каждого вложения в базе есть файл
УСПЕХ: триггер append-only на event_log на месте
УСПЕХ: права роли приложения selen_app восстановлены, историю она изменить не может
``` Запускайте на dev/stage; на production — только на копии.

Рекомендуется проверять восстановление раз в месяц.

### Лимит загрузки файлов (100 МБ)

Лимит задан в трёх местах и должен совпадать (ADR-0010): `config/selen.php` (`attachments.max_kb`),
`docker/php/php.ini` (`upload_max_filesize`, `post_max_size`), nginx (`client_max_body_size` в location
загрузки). Проверка после деплоя или изменения конфигов (нужна сессия — проще в браузере):

1. Откройте карточку, приложите файл ~90 МБ (`mkfile 90m big.bin` на macOS, `fallocate -l 90M big.bin` на Linux) —
   файл появляется в списке и скачивается. Если вместо этого «файл больше 100 МБ» или в DevTools ответ
   **413** — nginx или PHP режет раньше приложения: сверьте значения командами ниже и перезапустите
   `docker compose restart nginx php`.
2. Файл больше 100 МБ интерфейс не отправляет (сообщение «больше 100 МБ — такой файл не загрузить»);
   сервер в любом случае отклонит его — 422 от приложения или 413 от nginx.

```bash
docker compose exec php php -i | grep -E 'upload_max_filesize|post_max_size'
docker compose exec nginx nginx -T 2>/dev/null | grep client_max_body_size
```

## 7. Демо-данные и метрики (только локально)

`make fresh` создаёт демо-данные (`DemoSeeder` + `BoardsDemoSeeder`, только при `APP_ENV=local`):
пространства DEV, OPS, MKT, участники с разными ролями и ~390 карточек, которые «прожили» последние 60 дней
(создание, перемещения, возвраты на доработку, повторные завершения). Данные одинаковы при каждом
`make fresh` и строятся «от сегодня»: самые старые карточки созданы 60 дней назад. Пароль у всех — `password-123`.

Фасады карточек заполнены (этап 2): общие метки компании и метки DEV, ответственные (назначены автоназначением
при перемещениях), сроки — часть просрочена или выполнена после срока, «Срочно», оценки в часах.
`zhanna@selen.test` — editor DEV в режиме «только свои карточки»: на доске «Продукт» видит 10 карточек
(ответственная или участница), остальные для неё не существуют.
Доски DEV стоят рядами (страница пространства, ADR-0019): [«Дежурства» (две колонки), «Широкая доска»], [«Продукт»],
[«Инфраструктура»].
Содержимое карточек: чек-листы (у части пунктов галочки — прогресс на фасаде), комментарии с упоминаниями,
ссылки и картинки-вложения (счётчики на фасаде). `make fresh` очищает и каталог файлов вложений.

Посмотреть метрики:
- по одной карточке — откройте карточку на доске: в панели время выполнения (lead time), время в работе
  (cycle time) и история перемещений;
- сводка по доскам пространства — `make metrics SPACE=DEV DAYS=60` (среднее и медиана по карточкам,
  завершённым за указанное число дней). Отчёты и графики появятся на этапе 9.

## 8. Тесты в браузере (E2E, Playwright)

```bash
make e2e
```

- Поднимает отдельный compose-проект `selen-e2e-<папка рабочей копии>` (`docker-compose.e2e.yml`; у основной копии —
  `selen-e2e-selen`): своя база в памяти, Redis, php, nginx с **production-сборкой** фронтенда и контейнер Playwright.
  Dev-окружение не затрагивается, прогоны из разных рабочих копий друг другу не мешают (раздел 15). Порт nginx —
  случайный свободный на 127.0.0.1, адрес для ручной проверки печатается в начале прогона; постоянный —
  `E2E_PORT=8090 make e2e`.
- Данные — `E2eSeeder`: пространство QA, пользователи `e2e-admin`, `e2e-editor`, `e2e-outsider`, `e2e-restricted`,
  `e2e-analyst` (`@selen.test`; кто есть кто — в комментарии к сидеру).
- Вход: проект `setup` (`e2e/tests/auth.setup.ts`) один раз входит каждым пользователем и сохраняет состояние
  в `e2e/.auth/` (в `.gitignore`, удаляется после прогона); тесты подключают его через
  `test.use({ storageState: authFile(...) })` или `pageAs(browser, ...)` из `helpers.ts`. Через форму входят
  только `auth.setup.ts` и `auth.spec.ts`: весь прогон — 7 попыток входа при лимите 20 в минуту на IP
  и 5 в минуту на пользователя.
- После прогона стек удаляется. Если запуск прервали — `make e2e-down` (только стек этой копии).
- Отчёт о падении: `e2e/playwright-report/index.html` (в CI — артефакт `playwright-report`).
- Тесты лежат в `e2e/tests`; приёмочные автотесты тест-кейсов — в `e2e/acceptance/stage-<N>/` (с подэтапа 3c,
  правила — `e2e/acceptance/README.md`). Только они: `make e2e-tc TC=3.8,3.9` (по тегам `@tc-…`) или
  `make e2e-stage STAGE=3`; полный `make e2e` и CI запускают всё.
- Версия `@playwright/test` в `e2e/package.json` должна совпадать с тегом образа
  `mcr.microsoft.com/playwright` в `docker-compose.e2e.yml`.

## 9. Производительность доски (`make perf`)

`make perf` поднимает тот же изолированный стек, что `make e2e` (production-сборка фронтенда), заливает
демо-данные (`DemoSeeder` + `BoardsDemoSeeder` + `PerfSpaceSeeder`) и запускает замеры Playwright `e2e/perf/*.perf.ts`
(около 5 минут). Dev-окружение не затрагивается.

`board.perf.ts` — доска DEV / «Продукт» (≈300 карточек) её отдельной страницей (`/boards/ID`), по 5 прогонов при
обычной скорости процессора и при замедлении ×4 (Chrome DevTools, имитация слабого ноутбука):

| Действие | Как считается |
|---|---|
| Появление дерева | от начала загрузки страницы `/` до кадра, в котором в дереве навигации есть пространство DEV |
| Открытие доски | от перехода на страницу доски внутри приложения до кадра, в котором на экране все карточки (с сетью и загрузкой чанка) |
| Начало перетаскивания, переход в другую колонку, движение внутри колонки, отпускание | самый долгий кадр (разрыв между `requestAnimationFrame`) за действие — сколько интерфейс «стоял» |

`space.perf.ts` — страница пространства PERF (`PerfSpaceSeeder`: 5 досок по 200 карточек рядами [узкая, широкая],
[широкая], [две средние], одна из средних у anna свёрнута; ADR-0019), так же 5 прогонов при ×1 и ×4:

| Действие | Как считается |
|---|---|
| Открытие пространства | от клика по пространству в дереве до кадра, в котором видны все карточки первого ряда досок (остальные доски грузятся, когда подходят к экрану) |
| Перетаскивание на первой и на дальней доске | самый долгий кадр от взятия карточки до ответа сервера; дальняя — в третьем ряду, после прокрутки |
| Свернуть и развернуть доску | самый долгий кадр (разворачивание — с загрузкой карточек доски) |
| Свёрнутая доска | замер проверяет, что её карточки не запрашивались ни разу |

В выводе — медиана и все значения в мс. Кадр длится ~17 мс, поэтому значения кратны 17: 17 — плавно,
33–50 — одна-две пропущенные отрисовки, больше 100 — заметная задержка. Сравнивать цифры можно только
с замерами на той же машине (история — в журналах этапов `docs/stages/`).

## 10. Стенд PM

Постоянная копия Selen, в которой PM ведёт свои пространства (отложенные задачи, баги приёмки) и работает каждый
день. `make fresh`, `make test` и `make e2e` её не затрагивают. Стенд — ещё и репетиция будущего сервера:
обновления и миграции идут на накопленных данных, без пересоздания базы (ADR-0014).

| Что | Где |
|---|---|
| Приложение | **http://127.0.0.1:8081** — не `localhost:8081`, и во встроенном браузере Claude тоже (под таблицей). На Mac mini — ещё и адрес Tailscale `https://<имя Mac mini>.<tailnet>.ts.net` (с MacBook, раздел 13) |
| Письма (Mailpit стенда) | http://127.0.0.1:8026 |
| Код | `~/dev/selen-pm` — git worktree, локальная ветка `pm-stand` = `origin/main`, только fast-forward |
| Окружение и секреты | `~/dev/selen-pm/.env` — создаёт `make pm-up` (в `.gitignore`; шаблон — `.env.pm.example`). Бэкапы его не содержат: при переносе стенда скопируйте вручную (порядок — п. 1, «Переезд с другого компьютера») |
| Вложения | `~/dev/selen-pm/backend/storage/app/private/attachments` |
| Бэкапы | `~/dev/selen-pm-backups` (`hourly/`, `daily/`, `weekly/`): на Mac mini — каждый час, с копией в облако (раздел 13) |
| Docker | compose-проект `selen-pm` (`docker-compose.pm.yml`): свои тома PostgreSQL и Redis, образ `selen-php:pm`; `APP_ENV=production` — демо-данные не загружаются, `migrate:fresh` и `db:wipe` запрещены |

**Стенд — только http://127.0.0.1:8081**, в том числе во встроенном браузере Claude, где рядом работают сессии и агенты
с dev. Cookie браузера не различают порт: у `localhost:8080` (dev) и `localhost:8081` они общие. Cookie сессии у стенда
своё (`selen_pm_session`), но cookie `XSRF-TOKEN` одна на двоих. Любой ответ dev подменяет её — даже страница входа
в фоновой вкладке агента, вход не обязателен. После этого сохранение на стенде, отправленное раньше следующего ответа
стенда, падает с ошибкой 419 (повтора с новым токеном пока нет — LATER-78). Агент `ux-reviewer`, увидев вкладку
`localhost:8081`, dev не открывает и пишет об этом первой строкой отчёта (ADR-0023, «Изменения»).

Все команды — из основной копии (`~/dev/selen`), на любой ветке: они выполняют `scripts/pm.sh`
**из рабочей копии стенда** (код main), а не из ветки этапа. В каталоге стенда руками ничего не правьте и dev-команды
(`make up`, `make fresh`) там не запускайте.

| Команда | Что делает |
|---|---|
| `make pm-up` | Первый запуск: рабочая копия, `.env` с новыми секретами, сборка, миграции (~10 минут). Дальше — просто запуск |
| `make pm-down` | Остановить стенд (данные сохраняются) |
| `make pm-owner` | Создать свою учётную запись (системный администратор; первая на стенде — Владелец): имя, email и пароль вводятся в терминале |
| `make pm-owner-show` | Кто Владелец стенда и с какого момента (после обновления 3c миграция назначает Владельцем самого раннего активного администратора) |
| `make pm-transfer-ownership EMAIL=you@example.com` | Передать роль Владельца другому активному пользователю стенда (спросит подтверждение) — если миграция назначила не того |
| `make pm-backlog OWNER=you@example.com` (ваш email из `pm-owner`) | Пространство LATER «Временно, пока реализовывается» (вы — единственный администратор): доски «Бэклог» и «Баги приёмки», метки, карточки из `docs/pm/deferred.yaml`. Повторный запуск ничего не дублирует и уже заведённые карточки не меняет |
| `make pm-qa-bot` | Учётная запись «QA-бот» (`qa-bot@selen.local`, editor в LATER); пароль генерируется и хранится только в `.env` стенда |
| `make pm-bug FILE=bug.json` | Карточка-баг от имени QA-бота в колонке «Новый» доски «Баги приёмки»; печатает номер (LATER-12) |
| `make pm-bug-move KEY=LATER-12 TO=Исправлено` | Перевести карточку LATER по колонкам её доски: «Баги приёмки» — `Новый`, `Исправляется`, `Исправлено`, `"Не баг — решение PM"`; «Бэклог» — `"Взято в работу"`, `Сделано` |
| `make pm-bug-show KEY=LATER-12` | Карточка целиком: колонка, метки, описание, комментарии; вложения — в `.pm-bugs/LATER-12/` основной копии (в `.gitignore`), пути печатаются |
| `make pm-bugs-list` | Баги в колонке «Новый»: номер, название, метки (`COLUMN=Исправляется` — другая колонка) |
| `make pm-task FILE=task.json` | Карточка работы, у которой нет карточки на стенде (инфраструктура, хотфикс, подэтап), — на «Бэклоге» в «Взято в работу» от QA-бота; печатает номер. Повтор с тем же названием не дублирует |
| `make pm-bug-comment KEY=LATER-12 TEXT="Взято в работу"` | Комментарий от QA-бота. Длинный или со знаком `$` — `FILE=комментарий.md`: «## » — заголовок, «1. » и «- » — списки, адреса http(s) — ссылки |
| `make pm-update` | Бэкап → код до свежего main (только fast-forward) → роли базы (раздел 11; на переведённом стенде — проверка) → сборка → `migrate --force` под владельцем схемы → перезапуск |
| `make pm-backup` | Бэкап базы и файлов вложений стенда |
| `make pm-restore FILE=…` | Восстановить стенд из бэкапа (спросит подтверждение) |
| `make pm-restore-check` | Проверить, что бэкап восстанавливается, не трогая стенд: свежий бэкап с копией в облако → последний снапшот из облака (`FROM=local` — локальный бэкап) → временный проект → сверка числа карточек, вложений и файлов с живым стендом → временный проект удаляется. Ожидаемо — строка `УСПЕХ` |

**Первый запуск:** `make pm-up` → `make pm-owner` → `make pm-backlog OWNER=you@example.com` (email из `pm-owner`) → `make pm-qa-bot` →
войти на http://127.0.0.1:8081.

**Обновление.** После мёржа в main — `make pm-update`. Если он остановился с ошибкой, стенд остаётся в режиме
обслуживания, а в выводе — три команды отката с конкретными коммитом и бэкапом: вернуть код
(`git -C ~/dev/selen-pm reset --hard` и коммит), `make pm-restore FILE=` и путь к бэкапу, `make pm-up`.
В командах — свои значения без угловых скобок: zsh принимает `<…>` за перенаправление ввода.
Новые переменные из `.env.pm.example` команды `pm-up` и `pm-update` дописывают в `.env` стенда сами.

**Формат бага для `make pm-bug`** (JSON; `steps` — список или строка с переносами; `screenshot` — необязательный
путь к PNG/JPEG/WebP/GIF, абсолютный или относительно файла JSON; `substage` — номер подэтапа, он же метка;
`labels` — необязательный список меток стенда, например `["безопасность"]` для находок аудита (ADR-0020). Нужно хотя бы
одно из двух. Метки из `labels` бот только ставит: какой метки на стенде нет, ту карточка не получает, а команда
предупреждает — метки заводит PM):

```json
{
  "title": "Кнопка «Архив карточек» уезжает при прокрутке доски",
  "test_case": "ТК-3.5. Широкая доска прокручивается вбок сама",
  "steps": ["Открыть доску «Продукт»", "Прокрутить доску вправо до упора"],
  "expected": "Кнопка «Архив карточек» остаётся на месте.",
  "actual": "Кнопка уехала влево вместе с доской.",
  "substage": "3c",
  "screenshot": "screenshots/archive-button.png"
}
```

**Формат работы для `make pm-task`** (JSON; `description` — простая разметка, как у `pm-bug-comment`: «## » —
заголовок, «1. » и «- » — списки; `substage` — необязательная метка подэтапа):

```json
{
  "title": "Подэтап 4a — уведомления",
  "description": "## Что делаем\n- уведомления в колокольчике\n- письма по упоминаниям",
  "substage": "4a"
}
```

Описание карточки-бага собирается по шаблону: «Тест-кейс», «Шаги воспроизведения», «Ожидаемый результат»,
«Фактический результат» (со скриншотом); тип — «Баг». Метку подэтапа, если её ещё нет, заводит PM (у бота нет
права создавать метки пространства).

**Баги, которые заводит PM руками.** «Баги приёмки» → «+ Карточка» в «Новый», тип «Баг», метка подэтапа;
замечание по удобству или внешнему виду — метка «UX». Шаблон описания («Где», «Шаги воспроизведения», «Ожидаемый
результат», «Фактический результат», скриншот вложением) — в описании доски, под её названием (его дописывает
`make pm-backlog`, если описания нет). Дальше PM пишет сессии «исправь баг LATER-N» — порядок работы с карточкой
описан в CLAUDE.md (раздел о процессе): карточка проходит «Новый» → «Исправляется» → «Исправлено» с комментариями
QA-бота (взято в работу; причина, исправление, PR, тест-кейс).

**Отложенные задачи** — `docs/pm/deferred.yaml` (формат — в комментарии в начале файла). Новая задача — пункт
в конце файла → мёрж → `make pm-update` → `make pm-backlog OWNER=…`.

## 11. Роли базы данных

Приложение работает с базой **не суперпользователем** (docs/adr/0016-db-roles.md):

| Роль | Для чего | Переменные `.env` |
|---|---|---|
| `selen_app` | Веб, очереди, scheduler, тесты: только чтение и запись данных; историю (`event_log`, `card_transitions`, `card_blocks`) — только читать и добавлять | `DB_USERNAME`, `DB_PASSWORD` |
| `selen_owner` | Миграции (`make migrate`, `make fresh`), бэкап и восстановление | `DB_OWNER_USERNAME`, `DB_OWNER_PASSWORD` |
| `selen` (суперпользователь образа postgres) | Только перевод базы на роли | `DB_SUPERUSER`, `DB_SUPERUSER_PASSWORD` |

**Новая база** (новый том Docker, `make up` на новой машине, E2E) получает роли сама — при первом запуске postgres
(`docker/postgres/init/02-roles.sh`).

**База, созданная до ролей,** переводится один раз, данные не меняются:
- dev: `make db-roles` — дописывает `.env` (роли и новые пароли; копия прежнего — `.env.before-db-roles`), создаёт
  роли, передаёт владение базой и объектами `selen_owner`, выдаёт права `selen_app`, перезапускает контейнеры;
  затем `make migrate`;
- стенд PM: ничего отдельно — это первый этап `make pm-update` («Роли базы»).
Повторный запуск безопасен.

Проверить, что всё на месте:
```bash
docker compose exec -T postgres psql -U selen -d selen -Atc \
  "SELECT pg_get_userbyid(datdba) FROM pg_database WHERE datname = current_database();"   # selen_owner
docker compose exec php php artisan tinker --execute 'echo DB::selectOne("select current_user as u")->u;'  # selen_app
make backup-verify   # в конце — «УСПЕХ: права роли приложения selen_app восстановлены…»
```

**Откат перевода** (если что-то пошло не так): `cp .env.before-db-roles .env`, `make restart`, восстановить бэкап,
снятый до перевода (`make restore FILE=…`). Роли в базе остаются — прежнему коду они не мешают.

**Production** (PostgreSQL без Docker, `PG_MODE=local`): роли создаёт администратор БД суперпользователем:
```bash
cd docker/postgres/sql
psql -U postgres -d selen -v owner=selen_owner -v owner_password='…' -v app=selen_app -v app_password='…' -f roles.sql
psql -U postgres -d selen -v owner=selen_owner -f ownership.sql
psql -U postgres -d selen -v owner=selen_owner -v app=selen_app -f grants.sql
```
В `.env` сервера — только `DB_USERNAME=selen_app`, `DB_OWNER_USERNAME=selen_owner` и их пароли; пароль
суперпользователя на сервере не хранится. Миграции при выкладке — `php artisan migrate --force --database=pgsql_owner`.

## 12. Частые проблемы

| Симптом | Причина и решение |
|---|---|
| `Cannot connect to the Docker daemon` | Docker не запущен: `colima start` (или запустите Docker Desktop) |
| `docker: 'compose' is not a docker command` | Плагин не найден — см. `cliPluginsExtraDirs` в п. 1 |
| `command not found: brew` (или `docker`, `gh`) | Терминал открыт до установки Homebrew или в `~/.zprofile` нет `eval "$(/opt/homebrew/bin/brew shellenv)"` — п. 1, шаг 1; откройте новый терминал |
| `could not read Username for 'https://github.com'` | Нет входа в GitHub: `gh auth login` — п. 1, шаг 5 |
| `git fetch` / `push` зависает (ждёт связку ключей macOS) | Запущен системный `/usr/bin/git`, а не git из Homebrew: в терминале нет PATH Homebrew. `which git` должен показать `/opt/homebrew/bin/git` — откройте новый терминал |
| `make pm-up`: «это не рабочая копия стенда» | Папка `~/dev/selen-pm` создана руками, а не `make pm-worktree` — п. 1, «Переезд с другого компьютера», шаг 3 |
| `port is already allocated` (8080, 8025, 54320) | Порт занят другим приложением — поменяйте `APP_PORT`, `MAILPIT_UI_PORT`, `FORWARD_DB_PORT` в `.env`, затем `make restart` |
| 502 Bad Gateway | php или node ещё стартуют или упали: `docker compose ps`, `make logs`. После `npm install` перезапустите `node` |
| Страница не обновляется при правке frontend | В Docker на macOS события файловой системы не доходят до контейнера, поэтому Vite опрашивает файлы (`VITE_USE_POLLING=true`, по умолчанию; правка видна через 1–2 с, ~3 % CPU). Проверьте, что в `.env` не осталось `VITE_USE_POLLING=false` (старые `.env` из этапа 0), затем `docker compose up -d node` |
| 419 / «CSRF token mismatch» | Открыт не тот адрес. Хост должен быть в `SANCTUM_STATEFUL_DOMAINS` (по умолчанию `localhost:8080`, `127.0.0.1:8080`) |
| Письма не приходят в Mailpit | Письма уходят через очередь: проверьте сервис `queue` (`docker compose logs queue`) |
| Тесты в dev (`docker compose exec php vendor/bin/pest`) ругаются на базу `selen_testing` | База создаётся при первой инициализации тома postgres. Если том старый: `docker compose exec postgres createdb -U selen selen_testing`. `make test` от этого не зависит: у стека проверок своя база (раздел 15) |
| После изменения `.env` ничего не поменялось | Контейнеры читают `.env` при создании: `make restart` |
| Права на файлы (Linux) | Makefile передаёт ваш UID/GID в контейнеры; запускайте `make`, а не `docker compose` напрямую при первой сборке |
| `composer.json not found` / пустые папки в контейнере | Colima монтирует в VM только домашний каталог — проект должен лежать внутри `~` |
| Файл не скачивается, 404 на `/files/...` (или `/api/v1/attachments/...`) при видимой карточке | nginx не видит каталог вложений: проверьте монтирование `/var/www/attachments` (dev) или `alias` в `location /_protected/attachments/` и `/_protected/attachments-pdf/` (production, `prod.conf.example`) |
| Ссылка на файл `/files/...` показывает «Страница не найдена» Selen | nginx запущен со старой конфигурацией, без `/files` (UI-1b): он читает её только при старте — `make restart` (стенд — `make pm-update` перезапускает nginx сам) |
| Загрузка большого файла — 413 | Лимиты nginx/PHP меньше 100 МБ — см. «Лимит загрузки файлов» в п. 6 |
| Нужно начать с чистого листа | `make destroy && make up && make fresh` |
| Сборка образа php: `sha256sum: WARNING: … did NOT match`, `redis.tar.gz: FAILED` | Скачанный с GitHub архив расширения не совпал с суммой в `docker/php/Dockerfile` (LATER-82). Сборку не обходить: сначала понять, почему архив другой (новая версия под тем же тегом, подмена), — ниже «Обновить redis или pcov» |

**Обновить redis или pcov в образе php** (LATER-82; расширения — из исходников GitHub по коммиту тега, не с pecl.php.net):
1. Новая версия — тег в репозитории расширения: `phpredis/phpredis` (теги вида `6.3.0`), `krakjoe/pcov` (`v1.0.12`).
2. Коммит тега: `gh api repos/phpredis/phpredis/git/ref/tags/6.3.0 -q '.object.type + " " + .object.sha'`; если тип
   `tag` (аннотированный тег) — коммит: `gh api repos/phpredis/phpredis/git/tags/SHA -q .object.sha`.
3. Сумма архива коммита: `curl -fsSL https://github.com/phpredis/phpredis/archive/КОММИТ.tar.gz | shasum -a 256`
   (pcov — `…/krakjoe/pcov/archive/КОММИТ.tar.gz`).
4. Для redis — коммит подмодуля liblzf в этом теге: `gh api "repos/phpredis/phpredis/contents/liblzf?ref=6.3.0" -q .sha`,
   сумма — `curl -fsSL https://github.com/nemequ/liblzf/archive/КОММИТ.tar.gz | shasum -a 256`.
5. Поменять `ARG` и версии в комментарии `docker/php/Dockerfile`; `make up` пересоберёт образ dev, затем `make test`
   и `make e2e`; на стенде — `make pm-update` после мёржа. Образ `selen-php:dev` один на машине (раздел 15): пока
   ветка не смёржена, сборка из неё меняет его и для других копий.

Архив по коммиту не меняется при переносе тега: `FAILED` при прежнем коммите — повод разбираться, а не пересчитывать сумму.

## 13. Mac mini как хост

Mac mini (работа) — постоянный хост: код, Docker, dev, стенд PM, сессии Claude Code. MacBook (дома) — только окно:
браузер и Remote Control. Решения и причины — ADR-0018.

| Что | Где |
|---|---|
| Стенд с MacBook | **https://<имя Mac mini>.<tailnet>.ts.net** (точный адрес — `APP_URL` в `.env` стенда) — только внутри tailnet PM (`tailscale serve`); на самом Mac mini — и http://127.0.0.1:8081 |
| Сессии Claude Code с MacBook | https://claude.ai/code (или приложение Claude) → среда **selen**; новые сессии — «Selen · Mac mini-…» |
| Агенты launchd | `~/Library/LaunchAgents/local.selen.backup.plist` (бэкап каждый час в :07), `local.selen.remote-control.plist` (сервер Remote Control); Colima — `sh.brew.colima` (Homebrew) |
| Логи | `~/Library/Logs/Selen/`: `backup.log` (больше 5 МБ — в `.1` при следующем бэкапе), `remote-control.log` (~100 КБ в сутки; больше 5 МБ — в `.1` при перезапуске сервера), `launchd.log` (если агент не смог даже запуститься); Colima — `/opt/homebrew/var/log/colima.log` |
| Копия бэкапов вне Mac mini | **отключена до пилота** (решение PM 2026-10-16): `OFFSITE_ENABLED=false` в `~/.config/selen/offsite.env` (600); бэкапы стенда — только на Mac mini. Когда включат — restic → S3, ключи — в том же файле, пароль шифрования — `~/.config/selen/restic-password` (600, копия — в менеджере паролей PM) |
| Состояние задания бэкапов | `~/.local/state/selen/backup.state` (смотреть — `make host-status`) |

**Проверка за минуту:** `make host-status` — Colima, стенд, Tailscale, Remote Control, агент бэкапов, копии сессий, последний бэкап
(время, длительность, размер), копия вне Mac mini (сейчас — «отключена (решение PM, до пилота)»). Внизу — «Всё в
порядке.» или строки «ВНИМАНИЕ».

**Правила.**
- Папки `~/dev/selen`, `~/dev/selen-pm`, `~/dev/selen-pm-backups` не синхронизируются ни с какими облаками (iCloud,
  Яндекс Диск…). Копии вне Mac mini сейчас нет (отключена до пилота); когда её включат — только зашифрованная restic.
- Стенд — только внутри tailnet: **Tailscale Funnel не включать** (`host-status` предупредит). Узлом Mac mini
  ни с кем не делиться.
- Пароли и ключи не вставлять в переписку с Claude (при Remote Control она хранится на серверах Anthropic) — их
  вписывает PM сам, в Терминале или редакторе.

### Установка (один раз; делает PM, команды — в Терминале на Mac mini)

1. **Сон и питание** — проверить: `pmset -g` → `sleep 0`, `autorestart 1` (Mac mini не засыпает и включается после
   пропадания питания). FileVault включён — после перезагрузки всё стартует, когда PM войдёт в систему.
2. **Colima при входе:** `brew services start colima` (п. 1, шаг 4). Останавливать — `brew services stop colima`
   (после `colima stop` агент Homebrew поднимет её снова).
3. **Claude Code** (native installer, `~/.local/bin/claude`): `curl -fsSL https://claude.ai/install.sh | bash`, в
   `~/.zprofile` — `export PATH="$HOME/.local/bin:$PATH"`. Вход: `claude auth login` (аккаунт claude.ai).
   **Один раз** в папке проекта: `cd ~/dev/selen && claude remote-control --spawn worktree` — на вопросы
   `Trust …? [y/N]` и `Enable Remote Control? (y/n)` ответить `y`, дождаться «Connected», закрыть окно Терминала
   (без этого сервер под launchd не стартует: спросить без терминала он не может).
4. **Tailscale:** `brew install --cask tailscale-app` (спросит пароль Mac) → открыть Tailscale, разрешить системное
   расширение / VPN, войти, в настройках — «Launch at login». В консоли https://login.tailscale.com/admin/dns —
   MagicDNS и HTTPS Certificates. Затем опубликовать стенд (если Tailscale попросит включить Serve — открыть ссылку):
   ```bash
   /Applications/Tailscale.app/Contents/MacOS/Tailscale serve --bg http://127.0.0.1:8081
   ```
   Настройка сохраняется и после перезагрузки. В `~/dev/selen-pm/.env` (адрес — свой, из `tailscale status`):
   ```
   APP_URL=https://<имя Mac mini>.<tailnet>.ts.net
   FRONTEND_URL=https://<имя Mac mini>.<tailnet>.ts.net
   SANCTUM_STATEFUL_DOMAINS=127.0.0.1:8081,localhost:8081,<имя Mac mini>.<tailnet>.ts.net
   SESSION_SECURE_COOKIE=null
   TRUSTED_PROXIES=172.16.0.0/12
   ```
   затем `make pm-up`. `SESSION_SECURE_COOKIE=null` — cookie с флагом Secure по HTTPS и без него по http://127.0.0.1.
   `TRUSTED_PROXIES` — верить `X-Forwarded-For` и `X-Forwarded-Proto` от `tailscale serve` (ADR-0021):
   - nginx в Docker видит хост как шлюз сети Docker (172.16.0.0/12), а настоящий адрес устройства в tailnet есть
     только в заголовке от Tailscale;
   - без переменной у всех, кто входит через Tailscale, в журнале и в лимите входа один адрес — `172.18.0.1`;
   - компромисс: процесс на самом Mac mini (браузер, curl, сессии Claude), который обращается к `127.0.0.1:8081`
     напрямую, может подставить свой IP. Держится на том, что порты стенда — только на 127.0.0.1 (`make host-status`
     предупредит о другом);
   - на боевом сервере (LATER-31) значение выбирается заново, подсеть офиса туда не вписывать.
5. **Копия вне Mac mini — сейчас отключена** (решение PM 2026-10-16, до пилота; ADR-0018): в
   `~/.config/selen/offsite.env` стоит `OFFSITE_ENABLED=false` (так его создаёт `make host-install`). Ни уведомлений,
   ни «ВНИМАНИЕ» о копии нет, `make host-status` пишет «Копия вне Mac mini: отключена (решение PM, до пилота)»,
   `make pm-restore-check` проверяет локальный бэкап. Сбои самого бэкапа — по-прежнему с уведомлением.
   **Пока копия отключена, при потере Mac mini (диск, кража, пожар) данные стенда не восстановить.**
   Включить — ниже, «Копия вне Mac mini: как включить».
6. **Агенты:** `make host-install` (из `~/dev/selen`; после мёржа и `make pm-update`). Создаёт агенты бэкапов и
   Remote Control, `~/.config/selen/restic-password` и `~/.config/selen/offsite.env` из шаблона `.env.offsite.example`
   (копия отключена). Один агент — `make host-install AGENT=backup` или `AGENT=remote-control`.
7. **Уведомления о сбоях** показывает `osascript` — в системе они идут от «Редактора скриптов» (Script Editor):
   System Settings → Notifications → «Редактор скриптов» → разрешить. Проверка: `osascript -e 'display notification "проверка" with title "Selen"'`.
8. **Firewall macOS:** System Settings → Network → Firewall → включить (вторая линия защиты; порты Docker и так
   только на 127.0.0.1). Аккаунт claude.ai — с двухфакторной аутентификацией: доступ к нему — это командная строка
   на Mac mini.
9. **Проверка:** `make pm-restore-check` → строка `УСПЕХ: бэкап (local) …` (`offsite` — когда копия включена);
   `make host-status` → «Копия вне Mac mini: отключена (решение PM, до пилота)» и «Всё в порядке.»

### Копия вне Mac mini: как включить

Хранилище — S3 в РФ (для пилота — Object Storage компании; Selectel — так же: контейнер S3, сервисный пользователь
с доступом к одному проекту, S3-ключ, адрес `https://s3.ru-1.storage.selcloud.ru`, регион `ru-1`). Яндекс Диск не
подходит (ADR-0018, «Изменения»).
1. https://console.yandex.cloud → отдельный каталог, например `selen-backups` (ключ не будет видеть другие бакеты).
2. Object Storage → «Создать бакет»: доступ на чтение объектов, к списку объектов и настройкам — **ограниченный**.
3. «Сервисные аккаунты» этого каталога → создать `selen-backup` с ролью `storage.editor`.
4. В аккаунте → «Создать новый ключ» → «Создать статический ключ доступа». Секрет показывается один раз — сразу
   в файл из шага 6.
5. В бакете → «Версионирование» — включить; «Жизненный цикл» → правило для всех объектов: некурантные версии
   удалять через 30 дней. Тогда удалённое ключом (ошибка, шифровальщик на Mac mini) можно вернуть месяц.
6. В `~/.config/selen/offsite.env` впишите редактором `OFFSITE_ENABLED=true`, `RESTIC_REPOSITORY`
   (`s3:https://storage.yandexcloud.net/<бакет>/selen-pm`), `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`
   (`AWS_DEFAULT_REGION=ru-central1` уже стоит).
7. **В менеджер паролей** — пароль restic (`~/.config/selen/restic-password`) и содержимое `offsite.env`: без них копию
   не достать.
8. `make pm-restore-check` → `УСПЕХ: бэкап (offsite) …`; `make host-status` → «Копия в облаке: <время> …» и «Всё в
   порядке.»

### Remote Control: подключение и перезапуск

- **С MacBook:** https://claude.ai/code → в списке сред — **selen** → сессия или «новая» (каждая новая — в своём git
  worktree основной копии, они не мешают друг другу). Или приложение Claude на телефоне. Разрешения на команды
  подтверждаются там же.
- **Перезапустить сервер:** `launchctl kickstart -k gui/$(id -u)/local.selen.remote-control`. Лог — `tail -f
  ~/Library/Logs/Selen/remote-control.log`: при запуске — «Connected», дальше статус раз в 10 минут и события.
- **Вышли из аккаунта Claude** (в логе — «must be logged in»): `claude auth login`, затем перезапуск сервера.
- Остановить совсем: `make host-uninstall AGENT=remote-control`; вернуть — `make host-install AGENT=remote-control`.
- **Рабочие копии сессий** копятся в `~/dev/selen/.claude/worktrees/` (в git не попадают). `make host-status` —
  строка «Копии сессий: N, из них завершённых без изменений — M». Очистка — `make host-worktrees-clean` в окне
  Терминала: показывает, что оставит и почему, и после подтверждения (`y`) удаляет только **копии сессий Remote
  Control** (`bridge-cse_…`; копии сессий приложения Claude и `claude --worktree` — «не Remote Control», не
  трогаются, ADR-0018), где сессия завершена (внутри не работает ни один процесс, из копии не запущен docker-стек,
  блокировку сервера Remote Control никто не держит), нет незакоммиченных изменений, нет файлов вне git, кроме
  зависимостей и кешей (`node_modules`, `vendor`, результаты тестов) и ссылки `.env` на `.env` основной копии (раздел
  15), — то есть дампы в `backups/`, свой `.env` и подобное копию сохраняют, — и нет коммитов, которых нет на GitHub. После `y` каждая копия проверяется заново прямо перед
  удалением: если пока вы отвечали, в ней что-то появилось, изменилась блокировка или новый коммит, — «НЕ удалена» с
  причиной. Не смогла проверить копию (`git`) — эту копию не удаляет; не ответили `lsof` или docker — не удаляет
  ничего. Подтверждение — только с клавиатуры: `echo y | make host-worktrees-clean` ничего не удаляет (защита от
  случайного ввода, а не от агента). Удаляется только ветка самой сессии (`worktree-bridge-cse_…`), и безопасно
  (`git branch -d`): не слитая остаётся, на другую ветку, на которую переключилась сессия, очистка не трогает. Пока
  сервер держит блокировку копии, она не удаляется — после его перезапуска брошенные блокировки перестают мешать.

### MacBook (дома) — только окно

1. **Tailscale** — App Store или `brew install --cask tailscale-app`, войти тем же аккаунтом. Стенд —
   https://<имя Mac mini>.<tailnet>.ts.net (вход своим паролем стенда).
2. **Claude Code** — через https://claude.ai/code, код на MacBook не нужен.
3. **iCloud:** из iCloud Drive («Документы») удалить папки `selen`, `selen-pm` и `selen-pm-backups` — и на MacBook,
   и в iCloud (в них лежали `.env` стенда и бэкапы; секреты стенда уже сменены). Запасной клон, если нужен, — только
   код, вне iCloud: `git clone https://github.com/luvu1uvu/selen.git ~/dev/selen` (без `.env` стенда и без стенда).

### Сбои

| Признак | Что делать |
|---|---|
| Уведомление «Selen: бэкап стенда» / «ВНИМАНИЕ» в `host-status` | Текст ошибки — в уведомлении и в `~/Library/Logs/Selen/backup.log`. Стенд не запущен — `make pm-up`; хранилище restic недоступно — сеть, ключ в `offsite.env`, пароль. Проверить вручную — `make pm-restore-check` |
| «Последний успешный бэкап — больше 2 ч назад» | Агент не работает: `make host-install AGENT=backup`, затем `launchctl print gui/$(id -u)/local.selen.backup` (последний код выхода) и `launchd.log` |
| «Другой бэкап … идёт дольше 900 с» | Брошенная блокировка снимается сама (процесс завершился или ей больше 3 ч). Если бэкап действительно не идёт (`ps aux | grep backup.sh` пусто) — `rm -rf ~/dev/selen-pm-backups/.lock` |
| «Порт … открыт в сеть» | Порт контейнера проброшен не на 127.0.0.1 — в compose-файле должно быть `"127.0.0.1:ПОРТ:…"`, затем `docker compose up -d`. Чинить сразу: на этом держится доверие `X-Forwarded-For` от хоста (`TRUSTED_PROXIES`, ADR-0021) — через открытый порт любой подменил бы IP |
| В «Журнале событий» у входов с MacBook адрес `172.18.0.1`, а не 100.x | В `~/dev/selen-pm/.env` нет значения `TRUSTED_PROXIES` (`make pm-update` дописывает строку пустой). Вписать редактором (не `sed -i`) `TRUSTED_PROXIES=172.16.0.0/12` (шаг 4 установки), затем `make pm-down` и `make pm-up`: `make pm-update` при свежем коде контейнеры не пересоздаёт, и новое значение не применится |
| После перезагрузки стенд не открывается | Вошли ли в систему (FileVault)? `make host-status`: Colima не запущена — `brew services restart colima`; стенд — `make pm-up` |
| С MacBook адрес Tailscale не открывается | На обеих машинах Tailscale включён и вошёл в один аккаунт; на Mac mini `tailscale serve status` показывает `proxy http://127.0.0.1:8081` |

### Восстановление из облака (Mac mini потерян)

Только если копия вне Mac mini была включена (сейчас отключена — восстанавливать неоткуда). На новой машине — п. 1,
«Переезд с другого компьютера», но бэкапы — из restic. **`make host-install` — только после восстановления:** агент
бэкапов сразу положил бы в то же хранилище снапшот нового пустого стенда. Из менеджера паролей: содержимое
`offsite.env` → `~/.config/selen/offsite.env`, пароль restic → файл по пути из `RESTIC_PASSWORD_FILE` в нём (оба —
`chmod 600`, каталог — `chmod 700`); `.env` стенда — оттуда же или заново (`make pm-up`). Ключи — только в подоболочке
(скобки), чтобы они не остались в окружении терминала. Снапшот — по ID из списка (последний до потери Mac mini),
а не `latest`:
```bash
( set -a; . ~/.config/selen/offsite.env; set +a; restic snapshots --tag selen )      # список копий: ID, время
( set -a; . ~/.config/selen/offsite.env; set +a; restic restore <ID> --target ~/restic-restore )
find ~/restic-restore -name '*.dump'               # путь к дампу; рядом — <имя>.files с вложениями
make pm-restore FILE=~/restic-restore/Users/<пользователь>/dev/selen-pm-backups/hourly/selen_2026-10-16_130700.dump   # путь — из строки выше
rm -rf ~/restic-restore                            # после проверки стенда
```
Затем — шаги 6–9 установки (агенты, проверка `make pm-restore-check`).

## 14. Безопасность: аудит и проверки в CI

Решения и причины — ADR-0020; когда звать аудитора — CLAUDE.md, «Аудит безопасности».

| Что | Где и как |
|---|---|
| Уязвимости зависимостей | `make audit-deps` (локально, ~10 с; образы dev, файлы — только чтение) — то же, что job «Зависимости» в CI: падает на high и critical; low, medium и заброшенные пакеты — для сведения |
| Секреты в истории git | CI, job «Секреты в истории git (gitleaks)» — вся история, найденное значение в логе скрыто |
| Workflow «Security» | GitHub → Actions → Security: на каждый push и PR и по понедельникам в 07:00 МСК; вручную — «Run workflow» |
| Dependabot | GitHub → Pull requests: обновления безопасности — сразу, отдельными PR; minor и patch — один PR по понедельникам; major не предлагаются. Мёрж — как любой PR, после «принято» |
| Аудитор | В сессии Claude Code из `~/dev/selen` или его рабочей копии: «Запусти аудитора безопасности, полный режим» (или «точечный по этой ветке»). Отчёт полного аудита — `docs/security/audit-ГГГГ-ММ.md`, находки «критично» и «важно» — карточки с меткой «безопасность» на «Баги приёмки» |

**Включить Dependabot alerts и security updates** (один раз, делает владелец репозитория): GitHub → репозиторий →
Settings → Code security (Advanced Security) → Dependabot alerts — Enable, Dependabot security updates — Enable.
Проверка: Insights → Dependency graph → Dependabot — видны composer, npm (`frontend`, `e2e`), github-actions, docker,
docker-compose и время последней проверки; ошибки разбора `.github/dependabot.yml` показываются там же.

**Красная проверка «Security».** Зависимости: в логе — пакет и версия с исправлением → карточка или хотфикс «обновить
пакет» (не правка в чужом PR). gitleaks: секрет попал в историю — он раскрыт, сначала сменить его, затем решить с PM,
переписывать ли историю git.

## 15. Параллельные сессии

Решение PM 21.10, LATER-92. Несколько сессий Claude Code (Remote Control, приложение) работают одновременно — каждая
в своей рабочей копии: основная папка `~/dev/selen` или копия в `~/dev/selen/.claude/worktrees/…`. Правила для сессий —
CLAUDE.md, «Параллельные сессии»: одна папка — одна сессия; dev — у одной копии за раз, забирать — только с разрешения
PM (его можно дать сразу в задании); стенд — только `make pm-*`, одна сессия за раз; бэклог и дорожную карту правит
одна сессия.

| | У каждой копии своё | Одно на машине |
|---|---|---|
| Код и ветка | папка копии | |
| Тесты и линтеры backend (`make test`, `make lint`, `make fix`) | стек проверок `selen-test-<папка>-<номер процесса>` (`docker-compose.test.yml`): Postgres 18 в памяти с теми же init-скриптами, что у dev (роли и права — ADR-0016), и Redis; живёт, пока идёт команда | |
| Тесты и линтеры frontend | `docker compose run node` — папка копии | |
| E2E и `make perf` | стек `selen-e2e-<папка>`, порт — случайный (раздел 8) | |
| Dev: http://localhost:8080, его база, Redis, Mailpit | | работает с кодом той копии, из которой поднят |
| Образ `selen-php:dev` | | собирают `make up`, `make dev-take` и `make e2e` (`--build`) из своей копии; стек проверок берёт готовый. Ветка, которая меняет `docker/php/Dockerfile`, этой сборкой меняет образ для всех копий, а в копии без dev её тесты идут на образе, собранном последним, — пока не прогнан её `make e2e` |

**Замок на dev.** Цели, которые работают с dev, — `up`, `restart`, `down`, `destroy`, `shell`, `fresh`, `migrate`,
`db-roles`, `admin`, `metrics`, `backup`, `restore`, `backup-verify` — сначала проверяют, из какой копии поднят dev
(`scripts/parallel.sh dev-check`): по источнику тома `/var/www/backend` работающего контейнера php, по точному пути —
`~/dev/selen` и `~/dev/selen/.claude/worktrees/x` разные копии (регистр букв — как на диске). Своя копия или dev
не запущен — команда выполняется как раньше. Docker не ответил за 10 с — отказ «проверьте Colima и повторите»: команда
пошла бы в тот же docker вслепую. Цель dev в стенде `~/dev/selen-pm` или копии вне `.claude/worktrees` — отказ «это не
копия для dev». Чужая копия — отказ:

```
Попросите PM разрешить make dev-take или дождитесь, пока та сессия закончит.

Dev (http://localhost:8080) поднят из другой рабочей копии:
  ~/dev/selen/.claude/worktrees/bridge-cse_… — ветка stage-9b, с 22.10 14:05
  в той копии сейчас работают программы: claude, zsh
Эта копия: ~/dev/selen — ветка infra/parallel-sessions.
«make fresh» не выполнена: она сработала бы в чужом dev — по чужому коду и с чужими данными.
Забрать dev (другая сессия потеряет его посреди работы) — только с разрешения PM: make dev-take
Без dev в этой копии работают make test, make lint и make e2e.
```

«В той копии сейчас ничего не запущено» — подсказка, что dev, скорее всего, остался от завершённой сессии; решение
забрать его всё равно за PM. Список целей с замком сверяет `scripts/test-parallel.sh` (`make lint`, CI): новая цель
с `docker compose exec` или `up` без замка роняет проверку. `docker compose up | down | exec` напрямую замок не проверяет:
dev — только через цели Makefile, `exec` — это dev той копии, которая его подняла.

**Забрать dev — `make dev-take`** (сессия — только с разрешения PM):
1. Если у копии нет `.env` — создаёт ссылку на `.env` основной копии (ниже).
2. Собирает образ php из этой копии, останавливает контейнеры dev (данные базы и Redis остаются; идущие проверки
   frontend других сессий — одноразовые контейнеры `node` — не трогает) и поднимает dev из этой копии (`make up`).
3. Ветки отличаются миграциями — `make migrate`. Файлы вложений лежат в папке копии, поэтому у картинок демо-данных
   после смены копии нет файлов — `make fresh` (данные dev сотрутся).

**`.env` рабочей копии — ссылка на `.env` основной** (`make up`, `make dev-take`; только в `.claude/worktrees/…` и
только если в `.env` основной есть `APP_KEY`): один источник секретов, пароли базы dev совпадают (её роли созданы
паролями основной копии). **Не правьте `.env` в рабочей копии** — изменится `.env` основной копии и dev, кто бы его ни
держал; новая переменная — в `.env.example`, сам `.env` правит PM или сессия основной копии. В git ссылка не попадает
(`.gitignore`), очистке копий сессий не мешает (раздел 13). Если в копии уже свой `.env` с другими настройками базы,
цели dev и `make dev-take` останавливаются и подсказывают `rm .env && ln -s ~/dev/selen/.env .env`. Тестам, линтерам
и E2E `.env` не нужен. Новый `.env` из шаблона — с правами 600.

**Новая рабочая копия:** зависимости — `make install` (composer — в стеке проверок, npm — `docker compose run node`);
тесты backend и E2E ставят composer-зависимости сами, если их нет.

**Одна папка — одна сессия и для тестов:** два прогона Pest в одной копии одновременно мешают друг другу — `Storage::fake`
пишет файлы в её `backend/storage/framework/testing` (так было и до стеков проверок). Копии друг другу не мешают.

**Остался стек от прерванной команды.** `make e2e-down` — E2E-стек этой копии. Стек проверок удаляется сам, а брошенный
убитой командой (процесса с номером из имени уже нет) убирает следующий запуск в этой копии; вручную — `docker compose
ls`, затем `docker compose -p <имя> down -v`. Стек старого образца `selen-e2e` (до LATER-92) — `docker compose -p
selen-e2e down -v`. Пустой `backend/.env` в копии — точка монтирования, которую создаёт docker; очистке копий не мешает.

`make host-status` показывает строку «Dev: поднят из ~/dev/selen/.claude/worktrees/… — ветка …, с …» (или
«не запущен»); `make dev-status` — то же из копии сессии, с пометкой «из этой копии» или «из другой».
