# CLAUDE.md — правила проекта Selen

Selen — внутренний канбан-инструмент компании (~100 сотрудников). Продукт не для рынка: цель —
независимость от внешних SaaS. Сопровождают PM с Claude Code и штатные разработчики (Laravel / React).

**Главный принцип: конвенционально и предсказуемо.** Если есть «стандартный путь Laravel/React» —
выбираем его. Никаких самописных фреймворков и экзотики. Сомневаешься — спроси или сделай как в
документации Laravel/React и запиши решение в ADR.

## Стек

| Слой | Технологии |
|------|-----------|
| Backend | Laravel 13, PHP 8.4, PostgreSQL 18, Redis 8 (кеш, очереди, rate limiting) |
| Аутентификация | Laravel Sanctum, cookie-сессии SPA (один домен), сессии в PostgreSQL |
| Frontend | React 19 + TypeScript + Vite 8 (SPA), React Router (data mode), TanStack Query, Tailwind 4, shadcn/ui, react-hook-form + zod, react-i18next |
| Тесты | Pest (backend, на реальном PostgreSQL), Vitest + Testing Library + MSW (frontend) |
| Качество | Laravel Pint, Larastan level 6, ESLint + Prettier, `tsc` |
| Dev-окружение | Docker Compose: nginx, php-fpm, queue, scheduler, node (Vite), postgres, redis, mailpit |

## Команды (всё выполняется в Docker; локально нужны только docker и make)

```
make up              # поднять окружение (первый запуск тоже)
make fresh           # пересоздать БД: миграции + демо-данные (ВСЁ УДАЛЯЕТСЯ, включая файлы вложений)
make migrate         # новые миграции — под владельцем схемы (--database=pgsql_owner)
make db-roles        # перевести старую базу на роли selen_owner / selen_app (один раз; повтор безопасен)
make test            # все тесты (backend с покрытием + frontend с порогом покрытия 77 %); dev не нужен
make e2e             # тесты в браузере (Playwright) на изолированном стеке, dev-база не трогается
make perf            # замер производительности: доска на 300 карточек и пространство 5×200 (production-сборка, ~5 мин)
make metrics SPACE=DEV DAYS=60   # сводка lead/cycle time по доскам (проверка метрик)
make lint            # Pint, Larastan, ESLint, Prettier, tsc — без изменений файлов
make fix             # автоисправление стиля
make admin           # создать администратора (интерактивно)
make shell           # shell в контейнере php (artisan, composer)
make logs            # логи всех сервисов
make backup | make restore FILE=... | make backup-verify
make e2e-tc TC=3.8   # приёмочные автотесты тест-кейсов (несколько — через запятую); make e2e-stage STAGE=3 — этапа
make pm-up | pm-update | pm-bug FILE=... | pm-bug-move KEY=... TO=...   # стенд PM (runbook, «Стенд PM»)
make pm-bug-show KEY=LATER-12 | pm-bugs-list | pm-bug-comment KEY=... TEXT="..."   # баги стенда по номеру
make pm-task FILE=task.json   # карточка работы без карточки на стенде → «Бэклог», «Взято в работу»
make pm-owner-show | pm-transfer-ownership EMAIL=...   # Владелец стенда (ADR-0017)
make audit-deps      # уязвимости зависимостей (composer, npm frontend и e2e): падает на high/critical, как CI «Security»
make dev-status      # из какой рабочей копии поднят dev; make dev-take — забрать dev (только с разрешения PM)
make help            # полный список
```

Адреса: приложение http://localhost:8080, письма (Mailpit) http://localhost:8025, PostgreSQL localhost:54320.
Роли базы (ADR-0016): приложение и тесты — `selen_app` (только данные), миграции и бэкапы — `selen_owner`,
суперпользователь `selen` — только `make db-roles`.
Стенд PM (постоянная копия на коде main, ADR-0014): http://127.0.0.1:8081, письма http://127.0.0.1:8026.
Artisan: `docker compose exec php php artisan <команда>` — это dev той копии, из которой он поднят (`make dev-status`);
один тест backend — `./scripts/test-stack.sh --db vendor/bin/pest --filter=…`. npm: `docker compose run --rm node npm <команда>`.

## Обязательные правила

### Backend
1. **Бизнес-логика — в Actions/Services, не в контроллерах.** Контроллер: принять Form Request →
   вызвать Action → вернуть Resource. HTTP-специфика (регенерация сессии, cookie) остаётся в контроллере.
2. **Валидация — Form Requests, ответы — API Resources, доступ — Policies** (`Gate::authorize` или
   `authorize()` в Form Request). Бизнес-ограничения («нельзя оставить систему без админа») — в Actions,
   ошибка — `ValidationException` (422 с понятным текстом).
3. **Каждая фича сопровождается тестами** (Pest, `tests/Feature/...`): успех, валидация, права (403),
   граничные случаи. Сквозные сценарии с cookie — через хелпер `browser()` (tests/Support/Browser.php).
4. **Смёрженные в main миграции не редактируются** — только новые миграции.
5. **Все даты в БД — в UTC** (`timestampTz`, приложение и соединение PostgreSQL в UTC). В API даты
   отдаются в ISO 8601 с `Z`; в часовой пояс пользователя переводит frontend.
6. **Журнал событий (`event_log`) — append-only.** Писать только через `App\Services\EventLog\EventRecorder`
   внутри той же транзакции, что и доменное изменение. Новый тип события — новый case в `App\Enums\EventType`
   + `frontend/src/features/admin/eventTypes.ts` + перевод `admin.json → events.types` (сверяет тест
   `EventTypeCatalogTest`). Существующие значения типов не переименовывать. Подробно — docs/adr/0003-event-log.md.
   В payload — только id и значения перечислений, без email, имён и текстов (ПДн).
7. **Пользователей не удаляем** — только деактивируем. Приглашения тоже не удаляем.
8. API только под `/api/v1`. Ломающие изменения — через новую версию.
9. Секреты — только в `.env` (не в репозитории). Новая переменная → в `.env.example` с комментарием.
   **Роли базы (ADR-0016):** приложение — `selen_app` без владения и DDL; миграции — только
   `--database=pgsql_owner` (новое место запуска миграций — с этим флагом). Новая append-only таблица — `REVOKE`
   лишних прав у роли приложения в её миграции и строка в `docker/postgres/sql/grants.sql`.
10. Пароли и токены не логировать и не класть в payload событий. Параметры с секретами помечать `#[\SensitiveParameter]`.
11. **Доступ к содержимому пространств** — только через политики с трейтом `ChecksSpaceRole` (ADR-0005):
    не участник — 404, нехватка роли — 403. **Права — только из `Space::accessOf()` / `Space::accessesOf()`**
    (итоговые права по источникам: личное участие и группы, ADR-0012); источники из БД читает только
    `App\Services\Access\SpaceAccessResolver` — никаких прямых запросов к `space_members`/`space_groups` для прав.
    Действие разрешено, если его целиком разрешает хотя бы один источник (роль и «только свои» не смешиваются).
    В пространстве всегда есть хотя бы один **личный** активный администратор (ADR-0012); деактивация пользователя
    этот инвариант не проверяет — только предупреждает.
    Каждый новый маршрут пространства/доски/карточки — в матрицу `tests/Feature/Access/AccessMatrixTest.php`
    (иначе тест упадёт).
    **Режим «только свои карточки» (ADR-0008):** любая выборка карточек для пользователя — через
    `CardVisibility::scope()`, любая сущность внутри карточки (комментарии, файлы, чек-листы...) — с проверкой
    через `CardPolicy` / `allowCard()`. Чужая карточка — 404. Новое место применения — в таблицу ADR-0008.
    **Дерево навигации (ADR-0013):** папки доступа не дают; дерево пользователя строит только
    `NavigationTree::forUser` — папка без доступного пользователю пространства не попадает ни в один ответ
    (для всех, включая системного администратора; полная структура — только в «Структуре»). Единственное
    исключение — Владельцу видны ещё и по-настоящему пустые папки (без единого пространства на любой глубине),
    с `empty: true` (ADR-0017); пустая папка внутри скрытой не видна и ему.
12. **Положение карточки меняет только `CardPlacement`** (переход в `card_transitions` + метрики, ADR-0006;
    автоснятие блокировок при входе в «готово», ADR-0011). Позиции — дробные ключи, клиент присылает соседей
    `after_id`/`before_id` (ADR-0007).
13. **Связанная карточка показывается только через `CardVisibility::present()`** (связи, блокировки, лента
    истории): невидимая — `{hidden: true}`, без номера и названия. **`card_blocks`** — эпизоды: разрешено только
    закрыть открытый (триггер), правки и удаление запрещены; текст причины в журнал не пишется.
14. **Лента истории** (`CardHistory`) показывает все события по карточке: новый тип события с карточкой-subject
    попадёт в ленту сам (подпись — из `admin.json → events.types`); если в payload есть id карточки — ключ
    `card_id`/`blocking_card_id`, иначе маскировка его не увидит.
15. **Карточки не удаляются физически — только в корзину** (`SoftDeletes`, ADR-0015; удаляет системный
    администратор). Выборки Eloquent удалённых не видят сами. Запись, которая ссылается на карточку, грузит её
    `withTrashed()` и показывает/проверяет через `CardVisibility` (404, «Удалённая карточка»); «сырой» SQL по `cards`
    и `card_transitions` — только с `deleted_at IS NULL`. Триггеры append-only не ослаблять.
16. **Системные роли — `owner | admin | member` (ADR-0017).** `User::isAdmin()` (frontend — `isSystemAdmin`) —
    системный администратор, **включая Владельца**; исключительные права Владельца — `isOwner()` и политики
    (`UserPolicy::manages`: Владельцем не управляет никто, администраторами — только Владелец). Сравнение роли
    с `admin` напрямую — только осознанно, с комментарием почему. Роль `owner` назначается только передачей
    владения. Каждый новый маршрут `/admin/*` — в матрицу `tests/Feature/Access/AdminAccessMatrixTest.php`
    (owner / admin / member; иначе тест упадёт).

### Frontend
1. **Все строки интерфейса — через i18n** (`frontend/src/shared/i18n/locales/ru/*.json`). Литералы
   в JSX запрещены правилом ESLint `i18next/no-literal-string`.
2. Данные с сервера — только через TanStack Query (`features/<фича>/queries.ts`), HTTP — через `shared/api/client.ts`.
3. Формы — react-hook-form + zod; ошибки 422 раскладываются в поля через `applyValidationErrors`.
4. UI-компоненты — shadcn/ui в `shared/ui` (можно добавлять через `npx shadcn add ...`).
5. Типы ответов API — `shared/types/api.ts`, держать в синхроне с API Resources.
6. Тесты — рядом с кодом (`*.test.tsx`), запросы мокаются через MSW (`src/test/server.ts`).
7. **UI-референсы Kaiten.** Экраны, перечисленные в `docs/ui-reference/kaiten/README.md`, делаются и меняются
   со сверкой с этим README (раскладка и поведение описаны словами, скриншотов Kaiten в репозитории нет — ADR-0022):
   раскладка и поведение — как в Kaiten, фирменный облик (логотип, иконки, цвета) — свой.
8. **Подсказка к значку без текста — `Tooltip` (`shared/ui/tooltip`)** на элементе, который получает фокус, а не
   атрибут `title`: `title` не видна с клавиатуры и не во всех браузерах (LATER-57). Автотест проверяет видимую
   подсказку (роль `tooltip`), а не атрибут.
9. **Данные и действия — только от имени пользователя вкладки** (ADR-0002, «Изменения»): запросы несут его id
   (`X-Selen-User`), сервер на чужую сессию или запрос без заголовка отвечает 409 и ничего не выполняет; смену
   пользователя (вход, выход, 401, 409) обрабатывает `installSession` в `app/queryClient.ts` — сбрасывает весь кэш.
   Новые места, где меняется пользователь, — через него, без своих сбросов кэша. Запросы — только через
   `shared/api/client.ts`; адрес, который браузер открывает сам (`<img>`, скачивание), — на сервере
   `withoutMiddleware('tab-user')` и строка в `SessionUserMatchTest`.
10. **Правила вида — `docs/ui-guidelines.md`** (ADR-0023): цвета — только токены, шкала отступов, размеры, скругления,
    шрифт, состояния, тексты, контраст. Раскладка и поведение — по README Kaiten (правило 7), облик — по этому файлу.
    Новое правило вида или изменённое значение — строкой в файле в том же PR.

### Процесс
- Коммиты маленькие и осмысленные, **Conventional Commits** (`feat:`, `fix:`, `docs:`...); текст — на русском.
- **Отчёты и сообщения PM — на русском**: ответы в сессии, отчёты подэтапов и этапов, описания PR, тест-кейсы.
- Перед коммитом: `make lint && make test`.
- **Git и PR:** работа этапа — в ветке от актуального `main` (`stage-N` или подэтапы `stage-Na`, `stage-Nb`…).
  PR в `main` **не мёржится, пока PM не напишет «принято»**. После этого: мёрж через merge commit,
  удалить ветку этапа (локально и на GitHub), переключить локальную копию на свежий `main`.
  **Исключение — PR только с журналами и статусами** (решения PM 20.10, ADR-0014, «Изменения»): сессия мёржит PR
  сама после зелёного CI (merge commit, ветку удалить, свежий `main`) и сообщает PM ссылку — без ожидания «принято»,
  если **каждый** файл PR — это:
  - файл в `docs/stages/` (журналы этапов, хотфиксов, отчёты), но **не изображение** (`.png`, `.jpg`, `.gif`, `.webp`,
    `.svg`…) и **без новых или изменённых решений PM** (решения, поправки, ответы PM на вопросы — PM проверяет, как
    их записали);
  - или `docs/roadmap.md`, где изменены **только статус и ссылки существующих строк**: ни новых, ни удалённых, ни
    переставленных строк, «Этап» и «Что входит» не тронуты.

  Проверка перед мёржем: `git fetch origin`, затем `git diff --name-only --no-renames origin/main...HEAD` — только такие
  файлы (без `--no-renames` перенос файла снаружи в `docs/stages/` показал бы один новый путь); `git diff
  origin/main...HEAD -- docs/stages` — ни одной добавленной или изменённой записи о решении PM; `git diff
  origin/main...HEAD -- docs/roadmap.md` — только пары строк «−/+» таблицы, которые отличаются ячейками «Статус» и
  «Ссылки»; `gh pr checks` — все зелёные. Хоть один другой файл (код, тесты, скрипты, CLAUDE.md, ADR, runbook,
  `docs/security`, `docs/ui-*`, конфиги), хоть одна картинка (репозиторий публичный — картинку должен увидеть PM),
  решение PM в журнале, новая строка или изменение состава этапов в `docs/roadmap.md` — обычный порядок.
- Подэтапы: если предыдущий PR уже смёржен — новая ветка от свежего `main`. Ветку от ветки (stacked PR)
  делаем, только пока предыдущий PR ждёт проверки; её не rebase'им (GitHub сам перенацелит PR на `main`),
  при конфликтах — `git merge main` в ветку.
- Упавший CI чиним сами до отчёта PM; автоисправление CI не включаем и не предлагаем.
- **Один подэтап — одна сессия.** После отчёта по подэтапу следующий начинается в новой сессии. Отчёт подэтапа
  короткий: что сделано, ссылка на PR, тест-кейсы; полный отчёт этапа — в конце последнего подэтапа.
- **Журнал этапа** (`docs/stages/stage-N.md`) обновляется и коммитится после каждого крупного блока —
  чтобы обрыв сессии не терял состояние.
- **Не оставлять крупные незакоммиченные изменения:** коммитить рабочие промежуточные состояния
  (lint и тесты затронутой части зелёные).
- **Приёмка подэтапа перед PR** (стенд PM и QA-бот — docs/runbook.md, «Стенд PM»):
  1. Субагент-ревьюер — независимое ревью кода.
  2. Субагент-тестировщик (не участвовал в написании кода): `make fresh` на dev-стеке, проходит в браузере все
     тест-кейсы раздела «Как проверить руками». Где можно — читает текст страницы, а не делает скриншоты; скриншот —
     только доказательство провала. На каждый провал — карточка `make pm-bug FILE=…` (стенд недоступен — список
     в отчёте).
  3. **Тест-кейс → автотест** (с подэтапа 3c; старые тест-кейсы задним числом не автоматизируются). Пройденный
     в браузере тест-кейс тестировщик закрепляет Playwright-тестом `e2e/acceptance/stage-<N>/tc-<этап>.<номер>.spec.ts`
     с тегом `@tc-<этап>.<номер>` в названии, вход — через storageState (`e2e/acceptance/README.md`). Автотест
     провалившегося тест-кейса — регрессионный тест бага: падает до исправления, проходит после; ссылка на файл —
     в карточке бага. Удобство и внешний вид, которые скриптом надёжно не проверить, — «только вручную» (их
     проверяет PM). В основную сессию тестировщик возвращает только таблицу: тест-кейс → прошёл / провал (номер
     карточки) → автотест (файл или «только вручную»).
  4. **UX/UI-ревью** — если подэтап меняет интерфейс: агент `ux-reviewer` (`.claude/agents/`, ADR-0023) после
     тестировщика. Перед вызовом основная сессия делает `make fresh` (тестировщик менял данные) и открывает встроенный
     браузер на любой странице dev (агент работает только в своей фоновой вкладке; закрытую панель не открывает —
     останавливается). Перед открытием dev во встроенном браузере сессия смотрит вкладки (`tabs_context`): открыт стенд
     как `localhost:8081` — пишет об этом PM и dev в браузере не открывает, пока PM не переоткроет стенд как
     `http://127.0.0.1:8081` (общая cookie `XSRF-TOKEN` — runbook, «Стенд PM»). В
     задании — ветка и коммит, экраны (адреса или путь по дереву) и что изменилось, пользователь демо-данных. Находки
     «важно» основная сессия исправляет до отчёта PM (проверка — E2E или повторный короткий вызов агента по этому
     экрану — в том же бюджете);
     «важно» на месте, которое подэтап не менял, — карточка `make pm-bug` с меткой «UX»; «мелочь» и «вкус» — таблицей
     в отчёте PM; предложения агента для `docs/ui-guidelines.md` — в том же PR.
  5. Основная сессия исправляет провалы. Повторная проверка — **только скриптом**: `make e2e-tc TC=3.8` (несколько —
     через запятую) или `make e2e-stage STAGE=3`; исправленные карточки — `make pm-bug-move KEY=… TO=Исправлено`.
     **Менять приёмочные тесты, чтобы они прошли, основной сессии запрещено.** Если неверен сам тест — исправление
     с объяснением в отчёте PM и в комментарии к карточке бага.
  6. В отчёте PM — итоговая таблица тест-кейсов с колонками «Результат», «Карточка», «Автотест» (файл или «только
     вручную»); неисправленные провалы — явно, с причиной; итог UX/UI-ревью — числа «важно / мелочь / вкус», что
     исправлено, остальное таблицей.

  Приёмочные тесты входят в `make e2e` и CI; если E2E в CI станет дольше ~10 минут — разнести на параллельные job'ы
  и сообщить PM. Тестировщик не заменяет ручную приёмку PM: PM проверяет удобство и продуктовые решения. Бюджет
  субагентов на подэтап — два (ревьюер и тестировщик), аудитор безопасности, когда он положен (ниже), и UX/UI-ревьюер,
  когда меняется интерфейс; другие — только если основная сессия заметно раздувается. `ux-reviewer` — как и аудитор:
  только из `~/dev/selen` или его рабочих копий (hook работает, только если Claude Code доверяет папке; без hook агент
  браузер не открывает); из нового или изменённого описания — со следующей сессии. Dev показывает код той копии, из
  которой поднят (`make dev-status`): тестировщика и ревью звать, только когда dev поднят из своей копии; чужой — просить
  PM разрешить `make dev-take` («Параллельные сессии»).
- **Параллельные сессии** (LATER-92; runbook, раздел 15). Сессии работают одновременно, каждая — в своей рабочей копии.
  - **Одна папка — одна сессия**, в том числе основная `~/dev/selen`: вторая сессия — в своей копии
    (`.claude/worktrees/…`). Две сессии в одной папке замок не различит — у них общий код.
  - **Dev (http://localhost:8080) — у одной копии за раз.** Цели Makefile, которые работают с dev, сначала проверяют,
    из какой копии он поднят (замок): чужая — отказ с объяснением. Забрать dev — `make dev-take`, **только
    с разрешения PM**; **разрешение на dev-take PM может дать сразу в задании**. Новая цель Makefile, которая работает
    с dev (`$(PHP)`, `$(ARTISAN)`, `$(DC) up/down/exec`, скрипты бэкапа), — с `$(DEV_LOCK) $@` первой строкой рецепта
    (иначе упадёт `scripts/test-parallel.sh`).
  - Dev — только через цели Makefile: `docker compose up | down | exec` напрямую замок не проверяет, а `exec` — это dev
    любой копии, которая его подняла; тесты, composer — `./scripts/test-stack.sh` (runbook, раздел 15).
  - Тесты и линтеры (`make test`, `make lint`, `make fix`) и E2E работают в любой копии без dev — в стеках своей копии.
  - `.env` рабочей копии — ссылка на `.env` основной: **не правьте его в копии** (изменится `.env` основной и dev);
    новая переменная — в `.env.example`.
  - Стенд — только `make pm-*`, одна сессия за раз.
  - Бэклог (`docs/pm/deferred.yaml`) и дорожную карту (`docs/roadmap.md`) правит одна сессия, остальные просят PM.
- **Аудит безопасности** — агент `security-auditor` (`.claude/agents/`, ADR-0020): только читает код и выполняет
  команды из белого списка, ничего не меняет.
  - **Когда:** полный аудит — в конце каждого этапа (до отчёта этапа) и перед пилотом, отчёт —
    `docs/security/audit-ГГГГ-ММ.md`. Точечный (по изменениям ветки) — в подэтапе или хотфиксе, если затронуты вход
    и сессии, права (политики, `SpaceAccessResolver`, `CardVisibility`, дерево, админка), файлы (вложения, выдача) или
    инфраструктура (Docker, nginx, скрипты хоста и стенда, CI); итог — строкой в отчёте подэтапа. **Не чаще** —
    бережём лимиты.
  - **Находки:** «критично» — PM сразу, не дожидаясь отчёта; «критично» и «важно» — карточки `make pm-bug` с
    `"labels": ["безопасность"]` (JSON готовит аудитор, заводит основная сессия); «мелочь» — в отчёте.
    Исправления — отдельными задачами, не в PR аудита.
  - **Где запускать:** только из `~/dev/selen` или его рабочих копий (`.claude/worktrees/…`). Hook агента работает,
    только если Claude Code доверяет папке; агент проверяет это первой командой и без hook не выполняет команд Bash.
    Агент из нового или изменённого описания доступен со следующей сессии.
- **Проверки безопасности в CI** (workflow «Security», ADR-0020): уязвимости зависимостей high/critical (`make audit-deps`)
  и секреты во всей истории git (gitleaks); на каждый push, PR и раз в неделю. Красная проверка из-за новой уязвимости
  (а не из-за изменений ветки) — карточка или хотфикс с обновлением зависимости, а не правка в чужом PR. PR Dependabot
  (обновления безопасности — сразу; minor/patch — одним PR в неделю; major не предлагаются) мёржатся как любые: CI
  зелёный и «принято» PM.
- **Работа без карточки на стенде** (инфраструктура, хотфикс, подэтап): в начале работы — карточка на «Бэклоге»
  стенда `make pm-task FILE=task.json` (колонка «Взято в работу», метка подэтапа; формат — runbook, «Стенд PM»).
  Дальше — как с LATER-задачами: тест-кейсы и ссылка на PR — комментарием `make pm-bug-comment KEY=LATER-N FILE=…`,
  после «принято» и мёржа — `make pm-bug-move KEY=LATER-N TO=Сделано`. Если PM уже завёл карточку — работать с ней.
- **«Сделай / исправь LATER-N»** (баги PM на доске «Баги приёмки» стенда, в том числе с меткой «UX», и доработки
  с доски «Бэклог»):
  1. `make pm-bug-show KEY=LATER-N` — прочитать карточку и скриншоты (`.pm-bugs/LATER-N/`). **Задание — описание
     карточки:** если в нём промт или подробное ТЗ от PM, выполнять его целиком; название карточки — только краткая
     метка. Описание противоречит названию или комментариям — спросить PM. Не хватает шагов или ожидаемого
     результата — спросить PM, не угадывать.
  2. `make pm-bug-move KEY=LATER-N TO=Исправляется`, `make pm-bug-comment KEY=LATER-N TEXT="Взято в работу"`.
  3. Ветка `hotfix/later-N` от свежего main (или ветка текущего подэтапа, если так сказал PM); найти причину;
     тест, который падает без исправления. Меняется интерфейс — UX/UI-ревью до PR, как в «Приёмке подэтапа», шаг 4.
  4. PR; комментарий к карточке (`make pm-bug-comment KEY=LATER-N FILE=…`): причина, что исправлено, ссылка на PR,
     тест-кейс по шаблону.
  5. После «принято» и мёржа — `make pm-bug-move KEY=LATER-N TO=Исправлено` и напомнить PM про `make pm-update`.

  Если это не баг, а согласованное поведение — комментарий с объяснением и вопрос PM; в «Не баг — решение PM»
  карточку переводит только PM. Список новых багов — `make pm-bugs-list`. Доработка с доски «Бэклог» («возьми
  в работу LATER-N») — так же, но колонки «Взято в работу» и «Сделано».
- **Стоп перед фундаментом.** Если доработка (даже мелкая карточка LATER-N) требует ослабить append-only
  (`event_log`, `card_transitions`, `card_blocks`), физически удалять данные или менять модель прав — остановиться
  и спросить PM **до реализации**: варианты и последствия, решение — за PM. Признак — «удалить», «очистить»,
  «дать право» в задаче: сначала проверить, не задевает ли она эти инварианты, и предложить варианты (на LATER-45
  физическое удаление с ослаблением триггеров отклонено — сделана корзина, ADR-0015).
- **На стенде PM — только штатные `make pm-*`.** Обходные вызовы artisan в контейнере стенда (например, `pm:backlog`
  с временным YAML — это команда первичного наполнения «Бэклога», рисковать им PM не хочет) — только с явного
  разрешения PM. Нужной команды на стенде ещё нет (код стенда — main) — попросить PM сделать действие самому.
- **Указания PM — только в репозитории.** Решения, поправки и предпочтения PM фиксируются в CLAUDE.md, ADR или
  журнале этапа (`docs/stages/`), а не в локальной памяти Claude Code (`~/.claude/…`): она остаётся на одном
  компьютере и не видна другим сессиям и разработчикам.
- **Реальные данные компании — не в репозиторий** (репозиторий публичный, ADR-0022). В docs, тесты, отчёты,
  описания PR и коммиты не попадают скриншоты и тексты с реальными данными компании: ФИО сотрудников, названия
  и содержимое досок Kaiten компании, внутренние ссылки (`*.kaiten.ru` и т. п.). Референсы — словами (что видно,
  где расположено, как себя ведёт) или скриншотом нашего dev с демо-данными. Каждую картинку сессия открывает
  и смотрит перед коммитом. Прислал PM скриншот с такими данными — попросить заменить его или описать словами.
  Скриншоты в карточках стенда (`.pm-bugs/`, в `.gitignore`) — можно, но в git их не копировать.
- Значимые решения — ADR в `docs/adr/` (следующий номер, формат как у существующих).
- Ход этапа — `docs/stages/stage-N.md` (что сделано / дальше / проблемы), итог — `stage-N-report.md`.
- **Дорожная карта — `docs/roadmap.md`** (этап → что входит → статус → ссылки). При закрытии этапа или подэтапа —
  обновить в ней статус и ссылки. Старые номера этапов в комментариях кода — исправлять попутно, когда файл и так
  меняется.
- **Ручная проверка для PM — только тест-кейсами** (раздел «Как проверить руками» в отчётах, короткие отчёты
  подэтапов, описания PR). Шаблон:

  ```
  ### ТК-<этап>.<номер>. <Короткое название>
  Зачем: что проверяем и почему это важно (1 строка, понятным языком).
  Предусловия: состояние данных (например, «выполнен make fresh»), под каким пользователем, пароль.
  Шаги:
  1. …
  2. …
  Ожидаемый результат:
  - конкретные наблюдаемые признаки: что должно быть видно на экране и чего быть не должно.
  Если не так: что прислать (обычно — скриншот).
  ```

  Один тест-кейс — одна проверяемая вещь. Шаги — конкретные клики и пути (Дерево → «Эксплуатация» →
  «Участники»), без технических терминов. Ожидаемый результат — то, что PM видит глазами, а не внутреннее
  устройство. Если для сравнения нужен второй пользователь — отдельный шаг с явным ожидаемым результатом.

## Ловушки (уже наступали)

- В контейнере переменные `.env` попадают в `$_SERVER`; в `phpunit.xml` каждая переменная задаётся и как
  `<env>`, и как `<server>` с `force="true"`. Не удаляйте это — иначе тесты сотрут рабочую базу.
  Защита: `tests/TestCase::createApplication()` откажется работать не с `selen_testing`.
- `DatabaseTruncation` в тестах не использовать: триггер `event_log` запрещает TRUNCATE. Только `RefreshDatabase`.
- Отложенный триггер `users_owner_kept` («Владелец не пропадает», ADR-0017) проверяется при COMMIT, а транзакция
  теста (`RefreshDatabase`) не фиксируется — в тестах он молчит. Проверять с `SET CONSTRAINTS users_owner_kept IMMEDIATE`.
  Хелпер `owner()` в тестах — Владелец системы, `asOwner($sql)` — запрос под владельцем схемы БД (это разное).
- `FOR UPDATE` в PostgreSQL нельзя совмещать с `count()` — блокировать строки и считать в PHP.
- JSONB не сохраняет порядок ключей — в тестах payload сравнивать через `toEqual`, не `toBe`.
- После изменения `.env` — `make restart` (контейнеры читают его при создании). Не правьте `.env` через `sed -i`:
  он создаёт новый файл, а контейнеры смонтировали старый — Laravel перестаёт видеть `.env`.
- Vite в Docker на macOS не получает события файловой системы — включён опрос (`VITE_USE_POLLING=true`).
- Ключ пространства — только латинские буквы (`^[A-Z]{2,10}$`, CHECK в БД): `E2E` недопустим.
- В Pest-тестах с `travelTo()` время двигаем только вперёд от текущего: иначе cookie хелпера `browser()`
  считаются истёкшими. Сдвиг больше чем на 480 минут завершает сессию (так и задумано).
- `npx shadcn add ...` (CLI 2026) не разрешает наш алиас `utils` и **ставит посторонний npm-пакет `cn`**
  с импортом `from "cn"`. После добавления компонента: откатить `package.json`/`package-lock.json`,
  заменить импорт на `@/shared/lib/utils`, прогнать `make fix`.
- `pest --parallel` сейчас не работает (несовместимость pest 5.3 и paratest) — запускаем в один поток.
- **Права файлов на macOS не проверяются** (Docker Desktop/Colima): то, что nginx не может прочитать файл,
  видно только на Linux (CI, production). Файлы вложений — 0644/0755 (`visibility: public` у диска `attachments`).
- В Pest-тестах SQL-функция `now()` — время начала транзакции теста (`RefreshDatabase`), оно раньше времени
  PHP; в «сырых» запросах тестов используйте `clock_timestamp()`.
- Запрет ленивой загрузки срабатывает только для моделей, загруженных коллекцией: одиночный тест может пройти,
  а список упадёт. В ресурсах и сервисах — `with()`/`setRelation()` заранее.
- **E2E-тест не входит через форму**: `test.use({ storageState: authFile('e2e-...') })` или `pageAs(browser, ...)`
  (`e2e/tests/helpers.ts`). Лимит входа — 5 в минуту на пользователя и 20 на IP; лишний `login()` роняет
  соседние тесты на входе. Через форму — только `auth.setup.ts` и `auth.spec.ts`.
- **dnd-kit: в `onDragOver` состояние меняется только при смене целевой ячейки, а цель выбирается по указателю.**
  Перенос карточки сдвигает раскладку; если цель считать по прямоугольникам (`closestCorners`), она «перескакивает»
  обратно — пинг-понг между колонками каждый кадр и «Maximum update depth exceeded». Цель — `useBoardDnd`
  (`collisionDetection`). Перетаскивание проверять E2E на «Плотной доске» сериями махов без пауз (`board.spec.ts`).
- **bash 3.2 (macOS) под UTF-8-локалью** считает байты не-ASCII символа частью имени переменной: `«$VAR»` →
  «unbound variable» (у PM в терминале так упали `make pm-backup` и `make backup`; у сессии локаль `C`, и ошибка
  не видна). Переменную вплотную перед не-ASCII символом — только `${VAR}»`. Проверяет `scripts/check-scripts.sh`
  (`make lint`, CI).
- **Роль приложения не меняет схему и историю** (ADR-0016): `php artisan migrate` без `--database=pgsql_owner` падает
  на правах (схема не меняется), `UPDATE`/`DELETE`/`TRUNCATE` истории в тестах — ошибка прав 42501, а не текст
  триггера. Триггеры проверять под владельцем: `asOwner($sql)` (tests/Pest.php). Тесты — `RefreshDatabaseAsOwner`.
- **Cookie сессии общие для всех вкладок браузера**: вход другим пользователем в соседней вкладке меняет сессию и
  в этой. Без `X-Selen-User` вкладка показывала смесь двух пользователей и действовала от имени нового (LATER-57).
  Порядок middleware задают `prependToPriorityList` в `bootstrap/app.php` (`route:list -v` порядок не показывает;
  фактический — `app('router')->gatherRouteMiddleware($route)`). Тесты: `actingAs` (TestCase) и `browser()` сами шлют
  `X-Selen-User`; прямой API-запрос в E2E — с Referer и `X-Selen-User` из `/auth/me`. В E2E перед подменой cookie —
  `waitForLoadState('networkidle')`: каждый ответ Laravel заново ставит cookie сессии и вернул бы прежнего. E2E проверяет такое подменой
  cookie контекста (`context.clearCookies()` + `addCookies` из storageState другого пользователя), не выходом через
  меню: выход завершил бы общую для прогона сессию storageState.
- **`X-Forwarded-For` присылает сам клиент** (LATER-61, ADR-0021). Доверенные прокси — только `TRUSTED_PROXIES`
  (пусто — никому: пустой список, не `null`, иначе Laravel доверяет всем при `Host: *.on-forge.com`; стенд за
  `tailscale serve` — сети Docker). `trustProxies(at: '*')` не возвращать: с ним лимиты
  входа обходились новым адресом в заголовке. IP клиента в коде — только `$request->ip()`. В Docker на macOS nginx
  видит любого клиента хоста как шлюз Docker (dev — 172.19.0.1).
- **Расширения PHP не с pecl.php.net (LATER-82):** `redis` и `pcov` в `docker/php/Dockerfile` — из архивов тегов GitHub
  с проверкой sha256, установщику передаются пути к папкам. `install-php-extensions redis` (по имени) снова пошёл бы на
  PECL, который то и дело не отвечает. Новая версия — runbook, раздел 12.
- **Порты в compose-файлах — только `"127.0.0.1:ПОРТ:…"`** (dev, E2E, стенд). Без адреса Docker слушает все интерфейсы:
  на Mac mini dev был открыт в офисную сеть и tailnet, а у dev-базы пароль по умолчанию (ADR-0018). `make host-status`
  и ежечасный бэкап предупреждают о порте не на 127.0.0.1. На этом держится и доверие прокси стенда (ADR-0021).
- **Окно не прокручивается (ADR-0019):** прокручиваются `main` обычной страницы и холст страницы досок
  (`[data-board-canvas]`), тело доски — вбок. В коде и E2E прокрутку ищем у контейнера, не у `window`. `sticky`
  привязывается к ближайшему прокручиваемому предку, а `overflow-x: auto` делает элемент прокручиваемым и по
  вертикали — поэтому заголовки колонок вынесены из тела доски и повторяют его прокрутку (`useSyncedScrollLeft`).
- **Полоса дорожки, закреплённая при прокрутке вниз, — `position: fixed` (`useStickyLaneRows`, ADR-0019):** CSS sticky
  внутри тела доски по вертикали не работает (см. выше). У fixed-элемента цепочка прокрутки — окно, а не холст: колесо
  и тачпад над ним ничего не прокручивали бы — их пробрасывает хук. Новый закреплённый элемент внутри тела — так же.
- **Доска из дерева открывает страницу пространства** (`/spaces/KEY?board=ID`, все доски рядами, ADR-0019): в E2E
  `document.querySelector('[data-board-body]')` там — первая доска страницы, не открытая. Тесты одной доски открывают её
  страницей `/boards/ID` (`openBoard`), страницы пространства — `openSpaceBoard` и поиск внутри `region` доски.
- **Доски на странице пространства грузятся по IntersectionObserver**: во вкладке, которую браузер не рисует (скрытая
  панель встроенного браузера, фоновая вкладка), он не срабатывает — доски «вечно грузятся». Проверять при видимой
  панели или E2E (headless рисует).
- Контейнер прокрутки (`overflow-*-auto`), внутри которого есть абсолютно позиционированные элементы (в том числе
  `sr-only`), должен быть `relative`: иначе они отсчитываются от корня документа, не обрезаются и растягивают всю
  страницу (так доска прокручивала страницу целиком). Vitest/jsdom раскладку не считает — такое ловит только E2E.
